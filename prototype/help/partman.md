# 分区维护

菜单：SQL 查询 › 分区维护。为按时间 RANGE 分区的表配置"提前创建多少个分区、保留多久"，由系统自动续建新分区、清理过期分区，取代手写 `ALTER TABLE ... PARTITION` 脚本，也不再需要外部常驻的分区维护程序。

支持的实例：**MySQL / PolarDB**（`information_schema.PARTITIONS` 读分区）和 **SelectDB / Doris**（`SHOW PARTITIONS` 读分区，语法不同，见下文）。其它类型（SQL Server、PolarDB-X、ADB 等）标"暂不支持"，不能新增 / 预览 / 执行。

> 已经分区的表只**续建和清理**。MySQL 的**未分区表**可以由你**显式点一下**"初始化为分区表"（见下文），定时维护永远不会做这件事；SelectDB / Doris 的未分区表不会被初始化，需要先在库里建成 RANGE 分区表。

## 配置一张表

点「新增配置」（`partman.add`），填写：

| 字段 | 说明 |
|---|---|
| 实例 / 库 / 表 | 库名、表名、字段名必须匹配 `^[0-9A-Za-z_$]{1,64}$`；系统库（mysql、information_schema 等）不允许；库名还要符合实例的库名过滤规则。仅主库的 MySQL / SelectDB / Doris 实例可选 |
| 分区字段与类型 | 下拉里只列该表 datetime / int / bigint 类型的字段，类型随所选字段自动识别：`int`（秒级时间戳）、`bigint`（毫秒时间戳）、`datetime`（MySQL 必须是 RANGE COLUMNS）；int 秒级时间戳超过 2038 年上限时会拒绝并提示改 bigint |
| 周期与跨度 | 分钟 / 小时 / 天 / 周 / 月 / 年；跨度是每个分区覆盖几个周期 |
| 预创建数 | 当前时刻所在分区之后，要保证有几个分区 |
| 保留数 | 只保留最近几个历史分区，更早的会被删除；`0` 表示全部保留 |
| 时区 | 可留空，也可自由输入，见下一节 |
| 说明 | 自由文本，会显示在列表里并参与搜索 |
| 自动维护 | 开关；关闭时该配置只能预览，不能执行，也不参与定时维护 |

系统**只接受结构化配置，不接受手写 DDL**；分区名与边界值全部由服务端计算。

### 时区怎么填

时区决定"按哪个时区的墙上时间划分边界"。输入框里有常用项，也可以自由输入：

| 写法 | 例子 | 说明 |
|---|---|---|
| 留空 | （空） | **跟随目标库当前会话时区**（系统用 `SELECT TIMESTAMPDIFF(SECOND, UTC_TIMESTAMP(), NOW())` 取当前固定偏移，Doris 同理）；预览和列表里会显示实际使用的偏移 |
| 固定偏移 | `+08:00`、`+0800`、`+8`、`UTC+8`、`GMT+08:00`、`UTC-3`、`UTC` | 偏移绝对值不超过 14:00，分钟小于 60；`+00:00` 等于 UTC。**没有夏令时歧义，推荐** |
| IANA 名字 | `Asia/Shanghai`、`America/New_York`、`Europe/London` | 服务端内置时区库，不依赖服务器；**区分大小写**，不接受 `Local` |

- 库里的 `timezone` 列只有 20 个字符，更长的名字（如 `America/Argentina/Buenos_Aires`）会被拒绝，请改用固定偏移（如 `-03:00`）；
- 有夏令时的 IANA 区域（如 `America/New_York`）会给出**警告**（不拒绝）：换季日前后按日的分区边界在 UTC 上会漂移 1 小时，按小时 / 分钟的分区还可能在换季时重复或缺失一个窗口，建议改用固定偏移（如 `-05:00`）；
- 输入框下方会实时提示识别结果，保存和预览时同样校验。

## 列表与状态

配置页顶部的提示条给出定时自动维护的状态：是否开启、自动删除过期分区的开关、每多少分钟一轮和推送时机（规则见下文"定时自动维护"）；下面是六张统计卡（配置数、自动维护已开启、待续建、待清理、未分区、异常）。可按实例、自动维护开关、字段类型、周期筛选，搜索框匹配库名、表名和说明。

列表每行显示：实例 / 库.表 / 说明、分区字段与类型（`int` 为秒、`bigint` 为毫秒）、周期与跨度、预创建数、保留数、时区、自动维护开关、上次执行（时间、来源、结果）、状态和操作（预览并执行 / 编辑 / 启用或停用 / 日志 / 删除）。时区列：留空的显示"跟随目标库"和实际使用的偏移，有夏令时的 IANA 区域带「夏令时」标记；自动维护已开启而定时维护未开启时，开关下方标注"定时未开启"。

状态由读取目标表的真实分区后计算（只读）：

| 状态 | 含义 |
|---|---|
| 正常 | 分区已是最新，没有需要执行的语句 |
| 待续建 N | 当前分区之后不足"预创建"个，还差 N 个 |
| 待清理 N | 已过去的历史分区超过"保留数"，有 N 个可清理 |
| 待续建 + 待清理 | 两者同时存在 |
| 未分区 · 可初始化 | MySQL / PolarDB 的表还不是分区表，可在「预览并执行」里显式初始化（定时维护不会初始化） |
| 未分区 · 不可初始化 | 前置检查不通过，原因写在状态下方（见"初始化未分区的 MySQL 表"） |
| 异常 | 无法生成维护计划，原因写在状态下方：表不存在、字段类型不符、SelectDB / Doris 的表未分区（需先在库里建为 RANGE 分区表）等 |
| 暂不支持 | 实例类型不在 MySQL / PolarDB / SelectDB / Doris 之列，不能编辑和执行 |

**删除配置**会同时删除它的全部维护日志（避免新建同名配置时继承旧日志）；目标表上已有的分区不会被改动，只是之后不再自动续建 / 清理。

## 命名与边界

分区名由服务端按窗口计算，与原外部程序一致：

| 周期 | 分区名 | 例 |
|---|---|---|
| minute | `pYYYYMMDDHHmm`（窗口起始） | `p202610091530` |
| hour | `pYYYYMMDDHH`（窗口起始） | `p2026100915` |
| day | `pYYYYMMDD`（窗口起始） | `p20261009` |
| week | `pYYYYMMDD`，取**窗口最后一天**（旧版取周一，已改） | 周一 10-05 开始的周分区叫 `p20261011` |
| month | `pYYYYMM` | `p202610` |
| year | `pYYYY` | `p2026` |

- 新增分区**从"现有最后一个有边界的分区"的边界续接**，不依赖对齐网格；已存在的分区只看**边界**、不看名字（现网分区可能是原程序建的）；
- 将创建的分区与现有分区**同名但边界不同**会被拒绝（`name_conflict`），不会硬建；
- 只有"初始化未分区表"才按原程序的网格对齐：minute / hour 按日内取整，day 按 1970-01-01 起算的跨度倍数，week 按 1970-01-05（周一）起算，month 按 1970-01、year 按公元年的跨度倍数。

## SelectDB / Doris 的差异

| | MySQL / PolarDB | SelectDB / Doris |
|---|---|---|
| 读现有分区 | `information_schema.PARTITIONS` | `SHOW PARTITIONS`，`Range` 列里**最后一个** `keys: [...]` 是上界 |
| 新增 | `ALTER TABLE db.t ADD PARTITION (PARTITION p VALUES LESS THAN (边界))`，每个分区一条 | `ALTER TABLE db.t ADD PARTITION p VALUES [("下界"), ("上界"))`，每个分区一条 |
| 删除 | `DROP PARTITION p`，每个分区一条 | 同左 |
| 边界字面量 | datetime `'YYYY-MM-DD HH:MM:SS'`；int 秒；bigint 毫秒 | 都是双引号字符串：`"2026-10-08 00:00:00"`、`"1791388800000"`（bigint 13 位毫秒）、`"1791388800"`（int 10 位秒） |
| MAXVALUE 分区 | 改用 REORGANIZE（需确认，定时不执行） | **拒绝**（`max_partition`）：不能在 MAXVALUE 之后追加 |
| 未分区表 | 可显式初始化 | **不初始化**（`not_partitioned`）：请先建为 RANGE 分区表 |
| 上界读不到的分区 | 整体拒绝（`bad_bound`） | 视为"未知"：**不会被删除**，计划里给警告，其它分区照常处理 |

> 不同 Doris 版本 `SHOW PARTITIONS` 的 Range 文本略有差异（`keys: [1781937000000]`、`keys: [2026-06-20 06:30:00]`、多个 keys、带 `types:` 段都能识别）。读不出上界的分区，宁可保留也不会误删。

## 续建与清理规则

- **续建**：从现有最后一个有边界的分区继续向后接，保证边界连续；所有分区都已过期时先补到包含当前时刻的分区（追赶）；单次最多创建 100 个，超过就拒绝（说明配置不合理）；
- **清理**：边界早于当前时刻的是"历史分区"，只保留最近"保留数"个，更早的 `DROP PARTITION`；`MAXVALUE` 分区永不删除；
- MySQL 表里有 `MAXVALUE` 分区时无法直接 `ADD PARTITION`，改用 `REORGANIZE PARTITION`，会重写该分区的数据，标记为"重操作"，需要额外确认。

保存前可以点「预览」查看将要执行的语句和**检查过程**（只读，不会改动任何表）：

```sql
ALTER TABLE order_db.order_event ADD PARTITION (PARTITION p20261009 VALUES LESS THAN ('2026-10-10'));
ALTER TABLE dw_ads.ads_traffic_hour ADD PARTITION p2026100714 VALUES [("2026-10-07 14:00:00"), ("2026-10-07 15:00:00"));
ALTER TABLE order_db.order_event DROP PARTITION p20260702;
```

## 预览并执行

点「预览并执行」（`partman.run`，高危）：

1. 系统重新读取目标表、重新计算计划，列出将创建与将删除的分区，并给出"检查过程"；
2. **含 DROP 时必须输入 `库.表` 确认**（并需要 `partman.delete` 权限）；REORGANIZE 需要勾选确认；
3. 执行时服务端会**再次读取并核对**——如果预览之后表被别人改过、与你确认的内容不一致，会拒绝（409 `confirm_required`）并给出新计划，不会误删；
4. 执行前先写审计日志（含完整语句），写不进去就不执行；MySQL 执行时设置了 `lock_wait_timeout=15`，拿不到元数据锁就失败，不会让业务查询在 ALTER 后面排队；语句遇到第一个失败即停，其余标为未执行；
5. 同一个配置同一时刻只有一个维护在跑（手动和定时互斥）；配置的"自动维护"开关是关的时，需要先开启才能执行（`disabled`）。

> ⚠ `DROP PARTITION` 会永久删除该分区的数据且不可恢复。请先确认保留数配置符合数据保留要求，必要时先[导出](#help/export)留档。

## 初始化未分区的 MySQL 表

对**尚未分区**的 MySQL / PolarDB 表，列表状态显示"未分区 · 可初始化"。点「预览并执行」会进入初始化流程——这是一个**显式的、危险的重操作**：`ALTER TABLE … PARTITION BY RANGE` 会重建整张表（拷贝数据、持有元数据锁，期间表不可写），大表耗时很久，请在业务低峰执行。

**1. 选择起点**（`start_mode`）：

| 起点 | 含义 |
|---|---|
| 从当前窗口开始（默认） | 不读存量数据。早于第一个分区上界的存量行会全部落进第一个分区（之后按保留数删除它就会丢掉这些数据）；晚于最后一个分区上界的行会让 ALTER 失败，预览里会给出提示 |
| 从最早数据开始 | 执行一次 `SELECT /*+ MAX_EXECUTION_TIME(20000) */ MIN(分区字段)`（最长 20 秒）。超时或失败会拒绝（`earliest_unavailable`），请改用"指定起始日期"；表是空的则按"当前窗口"处理并说明 |
| 指定起始日期 | `YYYY-MM-DD`（可带 `HH:MM:SS`），在配置时区下向下对齐到网格；不能晚于当前窗口 |

分区从起点窗口一直建到"当前窗口 + 预创建数"，**不带 MAXVALUE 兜底分区**。

**2. 前置检查**（任何一项 ✗ 都不会发出 ALTER，并说明原因）：

| 检查 | 要求 |
|---|---|
| `table_kind` | 是普通表，不是视图 / 临时表 |
| `engine` | 存储引擎支持分区（MySQL 8.0 只有 InnoDB / NDB） |
| `foreign_key` | 表上没有外键（MySQL 分区表不支持外键） |
| `column` / `column_type` | 分区字段存在，类型是 bigint / int / datetime 且与配置一致 |
| `unique_keys` | **每一个唯一键（含主键）都包含分区字段** |
| `partition_count` | 将创建的分区数不超过 5000（超过 200 给警告，ALTER 会很慢） |

**3. 确认并执行**：弹窗列出起点、将创建的分区个数与范围（首个 ~ 末个、最后边界）和语句，**必须输入 `库.表`** 才能点"确认初始化"；需要 `partman.run`，并且与 DROP 一样需要 `partman.delete`（没有则 403）。服务端会重新读取目标表并重算计划，要求确认值（分区个数、首个 / 末个分区）与重算结果一致，否则拒绝并给出新计划。审计先于执行。

> **定时维护永远不会初始化**：未分区的表在定时一轮里直接跳过，只记服务日志，不写维护日志、不推送。

## 维护日志与运行输出

「维护日志」页签记录每次执行（手工 / 定时 / 外部程序遗留）的时间、语句、结果，可按配置和来源筛选。每条记录都有可展开的**运行输出**，格式与原程序每张表的运行日志一致，带毫秒时间戳和 `INFO` / `WARN` / `ERROR` 级别：

- 开头一行是本次参数（`env-table`、字段、类型、周期、跨度、保留数、预创建数、时区与偏移、方言、来源）；
- 中间是步骤：表是否存在、分区状态与现有分区数、"准备新增分区: …"、"准备删除过期分区: …"、跳过原因（`nothing to add` / `retain<=0` / 保护窗口 / `partman_auto_drop=false` / 未分区不初始化 / Doris 读不到上界的分区已排除）；
- 每条语句有"执行 SQL: …"和"执行成功 / 执行失败: …"，失败后其余语句标为未执行；
- 之后是**推送结果**：每个通道一行（地址脱敏）、HTTP 状态与平台返回，推送失败只出现一行 WARN，不影响维护结果；
- 结尾一行 `=== reconcile done ===`。

面板里可以按**级别**过滤、**搜索**、**复制**当前显示的内容或**下载 .log**。输出超过 200 行时保留开头和结尾，中间显示"…已截断 N 行"。预览弹窗里的"检查过程"是同样的输出（预检模式，语句标 `[DRY-RUN]`，不执行）。

定时维护每一轮还会产生一条**轮摘要**：列出这一轮每个配置的结果——已维护、已跳过（近期日志保护窗口 / `partman_auto_drop=false` 只续建不删除 / 暂不支持的实例类型 / 被另一个进程锁住 / 未分区不初始化）或失败，以及对应的原因。

## 定时自动维护

默认**关闭**，由管理员开启（`dbt_sql_config.partman_auto_run`）；自动执行默认只**续建**分区，不删除（`partman_auto_drop=true` 才删）；REORGANIZE 和未分区表的初始化**永不自动执行**，只记日志提示人工处理。同一配置最近一小段时间内（`min(间隔/2, 30 分钟)`）已经有任何来源写过维护日志，本轮会跳过——多个实例或手动与定时仍可能撞车，这个保护窗口依旧有用。

## 推送设置

列表右上角「推送设置」（需要 `partman.edit`）管理推送通道（`dbt_partman_webhook`）：

| 类型 | 允许的主机（https） | 成功判定 | 说明 |
|---|---|---|---|
| Slack | `hooks.slack.com` | HTTP 200 且正文 `ok` | |
| 企业微信 | `qyapi.weixin.qq.com` | `errcode = 0` | @ 手机号 / userid / `@all` |
| 飞书 | `open.feishu.cn`、`open.larksuite.com` | `code = 0` | 填了**加签密钥**时加签 |
| 钉钉 | `oapi.dingtalk.com` | `errcode = 0` | 填了**加签密钥**时加签 |

- 每个通道可设：地址、**加签密钥**（钉钉 / 飞书）、**自定义关键词**（企业微信 / 钉钉 / 飞书，拼进消息）、@ 时机（总是 / 仅失败时 / 从不）、@ 对象、启停；
- 地址只显示脱敏形式（密钥段是 `****`），**加签密钥只显示"已设置"**，编辑时留空 = 不改，勾选"清空"才会清掉；审计里也没有完整地址和密钥；
- 地址必须是 https 且主机在上表内（本机回环地址仅为联调保留），重复地址会被拒绝；
- 「测试发送」会立刻发一条固定的测试消息（不依赖维护事件，也不受推送时机影响），逐通道显示结果；单个通道测试不要求已启用；
- **什么时候推送**：一次维护（手动 / 定时）**执行了语句或失败**之后推送，没有变更不推；定时一轮里"计划失败 / 连不上目标库"也算失败；定时跳过的情形和手动执行被拒绝（权限、确认不一致、前置检查失败）不推。全局时机由 `dbt_sql_config.partman_notify_on` 决定：`always`（默认）/ `on_failure` / `never`；
- **推送失败绝不影响维护结果**，只记服务日志（地址里的 token 脱敏），在后台进行，不拖慢执行。
