# 性能工单

菜单：性能工单。系统从慢查询等来源**自动建单**，按影响程度定级 P0–P3，指派给负责人，按 SLA 跟踪、超时逐级升级催办，直到修复并验证关闭。研发处理，DBA 验证与兜底。

## 工单从哪来

采集器按"实例 + 库 + SQL 指纹"聚合慢 SQL（平台慢日志、pt-query-digest、performance_schema、Doris 审计表、自定义采集 SQL 等）；超过阈值就建单，并：

- **诊断问题类型**：全表扫描无索引、缺少索引、前模糊 LIKE、列上套函数、深分页、`ORDER BY RAND()`、IN 过长、隐式转换、filesort、相关子查询等；
- **评估级别**：按日均浪费的数据库时间、占比、平均耗时与日均次数判定 P0 → P3，任一条件命中即定级；
- **路由负责人**：按路由规则找团队和负责人；"纯缺少索引"类问题分给 DBA，其余分给研发；
- **去重**：同一指纹只有一张工单，影响扩大时自动升级级别；关闭后同一 SQL 再次出现会**自动重开**（被"误报关闭"的除外）。

DBA 也可以**手工建单**（`perf.create`），或从慢日志页面对某条慢 SQL 生成工单。手工建单要填实例（只列你能看到的 MySQL 系实例）和 SQL（真实慢 SQL，创建时自动诊断；只支持单条 SELECT / UPDATE / DELETE / WITH，不能带分号）；库名、级别（留空 = 自动评估，没有指标时默认 P2）、负责人（留空 = 按路由规则）和备注可选。同一实例 + 库 + SQL 指纹已有工单时不会重复创建。

## 状态与 SLA

| 状态 | 含义 | SLA 计时 |
|---|---|---|
| 待分派 | 还没有负责人 | 计时 |
| 待受理 | 已指派，等负责人受理 | 计时 |
| 处理中 | 已受理，承诺了完成日 | 计时 |
| 待验证 | 研发标记已修复，等 DBA 验证 | **暂停** |
| 豁免审批中 | 研发申请豁免，等 DBA 审批 | **暂停** |
| 已关闭 | 验证通过 / 豁免通过 / 误报 / 长期未复现 | — |

**SLA 只在待分派 / 待受理 / 处理中计时。** 默认策略如下（可在 SLA 策略页调整；受理 / 解决 / 超时升级总监 / 催办间隔 / 最多延期次数）。新的策略只对之后建立（或重算时限）的工单生效，已有工单的截止时间不变：

| 级别 | 受理时限 | 解决时限 | 升级总监 | 催办间隔 | 最多延期 |
|---|---|---|---|---|---|
| P0 | 4 小时 | 48 小时 | 24 小时 | 4 小时 | 0 次 |
| P1 | 24 小时 | 7 天 | 3 天 | 24 小时 | 1 次 |
| P2 | 72 小时 | 14 天 | 7 天 | 48 小时 | 1 次 |
| P3 | 72 小时 | 30 天 | 14 天 | 72 小时 | 2 次 |

超时升级：未受理超时 → **L1** 催办负责人（同级别按催办间隔重复）；超解决时限 → **L2**（加团队 TL 和跟进 DBA）；再超过设定时间 → **L3**（加总监，走全局渠道）；处理中距截止不足 20%（且至少 4 小时）会提醒一次。P0 不受免打扰限制，P2 / P3 周末静默，每天 22:00–9:00 静默（静默期间仍记录"曾超时"）。

## 工单列表

页顶 6 张统计卡：

| 统计卡 | 含义 |
|---|---|
| 我的待办 | 指派给你且在计时的工单，以及你作为跟进 DBA 要验证 / 审批的工单；下方标出其中几张已超时 |
| 已超时 | SLA 计时中且已过解决截止 |
| 待分派 | 还没有负责人 |
| 待验证 | 等待 DBA 验证 |
| 本周新增 | 近 7 天自动 / 手工建单 |
| 本周完成 | 近 7 天关闭（含豁免） |

页签（带数量角标）：全部 / 我的待办 / 待分派 / 待受理 / 处理中 / 待验证 / 审批中（待审批延期或豁免）/ 已超时 / 已关闭；可按可见范围（全部团队 / 我的团队与我负责的）、级别、团队、状态、来源、关键字（指纹 / 库 / 表 / #编号）筛选；默认按 SLA 剩余时间升序（已暂停 / 已关闭的排后），点列头可按级别 / 日均浪费 DB 时间 / 平均耗时 / SLA 排序；超时的工单整行高亮。侧栏角标是你的待办数（橙色表示有已超时的）。

可见范围：DBA（超级用户或持有 `perfcfg` 管理权限）看全部；其他人看到所在资源组的工单和指派给自己的。

## 各角色能做什么

### 研发（负责人 / 团队成员，`perf.handle`、`perf.comment`）

| 动作 | 允许的状态 | 校验 |
|---|---|---|
| 受理 | 待分派、待受理 | 必填承诺完成日：不早于今天，不晚于 SLA 解决截止日（已超时的工单最晚只能选今天）；备注可不填；没有负责人的工单受理后你成为负责人 |
| 标记修复 | 待受理、处理中 | 必填修复方案（至少 5 个字；可同时填关联的 SQL 上线工单号，详情页给出跳转链接）；记录修复前的耗时基线，进入待验证，SLA 暂停计时 |
| 申请延期 | 计时中的状态 | 次数不超过该级别上限（详情页显示已用 / 上限）；新日期晚于当前截止日且不超过一年；必填理由（≤ 1000 字，DBA 审批时可见）；不能已有待审批申请 |
| 申请豁免 | 计时中的状态 | 理由 10–1000 字；提交后进入豁免审批中，SLA 暂停计时；不能同时有待审批的延期 |
| 评论 | 任意（含已关闭） | 必填内容；会通知负责人与跟进 DBA（不含评论人本人） |

### DBA（`perf.assign`、`perf.verify`、`perf.approve`、`perf.adjust`、`perf.reopen`、`perf.close_dup`）

| 动作 | 说明 |
|---|---|
| 指派 | 改负责人 / 团队；负责人只能选启用状态的用户；待分派 → 待受理 |
| 验证通过 / 不通过 | 通过 → 已关闭；验证弹窗里给出修复前后的耗时对比；不通过必须写原因，工单回到处理中并累计重开次数，SLA 继续计时 |
| 同意 / 驳回延期 | 同意：解决截止改为该日 23:59:59，已延期次数 +1；驳回必须写原因，清除申请。**不能审批自己提交的申请** |
| 同意 / 驳回豁免 | 同意 → 已关闭（豁免）；驳回必须写原因，回到处理中 / 待受理 / 待分派。**不能审批自己提交的申请** |
| 调级 | 级别必须有变化；调级后**锁定**，不再自动调整（详情页的级别旁会标出）；计时中的工单 SLA 按新级别重算（调高从建单时起算，调低从现在起算） |
| 切换处理方 | 改为 DBA 处理（负责人 = 跟进 DBA，没有则为你）或改回研发（按路由重新找负责人，找不到则回到待分派） |
| 误报关闭（高危） | 必须写原因；填完后还有**第二步确认**（说明之后同一 SQL 再出现也不会重开，并要求键入工单号 `#编号`） |
| 重开 / 重新诊断 | 重开回到待受理 / 待分派并累计次数，未锁定级别的重新评估级别，SLA 时限从现在重新计算；重新诊断可粘贴真实 SQL 替换样例（只支持单条 SELECT / UPDATE / DELETE / WITH，不能带分号），处理方不会自动改变 |

所有按钮由"权限 + 当前状态"共同决定：不是负责人或团队成员时处理类按钮置灰（悬停可看原因），非法流转会被服务端拒绝。工单被别人同时更新时会提示"刚刚被他人更新，请刷新"，不会覆盖对方的操作。

### 自动流转

修复后观察几天（默认 3 天）自动验证；长期未复现的自动关闭（默认 14 天）；关闭后复现自动重开；每周一发送周报（全局渠道一条、各团队一条并 @ 待处理工单的负责人）。

## 工单详情

页顶是 SLA 概况：受理 / 解决截止、倒计时、升级级别 L1–L3 与已催办 / 升级次数；已暂停或已关闭的工单显示暂停原因与时限。下面依次是：

- 指标：日均浪费 DB 时间、占该实例慢 SQL 总耗时、日均执行次数、平均耗时 / 最大耗时、平均扫描行、平均返回行；
- 近 30 天平均耗时趋势（标记修复后回落）、SQL 示例与指纹、执行计划（EXPLAIN）；
- 诊断结论与优化建议，以及建议 DDL（需 DBA 评估后通过「SQL 上线」执行）；
- 处理信息（实例、库表、来源、处理方、团队、负责人、跟进 DBA、各时间点、修复前基线与修复后效果、延期 / 重开次数、级别）；
- 处理时间线：每次变更的动作、内容与操作人；
- 可用的操作按钮（研发一行、DBA 一行）；有待审批的延期 / 豁免申请时，页顶显示申请人、理由与期望日期。

## 团队排行榜

菜单：性能工单 › 团队排行榜。按团队统计**健康度**：未关闭工单数、超时数、平均修复天数、近 12 周的新增 / 完成趋势、未关闭问题类型分布；可按时间范围（近 7 / 30 / 90 天）和处理方（研发处理的问题 / DBA 处理的问题 / 全部）过滤。

- **统计卡**：未关闭工单、已超时、期间新增、期间优化完成、未关闭问题每天浪费的 DB 时间、期间优化每天节省的 DB 时间；
- **健康度**：每个团队一张评分卡（健康分、超时、未受理、未关闭、按时率）和一张排名表（含 P0 / P1 未关闭、期间新增 / 完成、平均修复天数、每天浪费 DB 时间），按健康分从低到高排序，点击行回到工单列表；
- **健康分** = 100 − 超时数 × 15 − 未受理数 × 5 − 日均浪费 DB 小时数 × 10 − (100 − 按时率) / 5，限制在 0–100；
- **趋势与分布**：近 12 周新增 vs 优化完成按周（周一起算）统计；未关闭问题类型按每日浪费 DB 时间（分钟）统计；
- **周报**：每周一 09:35 向全局渠道与各团队群推送同一份统计（本页只展示，不负责推送）；「团队配置」里“参与排行与周报”为否的团队不出现在这里。

## 配置（需要 `perfcfg.view`，修改另需对应码）

| 页面 | 内容 | 权限 |
|---|---|---|
| 采集配置 | 每个实例的采集来源、采集窗口、自定义采集 SQL（保存与每次执行前校验只读：必须单条 SELECT / WITH / SHOW，禁止 `INTO OUTFILE`、`sleep` 等）、**试采集**（只预览最近一个窗口，不建单不写游标）、批量生成默认停用的配置 | `perfcfg.collect` |
| 团队配置 | 团队、负责人、总监、路由规则（按库 / 实例 / 关键字分派） | `perfcfg.team` |
| SLA 策略 | 四个级别的受理 / 解决 / 升级时限、催办间隔、延期上限；保存前用**差异预览**列出变化的项，没有变化提示“没有变更”；“重置”按钮丢弃页面上未保存的修改 | `perfcfg.sla`（高危） |

只有“查看配置”权限的人可以看到这些页面，修改按钮是灰的，页顶提示配置为只读。

### 采集配置

每个实例一条采集配置；慢 SQL 按“实例 + 库 + SQL 指纹”聚合建单。

- **后台任务与采集窗口**：页顶显示采集 / SLA 巡检 / 每日验证 / 周报四个后台任务是否开启（系统配置 `perf.jobs`），以及采集窗口（分钟，系统配置 `perf.collect_window_minutes`，修改窗口需要 `perfcfg.collect`，范围 10–1440）。启用的配置距上次窗口结束满一个窗口才会采集，最多 3 个并行；采集从上次窗口结束处接续，长时间停机后一次最多补 24 个窗口；
- **阈值与排除**：平均耗时阈值（ms，大于 0）与窗口总耗时阈值（s），超过任一阈值就建单（总耗时阈值让高频小慢 SQL 也能建单）；排除规则（正则，匹配 SQL 文本则忽略）、排除库（逗号分隔）；默认归属团队为空时取实例的第一个资源组；
- **试采集**用表单里（可以是尚未保存的）配置采集最近一个窗口，按总耗时排序列出前 50 个指纹，并标注“将建单 / 未达阈值 / 已排除 / 已有工单”；只预览，不建单、不写游标、不改采集状态；
- **批量生成默认配置**会为还没有配置的 MySQL 系实例生成默认停用的配置，检查无误后再逐个启用；
- 保存时校验“采集方式 × 实例类型”是否匹配：pt-query-digest 只适用自建 MySQL，Doris audit_log 只适用 SelectDB / Doris，AnalyticDB 只能用自定义采集 SQL，PolarDB-X 的两种方式只适用 PolarDB-X；走 SSH 隧道的实例暂不支持。

采集方式共 8 种：

| 采集方式 | 来源 |
|---|---|
| 平台慢日志 | 元库 `dbt_slow_logs` 表 |
| pt-query-digest | pt-query-digest 写入的慢日志表 `dbt_mysql_slow_query_review_history` |
| performance_schema | `performance_schema` 的 digest 汇总 |
| mysql.slow_log | `mysql.slow_log` 表（需 `log_output=TABLE`） |
| Doris audit_log | SelectDB / Doris 审计表 |
| PolarDB-X statements_summary | PolarDB-X `statements_summary` |
| PolarDB-X SHOW FULL SLOW | PolarDB-X `SHOW FULL SLOW` |
| 自定义 SQL | 自定义采集 SQL |

自定义采集 SQL 在保存和每次执行前都要通过**只读校验**：只允许单条 `SELECT` / `WITH` / `SHOW`（≤ 4000 字符，含注释里夹带的第二条语句同样拦截）；不允许 `INTO OUTFILE` / `INTO DUMPFILE`、`sleep` / `benchmark` / `load_file` / `get_lock` 等函数、写操作关键字，以及 `FOR UPDATE` / `LOCK IN SHARE MODE`。占位符 `%(start)s` / `%(end)s` 是窗口起止时间（没有同时使用时给出警告，每个窗口都会重复扫描全量数据）；需要返回 `db_name, sql_text, exec_count, total_ms, max_ms, rows_examined, rows_sent, last_seen`。

### 团队配置与路由

团队就是资源组，这里只补充性能工单需要的信息：默认接口人（库负责人找不到时的兜底）、团队 TL（L2 升级，可多选）、总监（L3 升级，可多选）、是否参与排行与周报；群通知沿用「通知渠道」里资源组的配置。

**路由规则**按“实例（空 = 全部）+ 库名正则 + 表名正则 → 团队 / 负责人”分派：从上到下顺序匹配，首个命中的规则生效（可用 ↑ ↓ 调整顺序）；库名 / 表名为正则，整体匹配，表名留空表示不限；负责人留空表示团队默认接口人；删除规则不影响已建的工单。分派顺序：路由规则 → 实例「数据库管理」里的库负责人 → 团队默认接口人；处理方为 DBA 的问题改派给 DBA 值班（系统配置 `perf.dba_users`，轮询）。**路由测试**输入实例 / 库 / 表，显示命中第几条规则、指派给谁；没有命中任何规则时回退到实例资源组的默认接口人，仍没有则工单停在“待分派”。

### SLA 策略与升级通知

- **各级别时限**：受理时限、解决时限、超时后升级总监、重复催办间隔（小时）和最多延期次数，都是非负整数；解决时限不小于受理时限，受理时限与催办间隔至少 1 小时；
- **升级规则与通知对象**：L1 / L2 / L3 各自通知谁（负责人、团队 TL、跟进 DBA、总监、全局渠道），与时限一起保存；每一级都必须通知负责人。默认：L1（未受理超过受理时限）通知负责人；L2（超过解决时限）再加团队 TL 与跟进 DBA；L3（超过解决时限 + 升级总监时限）再加总监与全局渠道；
- **级别评估规则**（系统配置 `perf.severity_rules`，页面只读展示）：日均浪费 DB 时间、占实例慢 SQL 总耗时的比例、平均耗时 **且** 日均次数，任一条件满足即命中；占比条件还要求绝对量不低于该级别日均浪费的 30%；其余不命中的为 P3。免打扰时段、验证观察天数（3）、改善比例（50%）、未复现自动关闭天数（14）、回归重开最低影响、静默模式等运行参数在系统配置里，不在本页。
