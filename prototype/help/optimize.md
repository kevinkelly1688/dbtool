# SQL 分析与优化工具

涉及两个页面：**SQL 分析**（SQL 审核 › SQL 分析，批量文件分析）和**优化工具**（SQL 优化 › 优化工具，单条 SQL 即时分析）。两者都是**只读**的，不会修改目标库的数据或结构。

## SQL 分析（批量）

适合在上线前对一批 SQL 做体检，例如一个迭代里的全部 Mapper 文件。

1. 打开页面，选择实例（可选；不选只做静态分析）和库；
2. 上传文件：支持 `.sql` 文本、**MyBatis3 Mapper XML**、**MySQL 慢日志文本**，单文件 ≤ 5 MB、最多 1000 条、单条 ≤ 60 KB，内容只在内存里处理，不落盘；
3. 点「开始分析」，后台逐条分析，页面显示进度，可随时取消；结果只保留约 30 分钟（服务重启即丢失），到期后需重新分析；每人最多同时有 2 个进行中的任务；
4. 查看汇总（按语句类型、最高建议级别、SQL 指纹、涉及的表统计）和逐条详情。

每条 SQL 的分析内容：**SQL 指纹**（常量替换为 `?`，同类语句得到同一个 ID）、语句类型与涉及的表、内置规则建议；选了实例时还有表结构 / 统计信息、执行计划解读和索引建议；配置了 SOAR 时附上 SOAR 报告。

- Mapper XML 会展开 `<if>`、`<where>`、`<foreach>`、`<include>` 等动态标签，`#{}` 还原为 `?`；XML 解析失败按普通 SQL 处理；
- 慢日志文本会保留每条的耗时、扫描行数等统计，汇总里按指纹累加总耗时；
- 没配置 SOAR 不是错误，只输出内置规则；所选实例连不上则降级为静态分析并提示。

权限：`sqlanalyze.view` 查看报告，`sqlanalyze.run` 上传并开始分析。任务只有创建者本人和超级用户能查看。

## 优化工具（单条）

粘贴一条 SQL（SELECT / UPDATE / DELETE / INSERT…SELECT），选实例和库，按需点击不同的工具：

| 工具 | 说明 | 权限码 |
|---|---|---|
| 执行计划 | 对目标实例执行 `EXPLAIN`（含 JSON 格式），**不执行语句本身**，并解读全表扫描、filesort、临时表、join buffer 等 | `optimize.explain` |
| 内置建议 | 词法级规则，不连库也能用（规则见下） | `optimize.explain` |
| SQL 美化 | 格式化 SQL（关键字大写、子句换行、SELECT 列一行一个），保持各引擎方言；纯文本处理，不连接目标库，可一键替换编辑器内容 | `optimize.explain` |
| SQLTuning | 对 SELECT 采集表结构、统计、索引、系统参数，并做 PROFILE | `optimize.tuning` |
| SOAR | 小米开源的 SQL 优化与改写工具 | `optimize.soar` |

外部工具 SOAR 是外部程序，程序路径与 SOAR 的测试环境 DSN（不能指向线上库）由管理员在系统配置（`dbt_sql_config`）里设置；没配置时只提示"未配置"并说明缺哪一项，可一键改用内置建议，不影响其他功能。MySQL / PolarDB 可用全部方式；SelectDB / Doris / ADB 只提供执行计划；其他类型的实例不会出现在下拉里。

右侧「选项」里，SQLTuning 可勾选要显示的内容：系统参数、执行计划、相关对象（表、索引）统计信息、PROFILE 跟踪（会真实执行该查询，耗时分布条按平方根缩放）。

### 内置规则举例

每条建议带级别（高 / 中 / 低 / 提示）、规则编号、说明和改法，综合评分 = 100 − 20×高 − 10×中 − 3×低。规则编号里 R 系列是静态规则（不连库）、S 系列需要表结构（如隐式类型转换）、P 系列来自执行计划解读。规则是词法级的，结论只是建议，可能误报 / 漏报，以 `EXPLAIN` 为准。

| 规则 | 级别 | 内容 |
|---|---|---|
| UPDATE / DELETE 没有 WHERE | 高 | 会全表更新或删除 |
| ORDER BY RAND() | 高 | 全表排序，数据量大时极慢 |
| JOIN 缺 ON / USING | 高 | 产生笛卡尔积 |
| 深分页 | 中 / 高 | 偏移量 ≥ 1 万为中，≥ 10 万为高，建议改用游标 / 延迟关联 |
| 列上套函数 | 中 | `date(col)=...` 会使索引失效 |
| LIKE '%xxx' 前导通配符 | 中 | 无法使用索引 |
| 字符串列与数字比较 | 中 | 隐式类型转换导致索引失效 |
| IN 列表 ≥ 200 项 | 中 | 建议改临时表 JOIN |
| SELECT * | 低 | 增加网络与回表开销 |
| UNION 未指定 ALL | 低 | 多余的去重排序 |

选了实例后还会基于真实表结构推导索引：按"等值列在前、范围列在后"给出 `ALTER TABLE ... ADD INDEX ...` 草案，已有索引能覆盖时不重复建议；执行计划里的全表扫描、`Using filesort`、`Using temporary`、`DEPENDENT SUBQUERY` 等也会被逐项解读。每条索引建议附建议前后的执行计划预估对比（"后"是按建议索引和表统计信息推导的估算，不是真实执行计划）和相关表的现有索引；新索引以现有索引为前缀时，提示可评估删除现有索引。索引草案请先在测试环境验证，再通过[SQL 上线](#help/sqlworkflow)在低峰期执行，不要直接在线上库手工建索引。

```sql
-- 优化前：列上套函数，无法走 created_at 索引
SELECT id, order_no FROM orders WHERE DATE(created_at) = '2026-10-07';
-- 优化后：改为范围条件
SELECT id, order_no FROM orders
WHERE created_at >= '2026-10-07 00:00:00' AND created_at < '2026-10-08 00:00:00';
```

> SQLTuning 的 PROFILE 会**真实执行**该 SELECT，因此只接受 SELECT，执行前会设置只读事务和执行超时（60 秒），超时自动 KILL。

## 语句校验

服务端不信任前端传来的语句：去注释后必须恰好一条语句；只允许 SELECT / UPDATE / DELETE / INSERT…SELECT（及 WITH 开头）；用户写的 `EXPLAIN` 前缀会被去掉；`EXPLAIN ANALYZE`（会真执行）、`INTO OUTFILE`、`sleep()` / `benchmark()` / `load_file()` 一律拒绝。语句里带库名的表必须落在你可见的库内，防止借 EXPLAIN 探测被屏蔽的库。
