## PolarDB-X / SelectDB / ADB / Doris 的建表工单改走原生方式；定时时间可多次修改（1.93）

- **建表工单**：目标实例是 PolarDB-X、SelectDB、Doris、ADB，且工单里的语句全部是 `CREATE [TEMPORARY|EXTERNAL] TABLE` 时，检查不再走 goInception（它认不全这些库的建表语法），只做**语法检查**（`internal/sqlflow/check_createtable.go`：括号 / 引号成对、表名、列定义不为空且有名字和类型、`LIKE` / `AS SELECT` 写法；不连目标实例，不校验库表是否存在，各家扩展的表选项原样放过），检查来源 `create_table`；执行只有**原生方式**（逐条直连，不备份、无自动回滚），即使配置了 goInception 或开启了“强制使用 goInception”也一样；提交时记的 / 定时记的执行方式是 goInception 也会按原生执行；仍走审批，不会自动通过。混有 ALTER / INSERT 等别的语句的工单、其它类型的实例都不受影响。
- **定时执行可多次修改**：服务端本来就允许对“定时执行”中的工单重新设定时间（覆盖旧计划）；这次让它在页面上看得见——详情页执行卡片里带出当前定时时间，按钮改叫「修改定时时间」。
- 提示 / 错误信息补了英文译文；提交页检查来源提示新增“已做语法检查（原生方式执行）”。
- 测试：`check_createtable_test.go`（范围判断、语法检查的通过 / 报错用例）、`createtable_flow_test.go`（五种类型检查 + 原生执行且不碰 goInception、选 goInception 被拒、强制 goInception 时照样执行、混语句 / MySQL 不受影响、定时多次修改并到点原生执行）。

## SelectDB / Doris 的工单原生执行不再被 read_only 预检误拦（1.89）

- **问题**：SelectDB 实例的 SQL 工单用“原生执行”时报“实例read_only=1，禁止执行变更语句!”，通知里是“工单执行异常”。这个预检是执行前读 `@@global.read_only` / `@@global.super_read_only`，任何一个非 0 就拒绝，本意是防止在只读从库上执行变更；但 SelectDB 为了兼容 MySQL 协议把这两个变量固定报成 1（实测两个 SelectDB 实例都返回 1、1），并不表示真的只读，所以原生执行 SelectDB 的变更工单必然被拦，与执行账号有没有权限无关。
- **修复**：`internal/sqlflow/run.go` 的 `execNative` 对 `selectdb` / `doris` 跳过这一步预检；其它类型（MySQL / PolarDB 等）行为不变，`read_only=1` 时仍然拒绝。SelectDB 真不能写时，由数据库在执行语句时报错。
- **测试**：新增 `TestExecuteSelectDBIgnoresReadOnlyFlag`（selectdb、doris 在 `read_only=1` 时仍执行；去掉修复时这条用例会失败），原来的 `TestExecuteReadOnlyInstanceRefused`（MySQL 拒绝）保持通过。
- **没有验证的**：没有在真实 SelectDB 上执行过变更工单；Doris 只是按同类处理，没有实测它的变量值。goInception 执行方式不受这个预检影响（本来就不走它）。

## 接口响应开启 gzip 压缩（1.89）

- **问题**：在线查询的结果里有大文本列时，一次返回的 JSON 可以有几 MB（例如某张日志表前 100 行的 `ChangedTablesLog` 合计约 1.4 MB，单行最大 354 KB），数据库执行只要二三十毫秒，但原样经过公网 / 隧道 / 反向代理发给浏览器要等十几秒甚至更久，页面一直停在“正在执行…”。
- **改动**：新增 `internal/server/gzip.go`，对 `/api/` 下的接口响应启用 gzip。只压缩同时满足这些条件的：请求头 `Accept-Encoding` 接受 gzip（浏览器都会带；没带的客户端，如 MCP 的 Node `https`，拿到的还是原文）、方法不是 HEAD、状态 2xx（不含 204）、`Content-Type` 是 `application/json`、没有 `Content-Encoding`、不是附件下载、首次写出不小于 1 KiB。页面 HTML、静态文件、导出下载、错误响应、小响应都不压缩。响应头带 `Content-Encoding: gzip` 和 `Vary: Accept-Encoding`，压缩级别用最快档，CPU 开销很小。
- **验证**：新增 `gzip_test.go`（压缩与解压后逐字节一致、各种不压缩的情形、`Accept-Encoding` 解析）；在演示服务上用真实登录和真实接口核对，压缩前后逐字节相同，英文请求的错误响应（经过语言翻译中间件）正常，浏览器里跑查询正常。没有在你们的线上环境（Cloudflare + 隧道）验证过实际提速；JSON 文本一般能压到原来的十分之一左右。
- **没有解决的**：MySQL 系实例的在线查询仍然没有单元格 / 总量字节上限（SQL Server、ClickHouse、Oracle、达梦有），超大单元格不会被截断；压缩只减少传输量，浏览器渲染几百 KB 的单元格仍有开销。要不要加上限另议。
- 如果前面有自己的 nginx：默认不需要改动；它会原样转发已压缩的响应。若 nginx 开了 `gzip on`，它不会对已带 `Content-Encoding` 的响应再压一次。

## SQL Server 在线查询 / 导出：加固锁提示（1.86）

- **排查结论**：在线查询和数据导出读 SQL Server 的表和视图，每次查询前都会 `SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED`（等同给所有表加 `NOLOCK`），不加共享锁、不被写事务阻塞，也不阻塞写入；行数上限是改写成 `TOP n` 发给服务端的；每次请求新建连接、用完即关，会话设置不会带到别处；超时（默认 60 秒）到就取消语句。表和视图走同一条路径。
- **之前的缺口**：只读检查只禁了 `UPDLOCK` / `XLOCK` / `TABLOCKX` / `HOLDLOCK` / `SERIALIZABLE`，用户仍可以在语句里写 `WITH (TABLOCK)`（整表共享锁）、`REPEATABLEREAD`（持有读锁到语句结束）阻塞写入，或写 `READCOMMITTED` / `READCOMMITTEDLOCK` 覆盖会话的 `READ UNCOMMITTED`、改回读时加锁（查询反过来会被写事务堵住）。这是按 SQL Server 文档判断的，没有在真实 SQL Server 上验证。
- **现在**：上面四个也拒绝（提示“只读查询里不允许出现 xxx”），写在 `WITH (…)`、旧写法 `(…)` 或 `OPTION (TABLE HINT …)` 里都拦；`NOLOCK` / `READUNCOMMITTED` / `INDEX` / `FORCESEEK` 等不受影响；字符串、注释、`[标识符]` 里的同名单词和名字里只是包含这些词的列不会被误拦。在线查询和导出工单共用这个检查，一起生效。改动在 `internal/tsql/readonly.go`，测试在 `readonly_batch_test.go`（新增 8 条拒绝、1 组放行）。
- **没法处理的**：① 视图自己的定义里如果写了锁提示，会覆盖会话设置，只能改视图；② `READ UNCOMMITTED` 仍然持有架构稳定锁（Sch-S），一条跑得久的查询会让同一张表上的 `ALTER` / 重建索引排队，排队的 DDL 又会堵住后面的读写，影响最长是一个查询超时（默认 60 秒）；要缩小窗口可以调小查询超时，或避开 DDL 工单的执行时间。

## 权限体系改成只认按钮（第一步：一次性迁移 + 权限组页面精简）（1.79）

- **背景**：早期权限分两套——“权限码”（`menu_*`、`sql_submit`、`sql_review` 等，存在 `dbt_auth_permission` 等表）和“按钮”（`dbt_group_perm`），还有兼容 / 严格两种生效方式。菜单和按钮改名后，两套名字对不上，管理员分不清该勾哪一项。计划分三个版本改成只认按钮：1.79 迁移数据并精简权限组页面；1.80 把服务端的权限判断点逐个换成按钮校验；1.81 删除原权限码相关的代码、字段和表读写。
- **现在（1.79）**：
  - **一次性迁移**：新增 `dbt-admin perm migrate`。把权限组、用户**单独**持有的原权限码，按原来兼容模式的规则展开成按钮授权（持有某个权限码 = 得到它放行的全部按钮，含比权限码更细的按钮），再把生效方式切到严格。迁移前后每个用户能用的按钮完全相同（用 2026-10-23 生产库的权限组快照做了测试：Default / RD / DBA / TL / DE 五个组和 ives 的单独授权，迁移前后每个人的按钮集合逐个相等）。只增不减、可重复执行；没有对应按钮的早期遗留码（`menu_dashboard`、`menu_document`、`menu_instance`、`menu_sqlbatchworkflow`、`menu_sqlcheck`、`menu_sqloptimize`、`menu_sqlquery`、`menu_tools`、`menu_openapi`、`menu_schemasync`、`menu_system`、`query_download`、`optimize_sqladvisor`、`add_perfissue` / `change_perfissue` / `view_perfissue`）丢弃，对任何人都没有影响。默认只演练，`--apply` 才写，并先把“逐条撤销这次迁移”的 SQL 存成文件（只删这次新增的行）；用户已有的单独授权 / 禁止一律不动；写在一个事务里，失败整体回滚，写一条系统审计。
  - **升级自动执行**：`install.sh install / upgrade` 在**健康检查通过之后**执行 `dbt-admin perm migrate --apply --yes`（撤销脚本存在配置备份目录里）；新版本没起来而自动回滚时不执行，库里的权限保持迁移前的样子；迁移失败只警告，升级照常完成，权限仍按原权限码放行，修好后手工执行同一条命令。
  - **新增按钮 `archive.review`（审批数据归档申请）**：原来的 `archive_review` 没有对应按钮（DBA、TL 持有），迁移会把它迁成这个按钮。
  - **基础按钮**：没有任何限制的三个按钮——终止自己的工单（`sqlworkflow.cancel_own`）、查看 / 下载回滚语句（`sqlworkflow.rollback`）、申请 / 撤回查询权限（`qpriv.apply`）——严格模式下也对所有登录用户开放（原来严格模式要显式授予），不进权限树；对个别用户的“单独禁用”仍然优先。
  - **权限组页面只剩按钮这一套**：去掉原权限码矩阵（“基本信息与权限码”页签改叫“基本信息”，只有名称 / 说明、引用情况）、“兼容 / 严格”单选、切严格前的影响预检、“按原权限码生成…”、“按用户查看有效权限”里旧权限码的单独授权表。页面顶部只剩“无权限按钮的显示方式”（隐藏 / 置灰）；没迁移过时顶部有黄色提示。“复制该组”现在把来源组的按钮授权一并复制过去。
  - **权限树**：只列可授予的按钮；“仅超级用户”的按钮和基础按钮不再列成灰色 / 带“原：…”标签的复选框，改成各页面下方的一行说明；整页都是仅超级用户的页面（如“用户”）只显示页面名和“仅超管”；“默认仅超级用户”但可授予的按钮带提示。树里不再出现原权限码，搜索也不再匹配原权限码。
  - `PUT /api/v1/settings/auth-groups/:id` 不带 `perm_codes` 时不碰原权限码（带空数组才是清空）；旧权限码相关的接口暂时保留，1.81 删除。
- **行为变化**：迁移之后权限只按按钮判断，原权限码不再生效；新建的权限组只能在“按钮权限”页签里授权；其余页面和接口的行为不变（判断点仍走“按钮折算出的权限码”，1.80 才逐个换成按钮）。
- **回滚**：旧权限码相关的表、行都没有改动，回滚到 1.78 照常工作，权限与迁移前一致；迁移之后在新版本里改的权限组按钮，旧版本只当“追加”看待（不会收回旧权限码给的权限）。需要完全撤销迁移时执行撤销脚本（生效方式回到兼容）。
- **没有改**：各功能章节里的“原权限码”列（帮助文档）、判断点（1.80）、代码和表的清理（1.81）；资源组、库表授权、审批流配置结构。
- **升级动作**：建议升级前先在新包里预览：解压新包后用生产的连接串执行 `./dbt-admin perm migrate`（不加 `--apply`，只读），核对每个权限组新增的按钮和丢弃的权限码，再升级。
- **文档**：`help/btnperm.md` 重写（权限只有按钮这一套 + 从原权限码迁移）、`help/permcodes.md`（去掉原权限码列、加 `archive.review`）、`help/sysadmin.md`、用户手册 8.x、`admin-cli.md`（`perm migrate`）、`ops-manual.md` / `deployment.md`（升级步骤）。
- **没有验证的**：迁移引擎、命令、页面都只用单元测试、假仓库和无头 Chrome 页面测试（`internal/btnperm/migrate_test.go`、`internal/dbtadmin/permcmd_test.go`、`scripts/frontend-test/run_authgroups.mjs`、安装脚本测试新增 5 个用例）验证过；**没有在真实 MySQL 上执行过迁移的 SQL**（读取权限码、写入 `dbt_group_perm` / `dbt_user_perm` / `dbt_perm_setting`、由 `*sql.DB` 建 GORM 连接），所以务必先在生产上用不带 `--apply` 的命令预览。

## 在线查询：左侧对象栏的宽度可以用鼠标拖动调整（1.78）

## 首页“我可见的实例”卡片：按每个实例最近一次巡检统计，写清是巡检告警，点击去对应页面（1.77）

- **现象**：卡片下面写“N 个状态异常”，但实例列表里的实例都是正常的；点卡片跳到“在线查询”。三个原因：
  1. 这个数其实是“最近一次巡检有告警 / 巡检失败的实例数”，不是实例当前连得上连不上，“状态异常”容易看成实例挂了；
  2. 首页向巡检接口要 200 条报告，接口上限是 100，超过就悄悄改回 20 条，而且 20 条里同一个实例的历史报告还占名额，118 个实例只有少数几个被统计到，数字不准；
  3. 卡片链接指向在线查询，和卡片内容无关。
- **现在**：
  - 巡检接口 `GET /api/v1/inspection/reports` 新增参数 `latest=1`：每个实例只取最近一次结束（成功或失败，不含进行中、已取消）的报告，可以再叠加 `level` 筛选；带 `latest=1` 时 `limit` 上限放宽到 2000（不带仍是 100，超过回到 20）。首页用它，所以每个实例都能统计到；
  - 卡片文字改成“N 个实例有巡检告警”“N 个实例巡检失败”，两种都有时写“N 个有巡检告警，M 个巡检失败”；有实例没有巡检数据时写“已巡检的 N 个全部正常”，全部都有数据且没有问题写“巡检全部正常”，一个都没有写“尚无巡检数据”；鼠标放上去显示“按每个实例最近一次巡检统计：N / 总数 个实例有巡检数据”；
  - 点击：有告警去 `/inspection?latest=1&level=alert`，只有巡检失败去 `level=failed`，都没有就去实例列表（没有实例列表权限的退回在线查询）；
  - 巡检列表页认 URL 里的 `latest=1` 和 `level=`：级别筛选自动选中，页面上提示“仅显示每个实例最近一次巡检（成功或失败）的结果”，旁边的“查看全部报告”回到完整列表；其它筛选、翻页、批量操作都照旧。
- **行为变化**：只有首页这张卡片的统计、文字和链接，以及巡检报告接口多了 `latest` 参数；实例健康列表（最多 9 个）的小圆点改用同一份“最近一次”数据，规则不变（告警 / 失败标红）。巡检本身、报告内容、其它页面都没有变。
- **没有改**：实例健康列表底部的“另有 N 个，见 在线查询 的实例列表”链接；实例当前连通状态的判断（实例列表页仍是逐行现场检测）。
- **升级动作**：不需要。浏览器可能缓存了旧脚本，按 Ctrl+F5 刷新一次。
- **文档**：用户手册第 5 章首页一段、`help/quickstart.md` 的顶部 KPI 说明。
- **没有验证的**：只用单元测试（`inspect` 的 `latest` 筛选、SQL 语句片段）和无头 Chrome 页面测试（新增 `run_home_kpi.mjs`：各种统计结果、链接、巡检列表带参数打开）验证过；`latest` 的子查询（`r.id IN (SELECT MAX(id) … GROUP BY instance_id)`）没有在真实 MySQL 上执行过，也没有用大量历史报告看过耗时。

- **怎么配**：Webhook 填机器人的 sendMessage 地址 `https://api.telegram.org/bot<Bot Token>/sendMessage?chat_id=<Chat ID>`（Bot Token 向 @BotFather 申请，再把机器人拉进群；群 / 频道的 Chat ID 通常是 `-100…` 开头的负数，公开频道可以写 `chat_id=@频道名`；发到群里的某个话题时再加 `&message_thread_id=<话题 ID>`）。保存时检查主机必须是 `api.telegram.org`（https）、路径和 `chat_id` 的写法，不对会提示正确的写法；地址里的其它参数忽略，发送的内容由 dbtool 决定。
- **@ 的写法**：“渠道原生标识”填 Telegram 用户名（如 `dba_wang`，带不带 @ 都行，保存时去掉 @）或数字用户 ID（没设用户名的人用它，发送时写成用户链接）；@ 的对象都写在消息第一行。Telegram 没有“@所有人”，选了“所有人”的规则保存时被拒绝。用户资料里没有 Telegram 用户名 / ID，所以按平台用户（提交人 / 审批人 / 权限组成员 / 指定用户 / DBA 值班）@ 时只在正文写“@姓名”、不会真正提醒（预览里标成“文本，不会提醒”）；要提醒到人用“渠道原生标识”。
- **消息格式**：用 Telegram 的 HTML 格式发送，链接预览关闭，正文里的 `<`、`>`、`&` 会转义，不会被内容里的文字冒充成标签。没套消息模板时发纯文字（标题 + 正文）；套了模板时标题加粗、字段一行一个“名称：值”、SQL 放进代码块、链接可点。一条消息最长 4096 个字符（按显示出来的文字算，emoji 算 2 个），超出先缩短最长的 SQL / 文本块，缩不动就改发系统默认文案（同样截断，@ 那一行保留）。
- **没有加签**：Telegram 机器人没有签名校验，页面不显示“签名密钥”，服务端也不保存；Bot Token 在 Webhook 地址里，和其它机器人的 Webhook 一样加密入库、页面不回显；从钉钉 / 飞书 / Slack 改成 Telegram 时，旧的签名密钥一并清掉。
- **限制与网络**：Telegram 建议同一个群每分钟不超过 20 条，发得太快会返回 429，记在发送记录里，不重发；发送失败时页面和发送记录显示 `HTTP 状态码（api.telegram.org）：` 加 Telegram 返回的原因（如 401 Unauthorized、400 chat not found），不含 Bot Token。**服务器要能访问 `api.telegram.org` 的 443 端口，国内网络通常访问不了，需要给 dbtool 服务配置出站代理 `HTTPS_PROXY`；通知请求的超时只有 5 秒，代理要够快。**
- **其它页面**：资源组页“通知群”一列配了 Telegram 渠道才显示“Telegram ×n”；“未配置机器人”的统计把 Telegram 渠道算作机器人；消息模板页的预览多了“Telegram”。
- **没有改**：分区维护的“推送设置”是另一套推送通道，仍然只支持钉钉 / 飞书 / 企业微信 / Slack，这版没有动它。
- **升级动作**：不需要，不改表（渠道类型存在 `dbt_notify_channel.channel_type`，长度够用）。浏览器可能缓存了旧页面，按 Ctrl+F5 刷新一次。
- **没有验证的**：只用本机的假机器人测试过（发送格式、@ 列表、错误处理、页面交互），没有在真实 Telegram 群里验证过消息的显示、`@用户名` 与用户 ID 链接的提醒效果、话题，也没有验证过经代理访问；配好后先点“测试发送”到测试群看一眼。

## DBA 值班表：顶栏显示当前值班的人，平台设置里管理班次和临时调班（1.68）

- **新功能**：每个页面顶栏、时钟的左边显示当前值班的 DBA，如“● 值班 张三 08:00–19:00”（所有登录用户可见）。点开看联系方式、本班还剩多久、今日排班的 24 小时时间条与明细、下一次交班（“19:00 交班给 李四”）。管理页面：平台设置 › 值班表。
- **班次**：名称、值班人、开始 / 结束时间（24 小时制，按服务器时区；结束不晚于开始表示跨到第二天，如 19:00–00:00、22:00–06:00，开始等于结束表示 24 小时）、适用星期（默认每天；跨午夜的班属于开始那一天）、联系方式（选填，不填显示邮箱）。例如白班 08:00–19:00 张三、晚班 19:00–24:00 李四、夜班 00:00–08:00 赵五，首尾相接正好 24 小时。同一星期里启用的班次时间不能重叠（提示与哪个班次、星期几几点冲突，首尾相接不算）；每周没覆盖到的时段只提示、不拦截。最多 50 个。
- **临时调班**：请假、换班、节假日顶班：这段时间（最长 31 天，开始时间最远排到一年以后）由指定的人值班，优先于班次，不改班次本身；同一时段不能有两条有效调班（开始时间已过的调班，也要和已经结束的调班比较重叠）；没撤销、没结束的调班最多 200 条；可以选班次和日期自动填入起止时间；撤销要二次确认。
- **账号被停用 / 删除**：他的班次和调班不再算数，那段时间顶栏显示“值班 暂无”，管理页标红提醒。调班人的账号停用时，这段时间仍归这条调班、显示“暂无”，不会回落给被顶班的人；班次的值班人没换时，账号停用后这个班次仍可以改联系方式、停用。
- **同时编辑**：修改班次带版本号，别人在这期间改过同一个班次就拒绝保存，提示“刷新页面后重新编辑”，不会悄悄盖掉对方的修改；列表上的“停用 / 启用”走单独的接口，只改开关。
- **顶栏什么时候显示**：至少有一个启用的班次，或有一条还没结束的调班；都没有、值班表还没创建、取数出错时整块不显示，其它页面不受影响。到交班时刻、过服务器时区的零点页面自己更新（平时最长 5 分钟取一次）。窗口较窄时只显示姓名，手机宽度只显示“值班”。
- **登录有效期**：顶栏和管理页自己定时取值班信息的请求带请求头 `X-Background-Poll`，不给“滑动续期”的登录会话续期（会话是否有效照常校验）；放着没人动的页面不会让登录永不过期。其它接口不受影响。
- **权限**：顶栏的值班信息不需要权限；管理页和写操作用三个新按钮 `duty.view`、`duty.edit`（高危，含删除）、`duty.swap`，**默认只有超级用户**，可以在权限组里单独授予（不在 DBA 预设里）；值班人下拉里的账号名单（全部账号的登录名与显示名，不含邮箱）只给有 `duty.edit` 或 `duty.swap` 的人。新增 / 修改 / 停用 / 启用 / 删除班次、新增 / 撤销调班写系统审计（动作名以“值班-”开头，内容含时间、值班人、联系方式和备注）。按钮总数 145 → 148；使用文档新增“值班表”一章。
- **升级动作**：新增两张扩展表 `dbt_duty_shift`、`dbt_duty_override`（`deploy/sql/300_duty.sql`，升级时 `install.sh` 自动执行，可重复执行，不改任何已有表）。没执行时顶栏不显示、值班表页面提示先执行；缺表不会让 `/readyz` 降级；建表后约 30 秒内生效，无需重启。浏览器可能缓存了旧样式，按 Ctrl+F5 刷新一次。
- **说明**：1.67 的安装包里带有这个功能的早期状态（当时还没写进发布说明），本版是完整版；两个版本之间的升级不需要额外操作。脚本里“操作人”几列本版加宽到 150 个字符，1.67 已经建好的表里是 64 个字符，不用改——程序写入前会按 64 个字符截断。
- **暂时没有的**：时间只按服务器时区算；一个时段一个值班人（没有主 / 备班）；没有法定节假日日历（用临时调班）；值班信息还没有接入通知的“@ DBA 值班”和性能工单的 DBA 轮询（它们仍按各自原来的配置）；多个服务实例同时运行时，“班次时间不重叠”的校验只在单个实例内串行，两个实例同一瞬间各保存一个班次时可能产生重叠（重叠时取后开始的班次），建议只从一个实例的页面维护。
- **没有验证的**：只用内存存储和固定名单测试过（时间计算、校验、接口与权限、顶栏与管理页的浏览器测试），没有在真实的元数据库（MySQL）上跑过；升级后先建表，再按上面的例子建一个班次，看顶栏是否出现值班信息。

## 数据脱敏：通过视图查询时，顺着视图定义追到基表字段（1.68）

- **解决的问题**：脱敏配置写在基表字段上（如 `users.phone`），视图可以把字段改名（`phone AS mobile`）、套表达式（`left(phone,3) AS head`）、套另一个视图或自定义函数，结果列的名字和来源都看不出它来自敏感字段，通过视图查询会漏脱敏。
- **现在**：实例上配置了脱敏字段时，执行前平台从目标库读出语句用到的视图的定义（连同定义里又用到的视图，嵌套最多 8 层，一条语句里最多 100 个视图），把定义里的别名、表达式引用、自定义函数调用像子查询 / CTE 一样顺着传到视图的输出列，外层语句再引用这些列就脱敏。视图定义只用于分析，不会被执行。支持：MySQL 系（MySQL、PolarDB、ADB、SelectDB、Doris、PolarDB-X，读 `information_schema.VIEWS`）、SQL Server（`sys.views` 与 `sys.sql_modules`）、PostgreSQL（含物化视图，读 `pg_get_viewdef`）、ClickHouse（含物化视图、实时视图、窗口视图，读 `system.tables.as_select`）、MongoDB（视图 = 源集合 `viewOn` + 聚合管道：视图的管道接在语句的管道前面，沿 `$project`、`$addFields`、`$set`、`$group`、`$replaceRoot`、`$replaceWith` 里的改名追踪；视图的源集合、`$lookup` / `$graphLookup` / `$unionWith` 引用的集合也算语句涉及的集合）。
- **升级前必看（账号权限）**：读不到视图定义按**脱敏失败**处理。查询账号需要能看到视图定义：MySQL 系要有 `SHOW VIEW`（没有时 `VIEW_DEFINITION` 是空的）、SQL Server 要有 `VIEW DEFINITION`、ClickHouse 要能从 `system.tables` 读到 `as_select`、MongoDB 要能 `listCollections`（内置 `read` 角色有）。此外视图加密、定义超过 1 MB 或看不懂、目录查询出错（权限不足、超时、连接错误）、视图嵌套超过 8 层、一条语句涉及的视图超过 100 个，同样算失败。失败时：`query.block_on_mask_error` 开启 → 在线查询阻断（“数据脱敏异常，结果未返回”）；缺省（关闭）→ 放行结果并在页面提示是哪个视图（其余的列已按配置脱敏，只有经过那些视图的列可能漏）；SQL 导出工单一律中止导出。目标库根本没有视图目录（`information_schema.VIEWS` 不存在或列不兼容）不算失败，只是不展开。
- **开销**：实例上配了脱敏字段时，每条脱敏的 SELECT 按语句里写的对象名多几次目录查询（有嵌套视图时每多一层多一次；ClickHouse 每条多一次 `system.tables`，MongoDB 多一次 `listCollections`）；系统库 / 系统架构（`mysql`、`sys`、`information_schema`、`system`、`pg_*` 等）里的视图不查；实例上一条脱敏字段都没配置时不查，脱敏流程也不执行。
- **行为变化**：来源是视图的列现在按展开后的定义脱敏，宁多勿漏——视图定义把敏感字段改成某个名字后，同一条语句里别的表恰好同名的列也会被脱敏（保守匹配没有表级精度）。SQL Server 视图能直接溯源到基表的列仍按基表精确匹配；SQL Server 视图定义里显式写了列清单（`CREATE VIEW v (a, b) AS …`）时，输出列名按位置取自清单，查询体是 `*` 时清单里的每个名字都按最严规则处理。
- **顺带补的一处漏脱敏（ClickHouse）**：ClickHouse 特有的 `WITH <表达式> AS <别名> SELECT …`（别名取表达式的值）以前认不出来，`WITH phone AS p SELECT p` 会漏脱敏；现在语句里和视图定义里都认得，这类写法以前漏掉的列现在会被脱敏。
- **仍然认不出的**：MongoDB 视图的追踪覆盖的阶段与语句里自己写管道时一样，不覆盖 `$facet` 子管道内部的改名、`$setWindowFields` 等少见阶段；ClickHouse 视图定义里调用的自定义函数（`CREATE FUNCTION`）认不出来。应用内「数据脱敏」第 2.2 节第 6 条和第 6 节、使用文档已写明。
- **升级动作**：不需要，没有新配置项，不改表。升级后建议先检查查询账号的视图权限（见上），再决定 `query.block_on_mask_error` 的取值。
- **没有验证的**：只用手写的典型视图定义和假后端测试过，没有在真实 MySQL、SQL Server、PostgreSQL、ClickHouse、MongoDB 上建视图验证：各库返回的视图定义的实际格式（对象名是否带库名、是否规范化）、MongoDB 真实驱动解出来的 `options.pipeline` 的类型、SelectDB / Doris / PolarDB / ADB / PolarDB-X 的 `information_schema.VIEWS` 能不能用，都没有在真实实例上确认。上线前请在测试实例上各建几个视图（改名、套表达式、套视图）查一遍。

## 数据脱敏：调用存储函数 / 自定义函数的结果列整列脱敏（1.68）

- **解决的问题**：保守匹配只看结果列名、别名和表达式里引用的字段名，函数名被排除在外，`select fn_get_phone(1) as p`、`select dbo.fn_x(id)` 这类调用存储函数 / 自定义函数的结果列会漏脱敏——函数体里读了哪些字段，语句文本看不出来。
- **现在**：实例上配置了脱敏字段时，SELECT 列表里调用了非内置函数的结果列，以及取自 FROM 里自定义表值函数的列（SQL Server 的 `cross apply dbo.f(…) x`、PostgreSQL 的 `from public.get_users(1)`，含 `select *`、`别名.*` 和分不清来源的无限定列），整列按本实例已配置字段里**最严**的一条规则脱敏，与参数是不是敏感字段无关。这些列的别名视为已被污染：外层查询、子查询、CTE、变量（`DECLARE @k = dbo.fn(…)`、`SET @k = …`、MySQL 的 `@v := fn(…)`）和 SQL Server 的表变量（`INSERT INTO @t SELECT dbo.fn(1)` / `VALUES (dbo.fn(1))`）再引用也脱敏。
- **怎么判断“非内置”**：按各数据库的内置函数清单；带限定的名字（`库.fn(`、`dbo.fn(`、`schema.fn(`）一律算自定义函数，系统架构（`sys`、`pg_catalog`、`information_schema`）与 SQL Server 的 xml / hierarchyid / geography 方法除外；清单不全只会多脱敏、不会漏。ClickHouse 的内置函数太多、清单列不全，不做这一条。
- **行为变化**：这类列哪怕函数其实不碰敏感数据也会被脱敏，配置里有“整体隐藏”时显示 `***`；个别内置函数（尤其 Doris / ADB 的扩展函数、PostgreSQL 的少见函数）不在清单里时同样会被整列脱敏。有精确来源的普通列不受影响；实例上一条脱敏字段都没配置时这条规则不生效。
- **同时堵上的两处漏脱敏**：① 1.67 放开表变量写入后，`INSERT INTO @t (…) OUTPUT inserted.x AS y SELECT …` 会把写入的行当成第一个结果集返回，脱敏按 SELECT 列表匹配、认不出 OUTPUT 里的别名，敏感字段的原值能直接读出来；本版起只读批处理（在线查询和数据导出）一律拒绝 `OUTPUT`，提示“只读查询里不允许出现 output”。② SQL Server 里把敏感列拼进变量的 `SELECT @s += 列 FROM …`（以及 `-=`、`*=` 等）以前只有 `=` 赋值会把脱敏传给变量，之后 `SELECT @s` 取出来是原值；现在 `+=` 这类写法同样处理。
- **仍然认不出的写法（以前就有，不是这版引入的）**：保守匹配认不出把敏感字段的值换个列名输出的这几种：用列名列表给 CTE / 派生表的列改名（`WITH c(z) AS (SELECT phone …)`、`(SELECT phone …) d(z)`）、`PIVOT` / `UNPIVOT`、`VALUES` 派生表、`STRING_SPLIT` / `OPENJSON` / `JSON_TABLE` / `unnest` 等内置表值函数。SelectDB、Doris、PolarDB-X、ClickHouse 和没配 goInception 的 MySQL 系实例只有保守匹配，会漏；MySQL + goInception、SQL Server、PostgreSQL 先按来源精确匹配，这些写法能不能追到原字段没有在真实实例上验证。应用内「数据脱敏」第 6 节和使用文档的已知限制里已经写明。
- **升级动作**：不需要。
- **没有验证的**：只用语句文本和假后端测试过，没有在真实 MySQL、SQL Server、PostgreSQL 上建函数验证；SQL Server 内联表值函数，服务端能否把结果列溯源到基表也没在真实实例上确认（能溯源时按基表列精确匹配，不能时整列脱敏）。

## SQL Server：只读批处理可以用表变量攒中间结果；导出页和进度卡片调整；网络超时提示更清楚（1.67）

- **以前**：SQL Server 的在线查询和数据导出里，`INSERT` 一律被拒（“只读查询里不允许出现 insert”）。要先把配置或中间结果攒起来再统计的脚本，只能改写成 CTE。
- **现在**：用 `DECLARE @t TABLE (…)` 声明的表变量可以 `INSERT [INTO] @t SELECT … / VALUES (…)`，最后用 `SELECT` 输出结果。表变量只活在这个批处理里，不碰库里的数据（数据放在 tempdb 里，中间结果攒得太大会占用 tempdb 空间）。在线查询和数据导出共用同一套只读检查（写什么放行、写什么拒绝完全一致）；区别是在线查询要求批处理里有输出结果的 `SELECT`（没有就在检查时报错）并只执行第一个语句单元，导出遇到多个单元报错、有没有输出结果要到执行时才知道。
- **不放开的**：写表、`#临时表`、没用 `DECLARE … TABLE` 声明的变量、`INSERT TOP (n) INTO @t` 仍然拒绝，提示“INSERT 只能写入 DECLARE @变量 TABLE (…) 声明的表变量，不能写入表或临时表”；`INSERT … EXEC`、`OUTPUT`（包括不带 `INTO` 的 `INSERT … OUTPUT`，它会把写入的行当成一个结果集先返回，换个列别名就能绕过脱敏）、`SELECT … INTO`、对表变量的 `UPDATE` / `DELETE` 同样拒绝，但提示的是“只读查询里不允许出现 exec / output / into / update / delete”。在线查询里这些提示前面带“不允许的 T-SQL：”；不是以 `DECLARE` / `SET` / `SELECT` / `WITH` 开头的 `INSERT` 仍提示“仅支持 SELECT / WITH 查询”。
- **脱敏**：往表变量里写入了敏感字段的值，这个表变量的所有列都按最严的一条规则脱敏（写入来源是 `*` 时按配置里最严的规则），换个列名取出来也不会漏；代价是同一个表变量里不敏感的列偶尔会被一起脱敏。没有写表变量的脚本，脱敏行为不变。
- **行数上限**：在线查询的 `TOP n` 加在批处理里第一条产出结果的 `SELECT` 上（也就是返回的那个结果集），不会加到 `INSERT` 里的 `SELECT` 上；这条查询带 `UNION` / `OFFSET` / `TOP … PERCENT` 时不改写，由引擎在客户端截断。数据导出不改写语句：批处理无法预先统计行数，执行时读到“上限加 1”行就中止。
- **导出提交页**：超级用户的“导出原值（不脱敏）”放进一块卡片，说明文字在标题下面，勾选后整块变成危险色提醒，理由框带字数（够 5 个字变绿）；“批量导出”开关和上面选项的间距收紧。
- **进度卡片**：执行中的工单，“取消原因”输入框和“取消执行”按钮放在同一排，窄屏自动折行。
- **导出失败的网络提示**：提交前“检查并统计行数”、单实例导出、批量导出（含合并成一个文件）和失败实例的重试，遇到网络类错误时，结果里先写原因和下一步，原始错误（带地址和端口）附在最后方便 DBA 排查。分四类：连接实例超时（`dial tcp … i/o timeout`）、读取数据时网络超时（`i/o timeout`，多半是查询太慢，或网络 / 防火墙中断了长连接）、无法连接（连接被拒、地址解析失败）、连接被中断（连接被重置、`broken pipe`、`unexpected EOF`）。提示里只说“重试”，不假定有哪个入口（批量导出点失败实例的重试，检查阶段改完再检查）。语句自己的错误（语法错误、表不存在……）和没认出来的网络错误一律原样显示；超时时间和重试方式没有改。
- **升级动作**：不需要。浏览器可能缓存了旧样式，按 Ctrl+F5 刷新一次。
- **没有验证的**：只用语句文本、构造的错误文字和假后端测试过，没有在真实 SQL Server 上执行含表变量的批处理；网络错误按错误文字识别，没有在真实断网 / 超时的环境里验证（认不出的错误原样显示）；导出提交页的新样式在桌面宽度的浏览器里看过，其它窗口宽度和皮肤只有页面测试。

## 数据导出：批量导出可以合并成一个文件；列表页和在线查询的结果区填满窗口（1.66）

## 数据导出：超级用户可以在提交时选择“导出原值（不脱敏）”（1.63）

## 数据归档：归档并删除 / 仅清理不再按主键排序读取（1.61）

- **解决的问题**：原来每批读取是 `WHERE 条件 AND 主键 > 断点 ORDER BY 主键 LIMIT N`。在几十亿行、命中几亿行的大表上，一旦优化器改选时间索引再排序（统计信息偏差等），每批都要遍历几亿条索引项，会拖垮线上。归档并删除、仅清理读出来的行本来就要删，先后顺序不重要，所以去掉排序。
- **现在怎么读**：归档并删除、仅清理每批只取“当前符合条件的前 N 行”（`WHERE 条件 LIMIT N`，没有 `ORDER BY`、没有断点），备份校验并删除之后，下一批自然取到剩下的行。没有排序就不会有 filesort；窗口结束、暂停、失败、重启之后直接接着取，也不再有“主键小但后过期的行要等下次从头才能捡到”的限制。
- **仅备份没变**：它不删数据，仍按主键升序、用断点翻页。
- **主键含字符串等列的表仍按主键排序读取**：这两种模式要记下处理过的最小 / 最大主键（恢复数据时按它从备份表补回），范围必须和数据库的比较规则一致。整数、小数、日期时间类的主键能在程序里正确比大小；字符串（受排序规则影响）、浮点、二进制等不行，这类表保持原来的“按主键排序 + 断点”，不改变恢复的准确性。
- **配套保护**：① 空转保护——读到行却一行也没删掉（触发器、权限、行被并发修改）时立即停止并自动暂停任务，不会原地打转；② 读取过慢保护——不排序读取没有断点可以跳过“刚删掉、InnoDB 还没清理”的记录，清理落后（有长事务）或执行计划变了会越读越慢，连续 3 次读取一批超过 15 秒就停止并自动暂停；③ 试运行新增“首批读取”检查项：用每批真正会用的那条语句实测读取最多 200 行并计时，超过 3 秒黄色、超过 15 秒（或 60 秒没返回）红色；预计扫描行数很大但实测首批读取很快时，`EXPLAIN` 不再标黄（预计行数是不考虑 `LIMIT` 提前结束的上界估计）。
- **页面变化**：任务详情的“将执行的 SQL”里，归档并删除 / 仅清理的读取语句不再有 `ORDER BY` 和断点；这两种模式的任务不再显示“断点”，运行记录里“主键断点范围”改称“处理的主键范围”，内容仍是本次处理过的最小 / 最大主键。
- **升级**：没有数据库结构变化。升级前遗留在任务上的旧断点会被忽略，并在这两种模式的下一次运行结束时清掉；计划里的调度、审批、备份、恢复都不受影响。
- **没有验证的**：只用假 MySQL 服务端和内存替身测试过，没有在真实 MySQL / PolarDB-X 上验证；上线前请看试运行里的“首批读取”耗时，大表上线后观察每批的读取耗时（事件日志里每批会显示“读取 N ms”）。

## 数据归档：时间列支持 bigint / int 里的 10 位秒、13 位毫秒时间戳（1.61）

- **解决的问题**：很多业务表用 `bigint` 存 Unix 时间戳（10 位是秒，13 位是毫秒），向导会提示“该表没有 datetime / timestamp / date 列，不能按时间归档”。现在这类表可以直接按时间归档。
- **用法**：新建 / 编辑任务的“条件”一步，时间列下拉里除了日期时间列，还会列出 `int` / `bigint` 列（名字像时间的排前面，标“整型”）；选了整型列后出现“时间单位”（10 位秒 / 13 位毫秒），系统抽样读取该列按位数预填，并显示“最早 … 最晚 …”换算出的时间供核对；预填不对可以手动改。
- **条件怎么写**：系统把“N 天前”换算成同一单位的时间戳再比较，例如毫秒：`` `CreateTime` > 0 AND `CreateTime` < (UNIX_TIMESTAMP() - 15552000) * 1000 ``。比较的右边是常量、列上不套函数，时间列上的索引照常可用；值为 0 / NULL 的行视为“未设置”，不会被归档。
- **防选错**：单位选错会让条件命中整张表（例如把 10 位秒当成毫秒），所以有三道防线——向导里抽样与所选单位不符直接标红；试运行里新增“时间单位”检查项，不符判红且不再统计命中行数；运行中每批读到数据后，若这一批的时间值整批都小于所选单位的合理下限（1980 年）就立刻停止并自动暂停任务，此时没有备份、没有删除任何数据。
- **不支持**：`varchar` / `decimal` 里存的时间戳、`yyyymmdd` 这类整数日期、微秒 / 纳秒时间戳。
- **兼容**：旧任务不受影响——没有时间单位的任务按原来的日期时间列处理，生成的 SQL 与关键字段哈希都和升级前一致，已批准的任务不会被要求重新审批。时间单位属于关键字段：改它需要重新试运行并重新审批，旧断点清空。
- **升级**：`dbt_archive_task` 新增一列 `time_unit`（`deploy/sql/180_archive.sql` 末尾有可重复执行的加列语句，升级时 `install.sh` 自动执行）。程序比这一列先上线时，“数据归档”页面提示先执行 `deploy/sql/180_archive.sql`，不会报错。接口新增 `GET /api/v1/archive/sources/time-probe`（只读，抽样与最早 / 最晚值），任务的输入 / 视图多一个 `time_unit` 字段。
- **没有验证的**：整型时间戳的探测与运行只用假 MySQL 服务端和内存替身测试过，没有在真实 MySQL / PolarDB-X 上验证；上线前请在试运行里看一眼显示的最早 / 最晚时间是否合理。

## 日志解析：大结果落盘、回滚到上限在事务边界分段、读到末尾的校验（1.56）

- **回滚到上限不再失败，改为分段**：回滚模式遇到条数 / 体积上限、扫描事件数上限、超时、目标库中途卡住时，不再报“回滚 SQL 必须完整，本次不给出结果”，而是在**事务边界**结束成“一段”：这一段的回滚 SQL 完整可用，页面显示“第 N 段”和续接位置，点“继续下一段”把续接位置填进起始位置（其它条件不变），再生成下一段，直到读完。**完整回滚要按段号从大到小执行：先执行最后一段，最后执行第 1 段**；每一段的文件内部也要严格按文件顺序执行。结果文件头写明第几段、是否还有后续。连第一个事务都放不下时仍然失败（没法分段），要调大上限或缩小范围。还原模式不变：超限只截断并提示。
- **大结果存到磁盘，不再占内存**：单个任务的结果超过 8 MB 就转存到服务所在机器的临时文件（`<临时目录>/dbtool-binlog/`，临时目录是系统临时目录，可用环境变量 `TMPDIR` 指定）。分页和下载都从文件读，下载边读边写、不再把整个文件装进内存；页面的“下载 .sql”改为浏览器直接下载（不再先装进页面内存）。结果过期、任务失败 / 取消时立刻删除文件，进程被杀遗留的在下次启动时清掉；文件权限 0600。内存预算仍是 96 MB，磁盘预算是 `max(96 MB, 2 × 结果体积上限)`。**要保证临时目录所在磁盘有足够空间；若 `/tmp` 是内存文件系统（tmpfs），落盘就等于占内存，请用 `TMPDIR` 指到磁盘目录。**
- **读到末尾的校验**：以前读流时“8 秒没有新事件”一律当成读完，目标库中途卡住（磁盘冷读、网络停顿）也会悄悄得到一个不完整的结果。现在服务端发过“没有更多事件”的信号才算读完；没收到就对照结束位置，位置没到就是目标库卡住：还原模式保留已读到的部分并写明只读到哪里，回滚模式在事务边界分段，让你接着读。
- **没有改**：权限、接口路径、扫描事件数上限（5,000,000）与超时上限（600 秒）本身、“最多条数 / 结果体积上限”的取值范围与系统配置项。接口新增：请求参数 `segment`（段号，页面自动带上），任务视图新增 `segment`（回滚任务：`index` / `more` / `next_file` / `next_pos` / `reason`）。
- **没有验证**：没有在真实 MySQL 上跑过（只有假服务端和手工拼的事件）；“读到末尾”依赖服务端的 EOF 包或结束位置，若遇到结果被误报“目标库卡住”，请反馈。

## 日志解析：“最多条数”和“结果体积上限”的最大值改成系统配置项，默认 50 万条 / 1 GB（1.55）

- **改了什么**：“日志解析”页的“最多条数（≤ N）”原来最多只能填 20000，“结果体积上限 MB（≤ N）”最多只能填 8，写死在程序里，回滚范围稍大就会报“结果达到 20000 条的上限”。现在这两个最大值是系统配置项 `binlog.max_rows`（默认 500000 条，可调 1 ~ 10,000,000）和 `binlog.max_result_mb`（默认 1024 MB，可调 1 ~ 8192），在“平台设置 › 系统配置 › 日志解析”修改（仅超级用户；也可用 `dbt-admin settings set`），保存后几秒内对新任务生效。页面上括号里的 N 就是当前生效的最大值。
- **页面默认填写的值不变**：仍是 500 条 / 2 MB，要解析更大的范围，在页面上把这两项填大。

- **没有改**：扫描事件数上限（5,000,000）、超时上限（600 秒）、每人 / 全局的并发任务数、权限与接口格式；条数很多时可能先碰到扫描事件数或超时。

## SOAR 可在页面配置（1.45）

智能调优里的 SOAR 以前只能在服务器上用 `dbt-admin settings set --force` 配置，现在超级用户可以直接在“平台设置 › 系统配置 › SQL 优化工具”里设置程序路径、配置文件和测试库，并加了几道安全约束：

- **写法**：程序路径必须是绝对路径（不含 `..`），文件名必须是 `soar`（Windows 可带 `.exe`），不能指向 `sh`、`python` 之类的任意程序；配置文件必须是绝对路径；测试库 DSN 必须能解析出主机和端口（形如 `user:password@host:3306/db`）。
- **保存时核对服务器上的事实**（命令行 `--force` 不核对）：程序与配置文件必须存在、是普通文件（不能是符号链接或目录），程序要有执行权限，文件与所在目录都不能被“其他用户”改写，配置文件不超过 1MB；测试库地址不能是已登记的生产实例（含已停用的；主机名先解析成 IP 再比对，同一个 IP 和端口算同一个），实例没有标注环境时也拒绝，读不到实例清单时同样拒绝。
- **高危确认与留痕**：三项都标“高危”，保存时要原样键入确认文字；变更记录与系统审计照常写入，测试库 DSN 含密码，只记“已更新”，加密保存。
- **未配置时的提示**：智能调优页对超级用户在提示旁给出“去配置”链接，其他人只看到“请联系超级用户”。
- **局限**：测试库只按地址比对，经代理 / 别名 / SSH 隧道连到生产库的认不出来；程序文件只核对属性，不会在保存时执行它。
- **命令行**：`dbt-admin settings set --key optimizer.soar_path …` 不再需要 `--force`（写法检查仍然有）；`--force` 现在只用于页面里不显示的内部状态项。设置框架里的“页面只读”（`Locked`）机制保留，但目前没有登记项使用。

## SOAR 随包部署，install / upgrade 可重复部署（1.46）

  - **配置** → `<安装目录>/plugins/soar.yaml`（去掉 CR；`log-output` 改写为 `<安装目录>/data/soar.log`，包里原来的 `/opt/dbtool/soar.log` 运行用户写不进去）。已存在不覆盖，包内新版另存为 `soar.yaml.dist`，可自行比对合并。

- **还需要管理员做的**：`optimizer.soar_test_dsn`（SOAR 的测试库，必须是非生产库，SOAR 会在其中建临时表）。没配之前“智能调优”里的 SOAR 不可用，SQL 体检的离线分析不受影响；安装结束时如果这项没配会提醒。

## 工单 SQL 里的敏感字段值脱敏（1.40）

- **范围**：SQL 上线工单（MySQL / MariaDB / PolarDB / PolarDB-X / SelectDB / Doris / ADB / SQL Server）里的 `UPDATE` / `INSERT` / `REPLACE` / `DELETE` 及其 `WHERE`，凡绑定到“数据脱敏”已配置字段（库.表.字段，或实例内同名字段）的值，**除超级用户外一律只显示脱敏后的值**——提交人、审批人、执行人都一样，审批期间也一样。例：`update abc set password='345345345' and userid=9182` 显示为 `update abc set password=*** and userid=9182`。规则取自“数据脱敏”配置，与在线查询共用。
- **位置**：工单详情的 SQL、检查结果与执行结果里每条语句、错误信息里回显的同一个值、回滚语句、通知里的 SQL 预览与执行记录。库里保存的仍是原文，执行用它；遮盖发生在读取时。
- **限制**：含脱敏值的工单不能复制，回滚语句不能下载（页面上可查看脱敏后的内容），明文只有超级用户能取。
- **识别方式**：不依赖语法树的词法分析，宁多勿漏——认不出“字段 = 值”（如 CASE、复杂子查询）时，该语句里所有字符串与数字字面量都会被遮盖；`INSERT` 没有字段列表时，该表的 `VALUES` 全部遮盖。读脱敏配置失败时详情打不开（不会把原文给出去）。
- **没有真库验证**：只用假数据测试过，请先用一张带脱敏字段的测试工单核对显示。

## 侧栏改为手风琴：默认全部折叠，打开一组其余自动折叠（1.39）

- **侧栏**：同一时间只展开一个分组。默认只展开当前页所在的分组（首页等不属于任何分组的页面全部折叠）；点某个分组标题 = 展开它并折叠其它分组，再点一次折叠。不再把展开 / 折叠状态记在浏览器里，刷新或换页后回到“当前页所在分组”。这取代 1.20 的“默认全部展开”。

## SQL Server 脚本自管事务可执行、批量工单重试通知（1.39）

- **SQL Server 工单**：执行单元以前一律包在外层事务里，脚本里 `IF @@TRANCOUNT > 0 … 拒绝执行` 这类检查永远命中（报“当前会话有未提交的事务，本脚本不执行”），脚本自己的 `COMMIT` / `ROLLBACK` 也与外层事务冲突。现在检测到单元里有 `@@TRANCOUNT` 或 `BEGIN TRAN` / `COMMIT` / `ROLLBACK` / `SAVE TRAN`（不含注释、字符串里的字样）就不再包外层事务，原样在会话里执行；脚本结束时仍有未提交事务、出错或 PRINT 判失败时一律回滚，并把结果标为失败，不会把没提交的变更报成成功。其余单元仍是“一个单元一个事务”。
- **批量工单重试失败实例**：开始重试时发“开始执行”通知，结束时发“执行完成 / 执行异常”通知，标题与正文写明重试的实例与结果。

## 数据归档支持 PolarDB / PolarDB-X（1.38）

- **类型**：归档来源与库表备份目标除 MySQL / MariaDB 外，新增 `polardb`、`polardb-x`（`polardbx`）主库。Doris / SelectDB / ADB（没有按主键分批删除的事务语义）与 PostgreSQL 等仍不支持。
- **PolarDB-X 兼容处理**（它只是 MySQL 协议兼容）：会话锁等待参数设不上、读不到 `sql_log_bin` 时降级继续（读到 `sql_log_bin=0` 仍拒绝）；`information_schema.COLUMNS` / `STATISTICS` 不可用时退到 `SHOW COLUMNS` / `SHOW INDEX` 取列与主键；库表备份的建表语句去掉 `dbpartition` / `tbpartition` / `BROADCAST` / `SINGLE` / `LOCALITY` 子句；Threads_running、复制延迟读不到时标“未检测”，不阻止运行。
- **验证范围**：以上只用协议级假服务测试过，没有在真实 PolarDB / PolarDB-X 上跑过。启用前请在真实实例上先做试运行。
- **未包含**：PostgreSQL 归档（需要另写源库 / 目标库 / 探针与 SQL 方言）。

## 实例列表版本换行、脱敏保存反馈、PolarDB-X 对象信息兜底（1.36 / 1.37）

- **实例列表**：“类型 / 版本”列版本号过长时另起一行，不再撑宽行。
- **数据脱敏**：保存时暂存项与当前配置完全一致（含只改了正则表达式的情况）不再静默无反应：差异表带出正则表达式，无变更时给出提示并清除暂存。
- **对象信息（在线查询库表树右键）**：MySQL 系实例读表 / 视图详情时，`information_schema.TABLES` 缺列或 `COLUMNS` 不支持排序（PolarDB-X / DRDS 等兼容实现）不再让整个详情失败：表信息退到基础列，列信息改用 `SHOW FULL COLUMNS`，各小节读取失败只在该小节写原因。
- **错误状态码**：对象信息 / 可编程对象接口里目标库的报错与超时改用 HTTP 422（原 502 / 504 常被反向代理换成固定页面，看不到真实原因）。

## 实例列表批量设置环境（1.34）

- **功能**：“实例管理 › 实例列表”勾选实例后，用“批量设置环境”把它们一次设为生产 / 测试 / 未设置；已经是目标环境的跳过，看不到的实例和旁路表未建时分别报错 / 整批拒绝。权限与批量停用相同（`change_instance` + 按钮 `instance.edit`），审计动作“批量设置环境”。
- **接口**：`POST /api/v1/instances/batch/env {ids, env}`（`env` 取 `prod` / `test` / 空串），返回每个实例的结果 `{id, name, ok, message}`。
- **界面**：二次确认里要键入的文字改为红色加粗，避免把“以确认”这类提示词当成要输入的内容。
- **PolarDB-X**：在线查询、SQL 上线工单、数据导出工单现在能选到 PolarDB-X 实例（类型值 `polardb-x`，也接受 `polardbx`），走 MySQL 协议，与 PolarDB 同一套流程；数据脱敏**不用** goInception 语法树，视同 SelectDB / Doris，完全按结果列名与表达式引用保守匹配（宁多勿漏：不同库表里同名的列、引用了敏感字段的函数 / 运算列都会被脱敏）。没有在真实 PolarDB-X 上验证；EXPLAIN 扫描行数（SQL 防火墙）不支持，因为它的执行计划格式与 MySQL 不同。实例仍需带 `can_write`（上线工单）/ `can_read`（查询、导出）标签，并关联到用户的资源组。
- **数据字典**：去掉残留的“数据字典”权限码 `menu_data_dictionary`（菜单 数据字典）与 `data_dictionary_export`（导出数据字典）：权限组管理的权限矩阵里不再显示，新装库的基础数据里不再创建。已有库里的这两行与权限组授权保留不动，但不再生效；`internal/dict` 只保留在线查询工作台的“对象信息”和“可编程对象”两个接口。
- **在线查询报错**：目标库返回的错误（如 SQL Server 的权限错误）HTTP 状态由 502 改为 422，避免被反向代理 / 网关的 502 错误页替换后只剩“请求失败（HTTP 502）”。

## 系统设置重建：脱离 Archery 的 `sql_config`，新的设置中心（1.31）

> **注意**：本条里的“首次启动自动导入”、`dbt-admin settings import`、页面顶部的“升级导入”提示与对 `dbt-migrate` 的描述在同一版本内已被移除（见上面“移除运行时兼容层（1.31）”）；当前没有旧设置表的导入路径，`dbt-admin settings` 只有 `list` / `get` / `set` / `reset`。

**一句话**：系统参数不再是 Archery 那张键值表（`dbt_sql_config`），而是本项目自己的 `dbt_setting`：键名 `<领域>.<名称>`、每项有类型 / 默认值 / 取值范围 / 说明，页面是按功能分组的设置中心，所有模块经同一个服务读写，修改有变更记录和审计。

- **升级前必读（行为变化）**
  - **必须先执行 `deploy/sql/260_setting.sql`**（`install.sh upgrade` / `dbt-admin bootstrap --only-sql --apply` 会自动执行）。`dbt_setting` 现在是 `/readyz` 的必需表，缺失时 `/readyz` 返回 503（升级脚本的健康检查会因此自动回滚），所有设置按默认值运行。
  - **首次启动自动导入**：把 `dbt_sql_config` 与 `dbt_auth_setting` 里登记过的项一次性导入 `dbt_setting`（密文用当前密钥解开；敏感项重新加密，其余项明文保存）。已有值不覆盖；登记表里没有的旧键、旧值不合法的项、当前密钥解不开的密文**不导入**，页面顶部列出它们的键名，需要在设置中心重新填写。导入是幂等的：旧表内容没变不会重复执行；服务启动之后才迁入 Archery 数据（`dbt-migrate`）的，下次启动会补导入没有的键。
  - **键名全部改了**：旧 `lock_cnt_threshold` → `security.login_lock_attempts`、`query_check` → `query.block_on_mask_error`、`data_masking` → `query.mask_enabled`、`auto_review` → `review.auto_approve_enabled` …… 现行全部键见 [settings-reference.md](settings-reference.md)（由登记表生成，不含旧键；仓库里没有完整的“旧键 → 新键”对照表，上面只是示例）。外部脚本 / 手工 SQL 里按旧键名读写 `dbt_sql_config` 的，改用 `dbt-admin settings`，或直接读写 `dbt_setting`。
  - **取值收紧**：写入时按类型 / 范围 / 取值集合校验，旧库里的“怪值”不再被容忍：布尔只认 `true/false`（导入时 `True/1/yes/on` 会被规整）、`export.storage_type` 只能是 `local`、数值越界的不导入。
  - **一处语义改写**：`auto_review_wrong`（`1` / 空或 `2` / 其它）→ `review.auto_reject_level`（`warning` / `error` / `never`）；导入时按旧语义转换，缺省仍是“仅错误时自动驳回”。
  - **旧表不再读取**：升级后 `dbt_sql_config` / `dbt_auth_setting` 保持原样、不再被读取，可在确认无误后自行清理。**回滚到旧版本**时旧版读它们（升级时没动过），新版期间在设置中心里做的修改不会带回旧版。
  - 不再兼容“Archery 与 dbtool 同时读同一张设置表”：`dbt_sql_config` 里“空值 = 某种行为”的 Archery 约定不再适用，缺省值只在登记表里写一次。
- **设置中心（系统管理 › 系统配置，仅超级用户）**：左侧功能分组 + 搜索 + “只看已修改”；每项显示名称 / 键 / 说明 / 默认值 / 范围，开关 / 数字（带单位）/ 下拉 / 文本各用合适控件；修改先积在页面上，底部“保存修改”确认“旧值 → 新值”后**整批校验、一次写入**（任何一项不合法都不写，错误显示在对应项下）；高危项要键入确认文字；每项“恢复默认”和变更记录；敏感项只显示“已设置”，可修改 / 清除，变更记录与审计里不带内容。有专门页面的功能（防火墙规则、goInception 连接测试、登录方式等）在设置项下给跳转链接，两边写同一份数据。
- **命令行**：`dbt-admin settings list|get|set|reset|import`（`import` 已在 1.31 内移除；见 `docs/admin-cli.md` §6.3），写入走同一套校验、加密、变更记录与审计；程序路径类（`optimizer.*`）页面只读，用 `--force` 修改——取代了以前“只能直接改库”。`dbt-admin check-secrets` / `reencrypt` 的处理对象加上了 `dbt_setting`（仅 `encrypted=1`）。
- **读取**：进程内快照缓存（本进程保存后立即失效，其它进程最多 3 秒），各模块的读取从“每次查库”变成统一的设置服务；新增模块只需在登记表里加一项。
- **接口**：`GET/PUT /api/v1/settings/config`（批量 `{"changes": {...}}`）、`PUT /api/v1/settings/config/:key`、`GET /api/v1/settings/config/history`；旧的按项名 `PUT .../:item {value}` 仍可用，但项名要用新键。
- **数据库变更**：新增 `dbt_setting`、`dbt_setting_history`（`260_setting.sql`，幂等）；不改任何旧表。
- **没有验证**：只在内存假库 / 假驱动与演示服务上验证过设置服务、导入、页面与命令行；真实 MySQL 上的建表、`INSERT … ON DUPLICATE KEY`、导入（含真实 Archery 的 `sql_config` 密文）与多进程缓存延迟需要在演练库确认。

## 迁移的密文换成 dbtool 自己的密钥：dbt-migrate --reencrypt、dbt-admin reencrypt（1.30）

> **注意**：`dbt-migrate`（含 `--reencrypt`）从 1.31 起已移除；`dbt-admin reencrypt` 仍在，见 [admin-cli.md](admin-cli.md) §6.2。

- **背景**：迁移工具默认把密文原样复制，所以旧系统用哪把密钥加密的，新系统就得用同一把，否则实例账号 / 配置项读成乱码（旧 Archery 没自配密钥时用的是公开缺省 `SECRET_KEY`）。现在可以让目标库里的密文直接就是 dbtool 自己的密钥。
- **迁移时换**：`dbt-migrate --reencrypt`。`SECRET_KEY` / `MIRAGE_*` 仍是“旧系统的密钥”（用来解密），新增 `DST_MIRAGE_SECRET_KEY`（缺省 `DST_SECRET_KEY`）/ `DST_MIRAGE_CIPHER_MODE` / `DST_MIRAGE_CIPHER_IV` 是 dbtool 自己的密钥（与 `dbtool.env` 一致）。只处理 5 张表 12 个加密列（实例 / SSH 隧道 / 实例账号 / 系统配置 / 2FA）。
- **事后原地换**：`dbt-admin reencrypt`（已经原样复制过、读出来是乱码的库用它，不需要源库）。默认只演练；`--apply --yes` 写入；所有改动在一个事务里，条件更新，写一条系统审计“密文重加密”。旧密钥依次尝试 `OLD_MIRAGE_SECRET_KEY`（旧系统单独配置过时给）、`SECRET_KEY`、Archery 公开缺省密钥。
- **规则（两处相同）**：旧密钥解得开 → 用新密钥重新加密；明文 → 用新密钥加密（加密后超出列宽的保留明文，dbtool 读取时兼容明文）；已经是新密钥的 → 不动；**新旧密钥都解不开的 → 原样同步（不改、不丢）**，只列表 / 列 / 数量 / 配置项名或主键，管理员在“系统管理 › 系统配置”或实例管理页重新保存即可按当前密钥加密。解出的必须是可读文本，不会把乱码当明文。
- **重复运行安全**：转换是确定性的，第二次运行全部“已存在且一致”；`dbt-admin reencrypt` 对已换过的值不动，混合状态（一部分是新密钥保存的）也安全。已经原样复制过的目标库再用 `--reencrypt` 迁移会按冲突中止并提示（先清空这 5 张 `dbt_` 目标表，或改用 `dbt-admin reencrypt`）。
- **安全**：源库仍然只读；报告 / 日志 / 审计里只有数量、主键、长度和哈希前缀，没有任何密钥、密文或明文值；`dbt-admin reencrypt` 在当前生效密钥无效（不会退而求其次拿别的密钥写库）或就是 Archery 公开缺省值时拒绝写入。
- **没有验证**：只在内存假库 / 假驱动上测过；真实 MySQL 上的列宽、`ssh_tunnel.pkey`（大文本）与唯一键行为需要在演练库确认。写入前请先备份这 5 张表。
- 没有数据库变更；新增环境变量只在上述命令里使用（`DST_*`、`OLD_*`），服务本身不读。

## 密钥自检：dbt-admin check-secrets，启动日志提示实例账号 / 密码解不开（1.29）

- **现象**：从 Archery 迁来后用户能正常登录，但 `dbt_sql_config` 的值不是明文、实例连不上目标库。
- **原因**：旧系统没自配密钥时，`dbt_sql_config` 与实例账号 / 密码是用 Archery 公开的缺省 `SECRET_KEY` 加密的；新系统部署（`--gen-secrets`）用了另一把。登录用的是 PBKDF2 密码哈希，不依赖这把密钥，所以不受影响。
- **新增**：`dbt-admin check-secrets`（只读）判断是哪把密钥加密的并给出修法；服务启动时若有实例账号 / 密码解不开，日志里列出实例名（以前只检查 `dbt_sql_config`）。

## 慢查日志数据源自动选择：digest 表是空的时回退到平台采集（1.21）

- **现象**：“SQL 优化 › 慢查日志”对 MySQL 实例一直没有数据，而“SQL 查询 › 查慢日志”里同一批实例有数据。
- **原因**：自动选数据源时，只要 `dbt_mysql_slow_query_review` / `dbt_mysql_slow_query_review_history` 两张表存在就用 pt-query-digest 数据；而这两张表是基础表结构，安装 / `bootstrap` 时就会建出来（空表），没部署 pt-query-digest 推送脚本的环境因此永远查到空。
- **现在**：自动模式下，历史表里**确实有该实例（`hostname_max = host:port`）的数据**才用 digest，否则用平台采集 `dbt_slow_logs`。判定结果缓存 1 分钟，是 `LIMIT 1` 的存在性查询。“全部实例（汇总）”、统计、明细、趋势、库列表同一个判定；页面上手动选“数据源”不受影响。
- **行为变化**：同时有 digest 数据和平台采集数据的实例，仍然优先 digest；只有采集数据的实例，现在会显示采集数据（以前是空）。
- 没有数据库变更、没有新配置项。

## SQL Server：PRINT 的输出按语句显示，不再把工单判成失败（1.29）

- **问题**：脚本里在 `CREATE PROCEDURE` 后面写一句 `PRINT N'xxx 创建完成。'`，执行时这一句被标成“错误”，信息栏里就是 PRINT 的那句话，后面的语句全部“前序语句失败, 未执行”，整张工单变成“执行有异常”。原因是从原项目沿用来的约定：收到 PRINT（消息号 0）就按失败处理并回滚该单元（原项目里 PRINT 常被用来提示“不要执行”）。
- **现在（默认）**：PRINT / 严重度 ≤10 的 RAISERROR 输出只是**信息**，显示在对应那条语句的“信息”栏里，语句照常提交、标“通过”，后面的语句继续执行。
- **要恢复原来的约定**：系统配置（`dbt_sql_config`；1.31 起为 `dbt_setting` 的 `review.mssql_print_as_error`）里把它设为 `true`，之后 PRINT 又按失败处理并回滚该单元、其后的语句不执行。配置随时生效，不用重启。
- **注意（安全）**：如果你们有脚本靠 PRINT 来“拦截”（例如检查不通过时 PRINT 提示，依赖平台把这一单元回滚），升级后这类脚本的拦截不会再生效，请改用 `RAISERROR(..., 16, 1)` 或 `THROW`（它们是真正的错误，一直会让该单元回滚并停止），或把 `mssql_print_as_error` 设为 `true`。
- 只影响 SQL Server 的原生执行（含批量上线）；没有数据库变更。

## 取消执行：执行中的工单可以由 DBA 主动取消（1.29）

- **场景**：工单执行很久（大表变更、锁等待……）还没结束，需要停下来。
- **入口**：工单详情页的“执行进度”卡片里新增“**取消执行**”（只在工单“执行中”、你有权限、且这张工单由当前服务进程在执行时出现）。原因必填，点后先弹高危确认，说明后果，生产环境还要键入工单号。
- **权限**：新增按钮权限 `sqlworkflow.cancel_run`（“取消执行（执行中的工单）”，高危），**默认在 DBA 预设里**；另外要在该工单资源组里有“资源组内执行”权限。超级用户可用。提交人本人、审批人没有这个权限。
- **做了什么**：取消正在执行的 context。MySQL 系原生执行会在驱动关连接之外补发 `KILL QUERY`，让目标库真的停下这条语句；SQL Server / Redis / 数据导出靠 context 中断。其后的语句不再执行。
- **结果**：工单变为“执行有异常”，被中断的那一行写明“已被 xxx 取消执行（原因：…）”，工单日志里有“取消执行”记录（谁、为什么），系统审计里有“SQL上线-取消工单执行”，异常通知照常发送。**不会自动重试**。
- **不会做的**：已经成功执行的语句不会回滚；被中断的那一条由目标库回滚（大事务回滚本身也要时间；DDL 的后果取决于语句和 MySQL 版本，请到目标库核对）。取消请求到得太晚（语句已全部执行成功）时，工单仍是“已正常结束”，日志里写明没有生效。
- **限制**：①只能取消由本进程在执行的工单，别的节点在执行时无法远程取消（进程已失联请用“标记为执行异常”）；②goInception 执行的工单，取消只会断开与 goInception 的连接，已经下发到目标库的语句可能仍在执行，确认框里有提示，需到“会话管理”核对并终止；③批量工单取消会中断所有正在执行的实例，不是逐个实例取消。
- **接口**：`POST /api/v1/sqlworkflow/:id/cancel-run {remark}`；详情接口多了 `can_cancel_run`。没有数据库变更、没有新配置项。

## SET 打头的脚本整份按顺序执行，返回最后一条查询（1.22，修正 1.21）

- **1.21 的问题**：脚本以 `SET` 开头时，只执行 `SET` 加第 1 条查询，后面的查询被忽略，返回的是第 1 条（常常只是“校验”）的结果。
- **现在**：`SET` 打头的脚本，所有语句在同一个只读会话里**按顺序全部执行，返回最后一条查询的结果**。中间的查询结果丢弃，只有报错会中断整份脚本（校验型查询靠子查询返回多行报错来中断）；错误里指出是第几条。
- **整份先检查、再执行**：脚本里有任何一条不是放行的 `SET` / 查询（`INSERT` / `UPDATE` / `DELETE` / `PREPARE` / `INTO` / 加锁读取 / 其它 `SET` / `mysql` 系统库……），整份拒绝，一条都不执行。最后一条必须是查询。（1.21 里后面的写语句是“忽略”，现在是“整份拒绝”。）
- **安全**：中间的每一条查询都像单独运行时一样校验库表权限和 SQL 防火墙（表对象、扫描行数），行数按上限改写；脚本里禁止 `SELECT … INTO @变量`；变量的脱敏污染分析覆盖整份脚本。
- **上限**：脚本 ≤ 40 条语句，其中查询 ≤ 10 条、`SET` ≤ 20 条。
- **页面**：选中整份脚本再运行 = 按顺序全部执行；光标放在某条语句上运行 = 只运行这条（脚本开头的 `SET` 自动带上）。提示条里有说明。
- **没变**：没有 `SET` 打头的多语句仍然只执行第 1 条；导出工单仍然不接受 `SET`。
- **注意**：结果列的脱敏是按“引用了敏感字段名”保守匹配的。生成类脚本里的关联子查询（例如用 `ApiKey` / `ApiCode` 判断“凭证是否已存在”）会让它输出的列（如“已存在密钥Id”）也被脱敏；要看明文，用不开脱敏的实例，或让管理员调整该实例的脱敏字段。
- **没有在真实 MySQL / PolarDB 上验证**；goInception 解析很长的语句（上百个 `UNION ALL`）时如果失败，在 `query_check` 开启时会返回“数据脱敏异常，结果未返回”。

## 实例可以不绑定资源组（1.21）

- **以前**：新建 / 编辑实例时必须至少选一个资源组，否则报“请至少选择一个资源组（否则没有人能看到该实例）”。
- **现在**：可以一个都不选。实例先登记起来（只做慢日志采集 / 巡检，或还没想好给谁用），之后再关联资源组。添加时的确认框会说明“没有选择资源组”。
- **没有资源组的实例**：普通用户在在线查询、权限申请、SQL 上线、数据导出等页面里看不到它；超级用户与拥有“查询所有实例”权限的用户不受影响。SQL 上线 / 权限申请 / 数据导出的审批流跟着资源组走，必须关联资源组后才能用于这些流程。
- **不变**：选了的资源组 / 标签 ID 仍然校验必须存在。实例表单里没有“权限组”选项（权限组与实例之间没有绑定关系，权限靠资源组和查询权限），所以这里没有对应的限制。

## MySQL 系在线查询支持“前置 SET”：给 @变量 赋值后再查询（1.21）

- **以前**：脚本以 `SET @ShopId := 1008;` 或 `SET block_encryption_mode = …;` 开头，直接报“不支持的查询语法类型”。
- **现在**：开头连续的 `SET` 先在同一个只读会话里执行，再执行第一条查询。放行的只有 `SET @变量 := 表达式`（表达式可以带只读子查询）和 `block_encryption_mode` / `group_concat_max_len` / `div_precision_increment` / `time_zone` / `lc_time_names` 这几个会话参数；其它 `SET` 一律拒绝并指出是第几条。
- **页面**：运行“光标所在语句”时，脚本开头的 `SET` 自动随它一起提交；光标在某条开头的 `SET` 上时，运行“全部开头 SET + 紧随其后的第一条语句”；选中文本则原样提交。提示条里有说明。
- **数据与库的安全**：
  - 子查询按独立查询校验**库表权限**和 **SQL 防火墙**（表对象、扫描行数），不能把没权限的表读进变量再带出来；
  - **脱敏**把变量算进污染传播：`SET @p := (SELECT phone …); SELECT @p` 的结果列按 phone 的规则脱敏；同时修复了原来就存在的漏洞：`SELECT @v := phone, @v` 的第二列没有脱敏；
  - 赋值表达式里禁止 `sleep` / `benchmark` / `load_file` / `INTO` / `FOR UPDATE` / 写操作 / `mysql` 系统库（管理员同样不行，`max_execution_time` 管不到 `SET`）；
  - 前置语句与查询在同一个只读会话里，用过的连接丢弃，变量不会留给别人；写操作被数据库拒绝；
  - 查询日志（`dbt_query_log.sqllog`）和结果里的“实际执行的 SQL”都包含前置语句。
- **没变的**：每次仍只执行一条查询（`SET` 之后的第一条）；脚本里后面的 `INSERT` / `UPDATE` 等不会执行，也不会因为它们而整份被拒；导出工单仍然不接受 `SET`。
- **没有在真实 MySQL / PolarDB 上验证**：只有假后端与单元测试。升级后请先用只读账号在测试实例上试一下 `SET @a := (SELECT …)` 与脱敏结果。

## SQL Server 在线查询支持“只读批处理”，并补上字节上限（1.20）

- **以前**：只能执行一条以 `SELECT` / `WITH` 开头的语句，`DECLARE @ShopId INT = 1008; …` 这类脚本直接报“仅支持 SELECT / WITH 查询”。
- **现在**：`DECLARE @变量` / `SET @变量` 打头、最后用 `SELECT` 输出结果的批处理可以运行（`IF … THROW 50001, N'…', 1`、`STRING_AGG`、`CTE` 都行）。只返回第一个结果集；行数上限仍生效。
- **仍然禁止**：写入 / `EXEC` / `WHILE` / `WAITFOR` / `USE` / `OPENROWSET` / `SELECT INTO` / 游标 / 链接服务器，除变量外的 `SET`（如 `SET NOCOUNT ON`）。
- **新增禁止**（导出工单同样生效）：事务控制 `BEGIN TRAN` / `COMMIT` / `ROLLBACK`，`RAISERROR`，`NEXT VALUE FOR`，锁提示 `UPDLOCK` / `XLOCK` / `TABLOCKX` / `HOLDLOCK` / `SERIALIZABLE`（`NOLOCK` 不受影响），`THROW` 的参数必须是常量。
- **结果字节上限**：单元格默认 4 MiB（`dbt_sql_config.max_result_cell_bytes`，1.31 起为 `query.max_cell_bytes`），整个结果默认 32 MiB（`max_result_bytes`，1.31 起为 `query.max_result_bytes`）；超出时在结果提示里说明。导出工单不受这两个上限影响。
- **脱敏**：保守匹配修复了 `STRING_AGG(...) WITHIN GROUP (ORDER BY ...)` 和 `FORMAT(...)` 导致结果列漏脱敏的问题；变量（`DECLARE @k = (SELECT 敏感列 …)`、`SET @k = …`）会把污染传给后面输出的列。
- **注意**：这类脚本常把凭证字段拼进生成的 SQL；这些列一旦命中脱敏规则就会整格脱敏（规则取最严的），脚本的结果就不能直接拿去用——要么在不开脱敏的实例上跑，要么接受被脱敏。

## 慢日志采集改为默认开启（1.19，升级前先看）

**行为变化**：以前要在 `dbtool.env` 里设 `SLOWLOG_COLLECT_ENABLE=1` 并重启才会采集，只打开实例上的“慢日志采集”开关什么也采不到（旧系统不是这样，开关一开就采）。现在**采集器默认开启，只看实例上的开关**：

- 升级后，所有 `is_enable=1`（实例里“慢日志采集”已打开）、类型为 MySQL / PolarDB / PolarDB-X / SelectDB / Doris 的实例会开始读 `mysql.slow_log`（Doris / SelectDB 读审计日志），写入 `dbt_slow_logs`；Redis 实例勾了“启用”的同样开始采。**只读**，不会改目标库。
- 不想采：在 `dbtool.env` 里设 `SLOWLOG_COLLECT_ENABLE=0`（或 `false` / `no` / `off`）并重启；也可以在实例管理里关掉单个实例的开关（不用重启）。
- 参数没变：间隔 `SLOW_COLLECT_INTERVAL`（默认 10 秒，实例多时建议调到 60）、并发 `SLOW_COLLECT_WORKERS`（默认 2）、首次回溯 `SLOWLOG_COLLECT_BACKFILL_DAYS`（默认 7 天）。
- 采集的前提没变：目标库 `log_output` 含 `TABLE`、`slow_query_log=ON`、账号能读 `mysql.slow_log`；用 pt-query-digest 推送文件日志的，仍在“慢查日志”页选 `digest` 数据源。
- **SQL Server 等实例**在实例管理里能勾“慢日志采集”，但采集器不支持它们，不会采到任何数据。
- 要把旧库历史慢日志带过来：先 `dbt-migrate --include slow_logs` 再启动服务；启动之后才迁，最近 7 天的记录可能与已采集的重复。（`dbt-migrate` 1.31 起已移除，当前没有官方迁移工具。）

## 产品名去掉连字符：db-tool → dbtool，发布包命名与版本号（升级前先看）

> **注意**：下面的 `install.sh migrate-legacy`（旧名安装迁移）已在 1.31 移除，当前的 `install.sh` 没有这个子命令；旧名安装需要按“零、产品改名”和本节的对照表手工处理，或直接按全新部署重装。

名字里所有的 `-` 都去掉了：**程序、安装目录、配置目录、服务名、配置文件、发布包文件名**一起改，已部署的系统需要迁移（下面有一条命令的做法）。

|---|---|---|
| 发布包 | `db-tool-<版本>-linux-<arch>.run`、`db-tool-linux-<arch>.tar.gz`（不带版本号） | `dbtool-<版本>-linux-<arch>.tar.gz` + `.sha256`（都带版本号）；**部署用解压后的 `install.sh`，不再默认生成 `.run`**（需要时 `MAKE_RUN=1`） |

| 不变的 | `dbt_` 表前缀、运行用户 `dbtool`、`DBT_*` 与 `DB_TOOL_*` 环境变量名、元数据库里的全部数据与示例库名 `db_tool` | 同左——**旧配置文件里的内容原样可用** |

**把已部署的 db-tool 换成 dbtool**（元数据库里的数据不动；旧程序、旧配置、旧数据目录全程原样保留，任何一步失败都会自动把旧服务重新启动）：

```bash
# 1. 传 dbtool-<版本>-linux-amd64.tar.gz 与 .sha256 到服务器，校验、解压，先看计划（只读，什么都不改）
sha256sum -c dbtool-<版本>-linux-amd64.sha256

sudo ./install.sh migrate-legacy --dry-run
```

- 只升级版本、不换名字的老机器照常 `upgrade`；`dba-tool`（更早的名字）的旧安装不自动迁移，按 `install` 给出的提示手工处理。

## 数据脱敏：全引擎支持、新管理页、导出默认脱敏（升级前先看）

| 项 | 原来 | 现在 |
|---|---|---|
| 配置入口 | 没有页面，只能改库表 `dbt_data_masking_columns` | **系统管理 › 数据脱敏**（仅超级用户）：跨库跨表批量选字段 → 选规则 → 暂存 → 确认差异后保存，写系统审计 |
| 规则 | 三段式（规则 100）、正则 + 隐藏分组 | 新增**保留首尾**（前 N + `***` + 后 M，不泄露长度）与**整体隐藏**；旧规则原样继续生效 |
| 在线查询脱敏的引擎 | MySQL 系（goInception 语法树）；SelectDB / Doris、SQL Server 只按结果列名 | **MySQL 系、SQL Server、PostgreSQL、ClickHouse、MongoDB、SelectDB / Doris 全部支持**（Redis、ES 不适用）；精度见下 |
| PostgreSQL / MongoDB / ClickHouse | 查询结果完全不脱敏 | PostgreSQL 按结果列来源精确匹配；ClickHouse 保守匹配；MongoDB 按字段路径（含嵌套 / 数组 / 管道改名） |
| SQL 导出工单 | 不脱敏 | **默认脱敏**，开关 `dbt_sql_config.export_data_masking`（1.31 起为 `export.mask_enabled`；未配置 = 开；设为 `false` 关闭）；脱敏失败会**中止导出** |

- **升级动作**：执行新增的扩展表脚本 `deploy/sql/230_masking_policy.sql`（`install.sh upgrade` 会自动执行；手工：`dbt-admin bootstrap --only-sql --apply`）。表没建时在线查询仍按旧配置脱敏，新页面只能查看旧配置、不能保存。
- **原有配置不用重配**：迁移来的 `dbt_data_masking_columns` 照常生效，在新页面里标为“旧配置”；在页面里改它的规则 = 转存成新策略并停用旧配置，移除 = 删除旧配置。
- **行为变化（会让结果不同）**：
  - 导出工单里命中配置字段的列，文件里现在是脱敏后的值。**如果某些导出流程依赖原值（对账、迁移），先评估后再升级，或临时把 `export_data_masking` 设为 `false`**；系统脱敏总开关 `data_masking` 关闭时导出也不脱敏。
  - 脱敏总开关开着时，PostgreSQL / MongoDB / ClickHouse 结果上方不再显示“不做脱敏”提示（总开关关闭时仍显示）。
  - SelectDB / Doris、ClickHouse、以及 goInception 不可用 / SQL Server 无法分析结果集时用**保守匹配**：列名、别名或表达式引用了已配置的字段名就整列脱敏，会有少量误伤（宁多勿漏）。
- **没有验证的**：SQL Server 的结果列来源分析（`sys.dm_exec_describe_first_result_set`）、PostgreSQL 的表 OID 反查、ClickHouse / MongoDB 的真实服务端行为只用假后端验证过，没有对着真实实例跑过；上线前请在测试实例上各查一遍（含视图、别名、`concat(phone,'')` 这类表达式）。
- 页面使用说明与各引擎的定位方式见帮助 › 数据脱敏。

## SQL 防火墙（内核、在线查询 / 工单 / 导出接线、管理页与 EXPLAIN 扫描行数）

| 项 | 内容 |
|---|---|
| 新增表 | `dbt_firewall_rule` / `dbt_firewall_exception` / `dbt_firewall_hit`，脚本 `deploy/sql/240_firewall.sql`（可重复执行）。**不执行脚本 = 没有规则，行为与升级前完全一致** |
| 作用范围 | **在线查询**：MySQL 系、SQL Server、PostgreSQL、ClickHouse；**SQL 工单**（MySQL 系 / SQL Server，提交检查 + 执行前复核）；**数据导出**（提交检查 + 执行前逐实例复核）。MongoDB、Redis、线下手工执行的工单不接入 |
| 动作 | 拒绝 / 要求填写原因 / 限制返回行数 / 强制脱敏 / 仅告警；多条命中按“最严”合并，规则可先观察再生效 |
| 位置 | 语句检查之后、库表权限校验之前：被拒绝的语句不连目标库，记为“被拦截”（`firewall_denied`，403） |
| 规则怎么配 | **系统管理 › SQL 防火墙**（仅超级用户）：规则编辑器、历史回放、语句测试台、命中记录、例外名单、规则模板、全局模式与总开关；每次变更写系统审计。也可直接 `INSERT dbt_firewall_rule`；示例与应急开关见帮助 › SQL 防火墙 |

- **行为变化**：库表解析结果按 实例 + 库 + 语句 缓存 10 秒（防火墙与授权共用）。goInception 故障期间，刚解析过的语句 10 秒内仍可通过授权，没解析过的照常拒绝。
- **接口变化**：`POST /api/v1/query/execute` 新增可选字段 `reason`；新增响应码 `firewall_denied`（403）、`reason_required`（428）、`firewall_unavailable`（503，仅 `firewall_on_error=deny` 时）。外部脚本遇到 428 需要补 `reason` 重发。
- **新增配置项**（`dbt_sql_config`，都有缺省值）：`firewall_enabled`、`firewall_mode`、`firewall_on_error`、`firewall_store_sql`（1.31 起键名为 `firewall.enabled` / `firewall.mode` / `firewall.on_error` / `firewall.store_sql`，存 `dbt_setting`；全局模式的登记缺省是 `observe`）。
- 命中记录里的语句缺省只存**把字符串 / 数字字面量换成 `?` 之后**的形态；要存原文把 `firewall_store_sql` 设为 `raw`。
- **管理页要点**：新建规则缺省是观察模式；上线前可用最近 7 天的在线查询日志 / 工单语句**回放**；“观察 → 生效”“全局切到观察”“关闭总开关”会弹高危确认并记高危审计；例外必须写原因并有有效期（最长 1 年）；规则模板添加后都是观察模式。预估扫描行数条件取自目标实例的 EXPLAIN（见下）。
- **预估扫描行数（EXPLAIN）**：
  - 规则里的“预估扫描 ≥ N 行”现在真正生效：在线查询（MySQL 系 SELECT）、SQL 工单（MySQL 系 DML）、数据导出都会在目标实例上 `EXPLAIN`。口径是**要翻多少行**（连接按驱动表过滤后的行数放大），不是返回多少行。
  - **只在需要时才查**：条件按成本排序，前面的条件已经决定结果就不去 EXPLAIN；同一语句的多条规则共用一次。限时 `firewall_explain_timeout_ms`（缺省 3000 毫秒）、同一语句 10 秒缓存、每实例 4 路并发、实例连续 3 次超时 / 连不上就暂停 30 秒。
  - **取不到就是“未评估”，不拦**：超时、熔断、DDL、非 MySQL 格式的执行计划（PostgreSQL / SQL Server / ClickHouse / Doris / TiDB）、表不存在。
  - 在线查询里没有库表权限的语句**不会**被拿去 EXPLAIN，用户得到的仍是权限错误，探测不到表的大小。
  - 工单的“预估影响行数”：goInception 检查结果的值优先；没有 goInception（原生降级检查）时，UPDATE / DELETE 退回 EXPLAIN 的扫描行数（上界）。
  - 管理页：规则标“慢 · 平均 N 毫秒 / 未评估 N%”（只覆盖当前进程，重启清零）；概览下方汇总 EXPLAIN 的使用情况与熔断中的实例。
  - **行为变化**：规则里写了预估扫描行数条件的，升级后会在目标实例上多一次 EXPLAIN（有缓存与限时）。建议先放在观察模式，看“未评估 N%”再决定是否生效。
  - **性能修正**：此前每次求值 / 记录命中都会读 4 项 `dbt_sql_config`（各一次数据库查询），现在随规则快照缓存。
  - **没有验证的**：真实 MySQL 上的 EXPLAIN 输出解析只写了集成测试（`FIREWALL_IT_DSN`），本机没有跑过。
- **工单与导出（升级前先看）**：
  - 提交检查（点“检查”和“提交”都会）对检查结果的**每条语句**求值：拒绝 → 该行标红“驳回高危SQL（防火墙）”，随站点的“有错误是否自动驳回”处理；仅告警 → 该行标黄“SQL 防火墙提示”，**不会**被 `auto_review_wrong=1`（出现警告就驳回）驳回。`critical_ddl_regex` 仍然保留、先求值。
  - **执行前再复核一次，只认拒绝**：审批期间新增的规则会让工单进入“执行有异常”，一条语句也不执行；规则按**提交人**的用户 / 权限组 / 例外判断，换人点“执行”不能绕过。批量上线 / 批量导出按实例各自复核。
  - 数据导出：拒绝 → 检查不通过；限行与 `max_export_rows` 取小；强制脱敏的列在导出时整体隐藏（即使脱敏总开关没开），做不了就中止，不导出未脱敏的数据。
  - 要原因 / 限行 / 强制脱敏在工单场景没有对应能力，按“仅告警”处理并在提示里写明。
  - **行为变化**：规则的“预估影响行数”条件在工单提交检查里有值（来自 goInception 检查结果）；原生降级检查没有这个值，视为未知、不命中。
  - **修正**：脱敏总开关关闭、但防火墙对某列强制脱敏时，此前会把**已配置**的脱敏规则也一并应用；现在只隐藏被强制的列。
- **没有验证的**：管理页的存储层 SQL 没有在真实 MySQL 上跑过（只在假存储下验证）；首次使用请先在测试实例上执行 `240_firewall.sql` 并走一遍页面。使用说明与边界见帮助 › SQL 防火墙。

## 在线查询：MySQL 系查询改为数据库只读会话（升级前先看）

| 项 | 原来 | 现在 |
|---|---|---|
| MySQL / PolarDB 查询 | 只靠平台的语句检查 | 每次查询在服务端只读会话里执行（`SET SESSION TRANSACTION READ ONLY`），写操作被数据库拒绝（错误 1792） |
| 带写副作用的函数 | `SELECT f()` 若 `f` 会写表，词法检查看不出来，数据会被改 | 被数据库拒绝，记为“被拦截”（`readonly_violation`） |
| 不支持只读会话的服务端 | — | 自动降级为原来的行为，并在日志里对该地址警告一次（MySQL 5.6.5 之前、TiDB 默认、Doris / SelectDB / ADB） |

- **谁会受影响**：依赖“查询里调用会写数据的存储函数”的用法会失败，这类写入应改走 SQL 工单。普通查询、`SHOW`、`EXPLAIN` 不受影响。
- **登录页**：右上角的主题切换改成与内页顶栏一致的分段样式（明亮 / 深空 / 护眼），登录区占页面宽度的 35%。

## 取消只读视图限制（升级前先看）

| 项 | 原来 | 现在 |
|---|---|---|
| 带 `read_view` 标签的实例 | 在线查询、数据导出、数据字典、库表树都只能访问以 `v_` 开头的视图，对所有人（含管理员）生效 | **不再限制**：与普通实例一致，按库表权限访问全部对象 |
| 数据字典 | 只开放视图类别、不展示视图定义 | 全部对象类别，视图定义与定义者照常展示，导出含表与索引 |
| 数据归档 | 带该标签的实例不能做归档来源 | 与普通实例一致（仍只支持 MySQL / MariaDB 主库） |
| PostgreSQL / MongoDB / ClickHouse | 带该标签会被拒绝（`read_view_only`） | 不再拒绝，与 `can_read` 实例一致 |
| 标签本身 | 限制标签，同时放行“谁能查询 / 申请权限 / 导出” | **保留为 `can_read` 的旧同义标签**，只用来放行“谁能查询 / 申请权限 / 导出”，没有任何限制含义 |

- **原来只靠该标签限制的实例，现在可以按库表权限查询、导出、浏览全部对象**（含表和视图定义）。管理员需要继续收紧时，请改用库表权限控制：只授予具体表 / 视图的查询权限，不要授予库级权限；持有 `query.admin_run`（查询全部实例）或 `query.group_run`（资源组内实例）的人本来就不受库表授权限制，需要的话回收这两个权限。
- **数据不动**：不会删除或改写任何实例上已有的 `read_view` 标签，也没有迁移脚本。新建的库不再预置该标签（`dbt_sql_instance_tag` 的 3 号空缺，4、5 号不变），老库里已有的行照常识别。
- **接口**：`GET /api/v1/query/instances/:id/databases/:db/meta` 与 `GET /api/v1/dict/instances` 的响应不再带 `read_view` 字段，错误码 `read_view_only` 不再出现。

## 零、产品改名：dba-tool → db-tool（升级前先看）

| 项 | 原来 | 现在 |
|---|---|---|
| 安装目录 / 配置目录 | `/opt/dba-tool`、`/etc/dba-tool` | `/opt/db-tool`、`/etc/db-tool` |
| 服务名 / 配置文件 | `dba-tool.service`、`dba-tool.env`、`dba-tool.toml` | `db-tool.service`、`db-tool.env`、`db-tool.toml` |
| 主程序 / 安装包 | `dba-tool`、`dba-tool-<版本>-linux-<arch>.run` | `db-tool`、`db-tool-<版本>-linux-<arch>.run`（包内目录 `db-tool/`） |
| 环境变量 | `DBA_TOOL_CONFIG`、`DBA_TOOL_EXTRA_PERMISSIONS` | `DB_TOOL_CONFIG`、`DB_TOOL_EXTRA_PERMISSIONS` |
| 文档里的示例库名 | `dba_tool` | `db_tool`（只是示例，库名自己定，不影响程序） |
| 不变的 | `dbt_` 表前缀、`dbt-admin`、`dbt-migrate`（1.31 起已移除）、运行用户 `dbtool`、`DBT_*` 环境变量、MySQL 里的数据 | 同左 |

- **不兼容、不自动迁移**：新版 `install.sh` 发现旧的 `/etc/dba-tool`、`dba-tool.service` 或 `/opt/dba-tool` 时，没有新安装就**拒绝继续**并打印处理步骤（不动旧安装）；已有新安装时只提示。
- **处理步骤**（元数据库里的数据不受影响）：① 备份旧配置 `cp -a /etc/dba-tool /root/dba-tool-config.bak`（里面有 `SECRET_KEY` / `MIRAGE_*`，库里的密文靠它们解密）；② `systemctl disable --now dba-tool` 并删除旧单元；③ `./install.sh install --from-archery-env /root/dba-tool-config.bak/dba-tool.env --public-url …` 沿用旧连接串与密钥（`--from-archery-env` 1.31 起已移除：现在把旧配置里的连接串与密钥用 `--database-url` / `--secret-key` 与 `dbtool.env` 手工对应）；④ 需要的话把 `/opt/dba-tool/data` 拷到 `/opt/db-tool/data`；⑤ 确认后删除旧目录。
- **刻意没改名的内部标识**：归档文件加密密钥的派生前缀（`dba-tool/archive/file-key/v1`）与登录模块封装 / 指纹用的域分隔标签（`dba-tool/authx/…`）。它们是加密数据的一部分，改了会让已有的加密归档文件与库里已封装的密文无法解开。
- 外部引用要同步：nginx 配置里的 `dba-tool-proxy.inc`、sudoers 文件 `/etc/sudoers.d/dba-tool-goinception`（现在示例是 `db-tool-goinception`）、监控 / 备份脚本里的服务名与路径。

## 二、新增与变化的能力

- **独立部署**：`install.sh` 一键安装 / 升级 / 回滚 / 卸载 / 体检（`doctor`）/ 初始化库（`init-db`）/ 改配置（`reconfigure`）；`.run` 自解压包（默认不再生成，需要时 `MAKE_RUN=1`）；版本目录 + `current` 软链接，升级健康检查失败自动回滚；任何子命令都不会 `DROP` / `TRUNCATE` 数据库对象。
- **基础表自带**：`dbt-admin bootstrap` 用 `deploy/bootstrap` 里的基础表与基础数据初始化空库，不再依赖 Archery 代码（当时是 57 张表，1.31 起 48 张；`--schema-only` 已移除）。
- **迁移**（1.31 起已移除）：`dbt-migrate` 源端旧表名 → 目标端 `dbt_` 名，报告同时列“源表 → 目标表”，`--same-database` 显式开关，源库始终只读。
- **数据归档**、**保留策略清理**、**统一高危确认**、**多引擎在线查询（PostgreSQL / MongoDB / ClickHouse）**、**邮件通知渠道**等此前已完成的功能随本版本一起发布，说明见各自设计文档与 [ops-manual.md](ops-manual.md)（安装部署指南）。
- **分区维护并入外部程序**：
  - Doris / SelectDB 方言；命名与边界和原程序一致（周分区按窗口最后一天命名）；
  - 时区支持 IANA 名、`UTC+8` 写法，空值跟随目标库会话时区；
  - 未分区 MySQL 表的**显式**初始化（危险操作，键入 `库.表` 确认，定时维护永不触发）；
  - webhook 推送（slack / wecom / feishu / dingtalk）；
  - 运行输出日志：每次落盘的维护都有毫秒级步骤输出，页面可展开 / 筛选 / 搜索 / 复制 / 下载 `.log`，定时轮次摘要与推送测试也在平台可见。

## 三、已知限制

- `dbt_partman_log` 不在保留策略清理目标内，不会自动清理（需要时自行分批 `DELETE`，不要与清理任务同时处理同一张表）。
- Doris 不识别动态分区表；含 MAXVALUE 的表不处理；读不到上界的分区不会被删除。
- 外部写入方（pt-query-digest、自有脚本）改表名需要人工完成，平台无法替你检查。

## 四、没有验证的

- 真实 MySQL（5.7 / 8.0 / PolarDB）：加前缀后的基础表（含外键约束与 3 个截断的约束名）能否整体建出、同库共存无冲突、大表初始化分区的耗时与元数据锁（原“迁移映射”一项随 `dbt-migrate` 在 1.31 移除）。
- 真实 Doris / SelectDB：`SHOW PARTITIONS` 的实际文本、`ADD / DROP PARTITION` 的实际行为。
- 真实 webhook 平台：四类通道的返回与加签校验。
- 真实 systemd / root / firewalld / SELinux：安装脚本的测试使用假命令与临时目录。
- `scripts/smoke` 在改名后没有运行过（需要 Archery 的 Python 环境；该目录 1.31 起已移除）。
- 前端只在无头 Chrome + 假后端上验证过，没有与真实后端联调。

首次上线请先在演练库完整走一遍：建库 → `dbt-admin bootstrap`（先不带 `--apply` 演练）→ 页面配置 → 抽样验证，步骤见 [ops-manual.md](ops-manual.md) 第 8 章。（原写“备份 → 建库 → `bootstrap --schema-only` → `dbt-migrate`（先 dry-run）→ 对账 → 切换”，该迁移路径 1.31 起已移除。）
