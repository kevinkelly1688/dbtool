# 按钮级权限

权限管理细化到页面的按钮：**权限只有按钮这一套**。每个页面里的每个按钮都有一个独立的**权限码**，可以按权限组、按用户精确授予或禁用；页面能不能打开、按钮能不能点，都只看这里的授权（原来的“权限码”和“兼容 / 严格模式”已经取消，旧授权在升级时一次性迁移过来，见下文“从原权限码迁移”）。完整的码清单见附录 [权限码清单](#help/permcodes)，那一页与服务端的按钮登记表（`internal/btnperm/registry.go`）保持一致，登记表增删码时会同步更新。本章读者主要是管理员和需要排查“为什么看不到按钮”的人。

## 适用范围

按钮级权限覆盖全部页面，与实例类型无关。权限树按“模块 → 页面 → 按钮”组织：变更发布、数据服务、性能优化、性能治理、实例运维、访问控制、安全合规、平台设置八个模块（与侧栏分组一致）。

## 前提条件与所需权限

| 操作 | 需要的权限 |
|---|---|
| 查看权限组、给权限组勾选按钮、设置无权限按钮的显示方式 | 超级用户（`ag.view`、`ag.edit`、`ag.btnperm` 都是锁定码） |
| 给用户单独授权 / 禁用 | 超级用户（`ag.btnperm`） |
| 查看自己的权限概况 | 任何登录用户：头像菜单 › 个人信息与权限 |
| 迁移原权限码（升级时执行一次） | 服务器上的 root / 运维：`dbt-admin perm migrate`，需要元数据库连接（`install.sh upgrade` 会自动执行） |

## 三层结构

| 层 | 内容 |
|---|---|
| 页面 | 菜单是否显示、能否打开：持有该页面任一“查看类”按钮即可 |
| 按钮 | 页面里的每个按钮一个码，如 `sqlworkflow.execute_group`（立即执行（资源组内））；按钮授权存在表 `dbt_group_perm`（权限组）和 `dbt_user_perm`（单用户允许 / 禁止） |
| 数据范围 | 资源组 / 实例 / 库表授权，与按钮权限无关 |

按钮码分三类：

- **查看（v）**：显示菜单、打开页面、看数据；
- **操作（o）**：会产生副作用的日常操作；
- **高危（d）**：风险高的操作（执行、审批、终止、删除、授权、账号 / 参数管理、全部实例、审计、下载文件等），点击后必须二次确认（部分还要键入确认文本），授予它们时也会二次确认并写入系统审计，带 ⚠ 标记；
- 另外有两类**不进权限树**的按钮，只在权限树里各页面下方注明：
  - **仅超级用户**（锁定码）：服务端只认超级用户，不能授予权限组（访问控制、安全合规、平台设置里的大部分按钮、`sqlworkflow.skip_check`，数据导出的 `export.unmasked`，以及数据归档的 `archive.store_edit`、`archive.policy_edit`）；整页都是这类按钮的页面（如“用户”）在树里只显示页面名和“仅超管”；
  - **基础按钮**：对所有登录用户固定开放，不需要授权（终止自己的工单 `sqlworkflow.cancel_own`、查看 / 下载回滚语句 `sqlworkflow.rollback`、申请 / 撤回查询权限 `qpriv.apply`）；仍可以被对个别用户的“单独禁用”扣掉。

另有几个按钮标为“默认仅超级用户”（Binlog 回滚 / 下载、Binlog 清理、立即巡检 / 取消 / 删除报告、重置 Redis 慢日志、值班表的 `duty.view` / `duty.edit` / `duty.swap`），它们服务端已改为按钮校验，可以在权限组里显式授予。

## 权限组

权限组 = 按钮码的集合，同时是审批流里的“级”。用户可以属于多个权限组，**权限取并集**。内置预设：

| 权限组 | 定位 |
|---|---|
| DBA | 全部可授予按钮（含 Binlog 清理、性能巡检的立即巡检 / 取消 / 删除报告）；不含“仅自己的立即执行”（已有“资源组内立即执行”）、不含 Binlog 回滚 / 下载（需单独授予）、不含审计日志查看 / 导出、不含 Redis 慢日志重置，不含锁定码；可查看全部实例 |
| 组长 TL | 审批本组工单与查询权限、查看慢日志、受理性能工单、SQL 体检、分区维护只读；数据归档可查看、新建、试运行、暂停 / 恢复；**不能执行上线** |
| 研发 RD | 提交工单、立即执行自己的工单、在线查询、申请权限、导出提交、处理自己负责的性能工单；数据归档可查看、新建、试运行，分区维护只读 |
| 测试 QA | 提交工单、在线查询、提交与下载导出、查看回滚语句；数据归档只读；不能自行执行上线 |
| 审计 | 只读审计日志与全部工单、导出审计日志；数据归档只读（预设，不是内置权限组，需自行建组并套用） |
| Default | 新用户默认：在线查询，以及申请 / 查看查询权限（需另外申请库表权限才能真正查到数据） |

名称为 DBA / TL / RD / QA / Default 的权限组是**内置**的（带“内置”标签）：不能改名、不能删除，但可以调整它们的权限和说明。

在「权限组」里：

- **基本信息页签**：名称和说明（内置权限组不能改名）；新建时可以点“复制该组”，创建后会把来源组的按钮授权一并复制过去；
- **按钮权限页签**：按“模块 → 页面 → 按钮”勾选，高危按钮带 ⚠ 标记；可**套用预设**（DBA / TL / RD / QA / Default / 审计；预设只是起点，套用后仍可逐项调整，要保存才生效）、**预览页面效果**（按当前勾选显示这个页面上的按钮对该角色是什么样子）、保存前看**变更差异**并提示是否会让某级审批流无人可审（只提示不阻止）；页面级的“全选 / 仅查看 / 清空”和顶部的“仅查看类 / 全选可授予 / 清空”可以批量勾选；
- “默认仅超级用户”的按钮旁有提示，勾上才对这个组生效；
- 删除权限组前会检查是否被审批流引用或有待审批工单。

## 从原权限码迁移

早期版本的权限是“权限码”（`menu_*`、`sql_submit`、`sql_review` 等，存在 `dbt_auth_permission` 等表里）和按钮两套并存。现在只认按钮，升级时用 `dbt-admin perm migrate` **一次性**把原有授权展开成按钮授权：

- 规则（与升级前的判定一致）：一个权限组或用户持有某个权限码，就得到这个权限码放行的**所有**按钮（包括比权限码更细的，如 `sql_review` 对应的“审批通过”“驳回 / 终止他人工单”“修改可执行时间”）；迁移前后每个用户能用的按钮完全相同；
- 用户**单独**持有的权限码，写成这个用户的“单独授权”（原因写“迁移自原权限码”）；所在权限组已经覆盖的不重复写；用户已有的单独授权 / 禁用一律不动；
- 早期遗留、已经没有任何判断点的权限码（`menu_dashboard`、`menu_document`、`menu_sqlcheck`、`menu_sqlquery`、`menu_tools`、`menu_system`、`query_download` 等）没有对应按钮，迁移时丢弃，对任何人都没有影响；
- 只增不减、可重复执行，第二次执行没有任何新增；执行后在 `dbt_perm_setting` 里记下 `mode=strict`（“已迁移”的标记），服务最多 15 秒内生效，不需要重启；
- 先预览再执行：`dbt-admin perm migrate`（不加 `--apply` 只演练，列出每个权限组和用户迁移后新增的按钮、丢弃的权限码），确认后加 `--apply`；执行前会把“逐条撤销这次迁移”的 SQL 存成文件（`--rollback-file`，默认当前目录下 `perm-migrate-rollback-<时间>.sql`），只删这次新增的行；
- `install.sh install / upgrade` 会在**健康检查通过之后**自动执行一次（撤销脚本放在配置备份目录里）；输出实时显示，最多等 2 分钟，失败只警告，升级照常完成，但迁移完成前普通用户没有任何按钮权限（超级用户不受影响），请尽快修好后手工执行同一条命令；升级时不想执行就加 `--skip-perm-migrate`；
- 新装的库也走这一步：内置权限组（DBA / TL / RD / QA / Default）的初始授权以权限码的形式写在基础数据里，`install.sh install` 在健康检查通过之后把它们迁移成按钮授权。

迁移前，权限组页面顶部会有黄色提示“权限还没有迁移到按钮权限”。回滚到迁移前的老版本时，原来的权限码授权没有被改动，老版本照常工作；迁移之后在新版本里对权限组按钮做的修改不会带回老版本（老版本里按钮授权只是追加）。

> 提示：超级用户在任何时候都不受限，所以不会把管理员锁在外面。

## 单独授权与单独禁用

在用户页里对个别用户微调，而不必新建权限组：

- **单独授权**：在权限组之外额外给某个用户加某个码（如 rd_zhou 单独被授予 `export.download`）；
- **单独禁用**：从该用户的有效权限里扣掉某个码，**禁用优先于一切授权**；
- 两者都**必须写原因**（最多 200 字），可设**到期时间**（必须晚于当前时间，到期当天结束后自动失效），变更写入系统审计；
- 锁定码不能单独授权给非超级用户；超级用户本身无需单独授权 / 禁用；
- 保存单独授权 / 禁用、撤销时都会弹出确认框（页脚显示权限码 `ag.btnperm`），列出用户、按钮、到期和原因；授予高危按钮（⚠）时标红提示。撤销时：在用户详情抽屉里直接在确认框里填原因；在权限组页“按用户查看”里原因取自页面上方的“原因”框，要先填好。

## 有效权限

「按用户查看有效权限」把一个用户的全部码列出来，并标明**来源**：来自哪个权限组、单独授权，还是被单独禁用。排查“为什么看不到某个按钮”的第一步就是它；可按“仅允许 / 仅禁止 / 仅单独授权”筛选并看来源汇总，用户页里的“详情”抽屉也有同样的视图，并可直接单独授权 / 禁用。点右上角头像菜单里的“个人信息与权限”，也能看到自己的权限概况。

判定顺序（简化）：

1. 已停用用户 → 无权限；
2. 超级用户 → 全部通过；
3. 锁定码 → 只有超级用户；
4. 基础按钮（见上）→ 对所有登录用户开放（单独禁用仍然优先）；
5. 其余：所有权限组的并集 ∪ 单独授权，再减去单独禁用（**禁用优先于授权**）。

## 按钮的呈现

无权限的按钮默认**隐藏**；管理员可在“权限组”页顶部的“无权限按钮的显示方式”里把“无权限的按钮”改为**置灰**并带 🔒，悬停显示需要的权限名和码。无论界面如何呈现，**服务端对每个接口再校验一次**，绕过前端并不能越权；高危按钮的使用还会写入审计。

## 字段与选项说明

| 设置 | 取值 | 默认 | 说明 |
|---|---|---|---|
| 无权限的按钮 | 隐藏 / 置灰 | 隐藏 | 只影响呈现，服务端始终校验 |
| 单独授权 / 禁用的原因 | 必填，≤ 200 字 | — | 写入系统审计 |
| 单独授权 / 禁用的到期时间 | 可空 | 不过期 | 必须晚于当前时间 |

## 审计与安全说明

- 修改权限组按钮、修改显示方式、单独授权 / 禁用 / 撤销、权限迁移都写系统审计（动作名如“修改按钮权限”“修改按钮权限设置”“迁移原权限到按钮权限（全部）”“撤销按钮单独授权/禁用”，权限码 `ag.btnperm`）；
- 权限生效有约 15 秒的缓存：修改后其他用户最长约 15 秒生效；
- 服务端每个接口都校验按钮权限，前端隐藏或置灰只是体验层；
- 授予高危按钮会二次确认。

## 常见问题

| 现象 | 可能原因 | 处理 |
|---|---|---|
| 权限组页面顶部提示“权限还没有迁移到按钮权限” | 升级时的 `dbt-admin perm migrate` 没执行成功（此时普通用户没有任何按钮权限，超级用户不受影响） | 在服务器上执行 `dbt-admin perm migrate` 预览，再加 `--apply` |
| 升级时卡在“权限迁移”一步（1.79 的问题，1.80 已修复） | 旧版 `dbt-admin` 的迁移命令在只开一个数据库连接的结构上死等 | Ctrl+C 即可（迁移在一个事务里写入，卡住时什么都没写）；必要时 `pkill -f 'dbt-admin perm migrate'`；换 1.80 以上的包升级，或加 `--skip-perm-migrate` 跳过后手工迁移 |
| 给用户单独授权提示“仅限超级用户，不能授予” | 该码是锁定码 | 只能由超级用户使用 |
| 用户有权限组授予，按钮仍不可用 | 对该用户存在单独禁用，或权限已被缓存 | 在“按用户查看有效权限”里看来源；等待约 15 秒 |
| “终止自己的工单”这类基础按钮用不了 | 对该用户存在单独禁用，或用户已被停用 | 在“按用户查看有效权限”里看来源；基础按钮不需要授权 |
