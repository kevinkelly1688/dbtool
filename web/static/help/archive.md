# 数据归档

数据归档把表里“过期”的数据按计划搬走或清掉，取代手写的 `pt-archiver` 与定时 `DELETE` 脚本。系统按主键分批、小事务、限速、先做负载自检，先把数据备份到目标并校验，通过后才删除源表数据，任何一步失败都不会删。审批流里的“数据归档申请”就是本功能的审批。菜单：数据服务 › 数据归档。

## 1. 功能概述

本功能只执行三类 SQL，任务详情的“将执行的 SQL”里全部可见：

- 读：不用 `OFFSET`。**归档并删除、仅清理**不排序、没有断点，每批只取“当前符合条件的前 N 行”（`... WHERE 条件 LIMIT N`），备份校验并删除之后，下一批自然取到剩下的；**仅备份**不删数据，按主键升序、用“主键 > 上一批最大主键”翻页。
- 写目标：`INSERT` 到归档库表；文件备份按所选格式追加写入，运行结束生成清单并回读校验。
- 删源：`DELETE ... WHERE 主键 IN (...)`，仅在备份并校验通过后执行，并重复一遍归档条件，避免删到期间被改过的行。

没有自由 SQL 入口。

| 页签 | 谁能看 | 内容 |
|---|---|---|
| 归档任务 | 持有 `archive.view` | 任务列表、“待我审批”、运行中的实时进度、任务详情（配置、将执行的 SQL、审批进度、最近运行、变更历史） |
| 运行记录 | 持有 `archive.view` | 每次运行一行（定时、手动、试运行、恢复），详情里有吞吐曲线、限流事件、校验结果、备份位置、日志 |

## 2. 适用范围

| 角色 | 条件 |
|---|---|
| 归档来源 | 类型为 `mysql`、`mariadb`、`polardb` 或 `polardb-x`（别名 `polardbx` 同样接受）、角色为主库（`master`）、已启用、你可用的实例。Doris、SelectDB、ADB、PostgreSQL、SQL Server、Redis 等一律拒绝，提示“目前只支持 MySQL / MariaDB / PolarDB / PolarDB-X” |
| 库表备份目标 | 同样须是上述类型的主库，可与源同实例或另一实例；不要求与来源是同一类型 |
| 文件备份存储 | 本地目录、NFS 挂载目录、S3 兼容（含 MinIO）、阿里云 OSS（通过其 S3 兼容端点） |
| 复制延迟探测 | 从库须在平台登记为启用的从库（角色 `slave`，类型在上述范围内，不要求与源库同类型），地址与源库上 `Binlog Dump` 连接来源一致（登记主机名的解析后比较）。PolarDB-X 不一定能读到复制状态，这时试运行与运行里标“未检测”（黄色），不阻止运行 |
| PolarDB-X 说明 | 它是 MySQL 协议的兼容实现，只有 `polardb-x` 类型走降级：设不上会话锁等待参数时忽略（锁等待超时取实例默认值）、读不到 `sql_log_bin` 时放行（读到值不是 1 仍拒绝运行）。另外，所有类型读列与索引时都是先查 `information_schema`、失败再退到 `SHOW COLUMNS` / `SHOW INDEX`。库表备份的建表语句会去掉 `dbpartition` / `tbpartition` / `BROADCAST` / `SINGLE` / `LOCALITY` 等拆分子句（备份表不拆分）。**正式启用前请先用试运行在真实实例上确认** |
| PolarDB 说明 | 与 MySQL 走同一条严格路径，没有降级 |

实例表单里没有 MariaDB 选项，MariaDB 服务端按 `mysql` 类型登记。任务按资源组可见：你只能看到自己所在资源组的任务（超级用户或持有 `query.admin_run` 的管理员看全部）。

## 4. 操作指南

### 4.1 新建归档任务

目标：登记一个按计划运行的归档任务。入口：数据归档 › 归档任务 › 新建归档任务（`archive.apply`）。向导按六步填写，每一步下一步前都会校验，错误直接列在表单下方。向导可“保存草稿”，草稿可继续编辑、提交或删除。

#### 第 1 步：来源

- 任务名称：2–50 字，全局唯一。
- 实例、库、表：只能选 MySQL / MariaDB / PolarDB / PolarDB-X 的主库；实例还受其显示 / 隐藏库规则过滤；库表列表最多 3000 张表。
- 所属资源组：决定走哪条审批流。资源组没有配置“数据归档申请”审批流就不能提交，请联系管理员在“审批流程”里配置。
- 不允许的表：没有主键（含唯一非空键）的表、受保护库表（安全策略里配置，默认含 `mysql`、`information_schema`、`performance_schema`、`sys`）、被外键子表引用的表、没有可作时间列的表（既没有 `datetime`、`timestamp`、`date` 列，也没有存着 10 位秒 / 13 位毫秒 Unix 时间戳的 `int` / `bigint` 列）。
- 同一张表同时只能有一个进行中的任务（待审批、已启用、已暂停都算），提交审批时检查。
- 编辑已有任务时页面锁定实例、库、表；换来源请新建任务（服务端更改来源属于关键字段，需要重新试运行与审批，并清空断点）。

#### 第 2 步：条件

条件是结构化的，不是手写 SQL：

- 时间列：下拉里先列 `date` / `datetime` / `timestamp` 列，再列 `int` / `bigint` 列（名字像时间的排前面，下拉里标“整型”）；该列必须有索引，表较大时否则试运行判红（避免全表扫描拖垮线上）。
- 时间单位（只在选了整型列时出现）：很多业务库用 `bigint` 存 Unix 时间戳——**10 位是秒，13 位是毫秒**，选哪个必须和列里的实际数据一致。选好列后系统会抽样读取该列（只读，抽样 1000 行；列上有索引或表很小时再取最早 / 最晚值），按位数自动预填单位，并显示“最早 … 最晚 …”换算出的时间供你核对（服务器时区）；预填不对可以手动改。系统会按所选单位把“N 天前”换成同一单位的时间戳再比较（见下面的 WHERE 示例）。
  - **选错的后果**：把 10 位秒当成毫秒，条件会变成“全表都早于 N 天前”，整张表都命中。为此有三道防线：向导里抽样发现与所选单位不符会直接标红；试运行里“时间单位”一项判红，不再统计命中行数；运行中每批读到数据后，如果这一批的时间值整批都小于所选单位的合理下限（1980 年），立刻停止并自动暂停任务，此时还没有备份、没有删除任何数据。
  - **值为 0 / NULL 的行**视为“未设置”，永远不会被归档（条件里带 `> 0`）。例如通知表的“已读时间”用 0 表示未读：不要拿它当时间列；只想清理已读数据，把时间列选“创建时间”，附加条件写 `ReadTime > 0`。
  - 只支持 `int` / `bigint`（含 `unsigned`）。存在 `varchar` / `decimal` 里的时间戳、`20260101` 这样的整数日期、微秒 / 纳秒时间戳目前不支持。
  - 修改任务的时间列或时间单位都属于关键字段：需要重新试运行、重新审批，并清空旧断点。
- 保留天数：只归档“时间列早于 N 天前”的数据。不得小于安全策略的最小保留天数（默认 30，页面上标在字段名后），最大 3650；想放宽要由管理员改安全策略。
- 附加条件（可选，至多 500 字）：只允许比较（含 `<=>`）、`IN`（至多 200 项）、`LIKE`、`BETWEEN`、`IS [NOT] NULL / TRUE / FALSE`、`NOT`、`AND`、`OR` 和括号。禁止分号、注释、子查询、函数调用、算术、十六进制字面量、反斜杠、`库.列` 限定名，以及 `SLEEP`、`BENCHMARK`、`INTO OUTFILE`、`UNION`、DDL、DML 关键字；引用的列必须是这张表里的列。

系统生成最终的 WHERE，例如：

```sql
`created_at` < NOW() - INTERVAL 180 DAY AND (`status` IN (3, 4))
```

时间列是 13 位毫秒 / 10 位秒的整型列时，条件是（保留 180 天 = 15552000 秒）：

```sql
-- 13 位毫秒
`CreateTime` > 0 AND `CreateTime` < (UNIX_TIMESTAMP() - 15552000) * 1000 AND (`status` IN (3, 4))
-- 10 位秒
`CreateTime` > 0 AND `CreateTime` < UNIX_TIMESTAMP() - 15552000 AND (`status` IN (3, 4))
```

比较的右边是常量、列上不套函数，所以时间列上的索引照常可用；`UNIX_TIMESTAMP()` 与会话时区无关。

附加条件永远带括号（不只是含 `OR` 时），避免和保留天数条件的优先级混淆。最终 WHERE 由服务端生成并校验，页面上的预览与校验提示仅供参考，以服务端结果为准。

#### 第 3 步：模式与备份

| 模式 | 做什么 | 什么时候用 |
|---|---|---|
| 归档并删除 | 备份到目标并校验通过后，才删除源表数据 | 最常用 |
| 仅备份 | 只拷贝，不删除源表 | 先观察一段时间，确认条件、速度、备份都没问题 |
| 仅清理 | 不备份，直接删除 | 日志类临时表；默认不允许，见下 |

备份去向可多选，也可以两个都选：

- 归档库表：同实例或其他实例，库名加表名模板（`{table}`、`{yyyy}`、`{mm}`、`{dd}`、`{yyyymm}`、`{yyyymmdd}`，如 `{table}_{yyyy}`）。目标表不存在时用源表的建表语句改写为 `CREATE TABLE IF NOT EXISTS`（去掉 `AUTO_INCREMENT` 起点、分区定义、外键行，以及 PolarDB-X 的 `dbpartition` / `tbpartition` / `BROADCAST` / `SINGLE` / `LOCALITY` 子句）自动创建；目标库不存在不会自动建库（试运行判红）。读不到源表建表语句时试运行不会提前发现，运行时报“缺少源表的建表语句，无法创建目标表”。已存在时要求结构兼容：源表每列在目标有同名同类型列（忽略大小写与 int 显示宽度）且主键列一致，目标可有多余列。
- 文件存储：选一个已配置的“备份存储”（连接异常的存储可以选，但试运行判红、运行会被拒绝），格式 CSV 或 SQL，可 gzip 压缩、可 AES-256-GCM 加密（密钥由系统保管，页面不展示，加密后的文件由 DBA 解密）。路径模板可用 `{inst}`、`{db}`、`{table}`、`{yyyy}`、`{mm}`、`{dd}`、`{yyyymm}`、`{yyyymmdd}`、`{run_id}`、`{task_id}`，至多 128 字，不能以 `/` 开头，不含 `..`，拼在存储前缀之后、扩展名由系统追加；单个文件超过上限（默认 256 MB，可填 1–4096 MB）会自动滚动成新文件；运行结束生成清单并回读校验大小与 sha256。

仅清理要同时满足：安全策略里“允许不备份清理”是开启的（默认关闭，仅超级用户能打开）；任务里写明“不备份理由”（5–500 字，审批人审批时会看到）。“不备份”与备份去向互斥：要不备份只能选这个模式，另两个模式至少要选一个备份去向。

> 警告：仅清理删除后无法恢复，只适用于确认没有保留价值的日志类临时表。

#### 第 4 步：稳定性参数

| 参数 | 默认 | 范围与说明 |
|---|---|---|
| 批大小 | 1000 行 | 100–10000；每批取一批行（归档并删除 / 仅清理：当前符合条件的前 N 行，不排序；仅备份：按主键升序、`主键 > 上一批最大值`；都不用 `OFFSET`），每批一个独立的小事务 |
| 批间休眠 | 200 ms | 会删除数据的模式（归档并删除、仅清理）50–5000 ms；仅备份 1–5000 ms。不能填 0：系统把 0 当作“使用安全策略默认值”，不是不休眠 |
| `Threads_running` 阈值 | 32 | 4–1000；每批开始前检查，超限就暂停等待 |
| 复制延迟阈值 | 5 秒 | 1–3600；检查不能关闭（只能调阈值）。没有从库时自动跳过；有从库但测不到延迟（从库没在平台登记、连不上）时标“未检测”，试运行为黄色，不当作通过 |
| 磁盘剩余阈值 | 15 % | 5–50；取不到时标“未检测”，不当作通过（见 5.2） |
| 最长等待 | 10 分钟 | 向导里 1–60 分钟；负载超限后每 30 秒复查，超过则本次以“负载中断”结束，不算失败 |
| 批耗时目标 | 500 ms | 100–5000；某批超过目标：批量减半（下限为 100 与设定批量中较小者）、休眠加倍（上限 5000 ms）；连续 5 批正常再逐步恢复 |
| 连续失败暂停 | 3 批 | 1–10；死锁或锁等待超时按 200、400、800 ms 退避重试 3 次，仍失败该批回滚并计 1 次失败；连续失败 N 批自动暂停任务并通知 |
| 单次运行最多处理 | 5,000,000 行 | 至少 100；超过安全策略上限时实际按上限截断（试运行给黄色提示）；达到上限的运行以“已达上限”结束，下次接着跑 |

锁等待超时（`lock_wait_timeout` 与 `innodb_lock_wait_timeout`）默认固定 3 秒，API 可设 1–60 秒，向导不暴露。

#### 第 5 步：调度

- 调度方式：每天、每周（选星期）、每月（选 1–28 日，避开月末天数差异）加开始时间，或高级 cron（5 段：分 时 日 月 周，支持 `*`、`,`、`-`、`/`，周 0–7（7 为周日），最短间隔 1 小时，如 `30 1 * * 0` 表示每周日 01:30）。页面预览未来 5 次触发时间，并标出落在窗口外会被跳过的。
- 时区：调度与窗口按服务进程所在时区计算。
- 执行窗口：开始到结束时间，至少 30 分钟，可跨零点（开始与结束相同表示不限制；都不填时缺省 01:00–05:00）。窗口为半开区间 [开始, 结束)。只在窗口内运行；窗口结束时当前批做完后优雅停止，记录断点（最大主键），下次接着跑。
- 开始时间必须落在窗口内，否则任务永远不会被调度；到点但已错过窗口时静默推进下一次，不记运行记录。

#### 第 6 步：试运行并提交

见 4.2。提交后任务进入待审批，通过最后一级后自动变为已启用。

### 4.2 试运行

提交前必须先“试运行”（`archive.dryrun`）。试运行只读，不写不删，给出：

- 预估命中行数、占表比例、预计批数、预计耗时、预计 binlog 体积（命中行数的统计有上限，超过上限会标注“至少”）。
- 最前 10 行样例（`SELECT … WHERE (条件) LIMIT 10`，无排序；单值截 200 字）。
- 将执行的 SQL（填入示例参数）。
- 检查项，每项绿、黄、红，见 5.1。

提交规则：

- 红色项不能提交，回到对应步骤修改后重新试运行。
- 黄色项需要勾选“我已知晓”。
- 预估命中超过表总行数 30% 属于大批量，需要额外勾选“已确认大批量”。
- 试运行结果 7 天内有效；资源组、实例、库表、时间列、保留天数、附加条件、模式、不备份理由、备份去向（含压缩、加密、格式、路径模板、单文件大小）和单次总量上限任一改动后立即失效，需重新试运行。调度、窗口与其他限速参数不影响。

### 4.3 审批

- 新建、修改关键字段、重新提交被驳回或已停用的任务，都走资源组审批流里的“数据归档申请”。
- 审批人 = 该级权限组中、属于该资源组的用户；不能审批自己提的申请（超级用户也不例外）；该级没有其他可审批人时，只有超级用户能审。
- 审批人在任务详情（或列表行）里点“通过 / 驳回”；驳回必须填写原因（至少 2 字）并通知申请人，申请人修改后可重新提交。
- 通过最后一级后任务自动已启用，按调度运行；侧栏“数据归档”的红色角标是“等我审批”的数量。

关键字段（修改后需重新审批）：资源组、实例 / 库 / 表、时间列、保留天数、附加条件、模式、不备份理由、备份去向；总量上限单独处理：提高才需审批，降低不需要。调度（方式、时间、cron）与名称修改永不需要审批。修改限速参数不需要重新审批，但只能更保守；放宽要重新审批：批量只减不增、休眠只增不减、窗口只缩不扩、总量只降不升，另外 `Threads_running` 阈值提高、复制延迟阈值放宽、磁盘剩余阈值降低、批耗时目标放宽、最长等待延长、连续失败暂停阈值提高也算放宽。

### 4.4 运行与控制

- 立即执行（`archive.run`，高危）：仅已启用的任务；不等调度，仍遵守负载保护，可勾选“忽略执行窗口”，未勾选而当前在窗口外时会被拒绝并说明原因。前置检查同调度：保留天数不低于策略下限、策略仍允许仅清理、非受保护库表、备份存储未删除未停用且状态不是异常、实例可用、没有冲突的 SQL 上线工单；被拒绝时返回“已跳过”并写审计。
- 暂停 / 继续（`archive.pause`）：运行中点暂停，当前批做完后停，可继续；空闲的任务点暂停则不再按调度运行，恢复后接着跑（归档并删除、仅清理接着取剩下的行；仅备份从断点继续）。
- 终止（`archive.stop`，高危）：当前批做完后结束，本次运行标记“已终止”，已处理的部分不会回滚，下次运行接着处理剩下的。
- 运行中任务在列表里显示进度条、速度、预计剩余、是否正被限流（页面每 2 秒刷新一次）；详情里还有 `Threads_running` 与复制延迟仪表、当前批大小和设定休眠（自适应后的当前休眠不上报，显示设定值）。
- 同一实例同时最多 2 个归档运行（安全策略可调）；任务上一次还没结束就到点，本次跳过并记录；源表有待执行或执行中的 SQL 上线工单时，本次也会跳过（按工单 SQL 文本里出现源表名判定）。
- 运行中的暂停与终止只能在启动该运行的服务进程里操作；编辑、暂停、停用、删除任务会检查数据库里是否有租约未过期的运行（别的进程在跑也会被拦）。

### 4.5 恢复数据

仅库表备份，权限码 `archive.restore`（高危）。在运行记录详情里点“恢复数据”，输入任务名确认后，按该次运行的主键范围用 `INSERT IGNORE` 把数据回灌到源表，只补缺、不覆盖；恢复本身也会生成一条运行记录，回灌同样会产生 binlog，注意从库延迟。文件备份在详情里显示文件清单（行数、大小、sha256）并可“下载清单”，恢复靠 DBA 手工导入（用清单核对 sha256）。

### 4.6 停用与删除

停用（`archive.delete`）可用于已启用、已暂停、待审批的任务（进行中的审批作废）；删除只限草稿、已驳回、已停用的任务，需输入任务名确认。运行中的任务不能编辑、停用或删除。停用后不再调度，运行记录与已备份的数据保留。

### 4.7 管理备份存储（管理员）

“备份存储”页签列出可用的存储。新建、编辑、测试、启停、删除都需要 `archive.store_edit`（仅超级用户）。

| 字段 | 说明 |
|---|---|
| 名称 | 2–50 字，不能重名 |
| 类型 | 本地目录、NFS、S3 兼容（含 MinIO）、阿里云 OSS |
| 地址、桶 | S3 与 OSS 需要 `http(s)://` endpoint 与桶 |
| 路径前缀 | 至多 200 字；拼在路径模板之前，不得含 `..` |
| AK / SK | 加密保存、永不回显，编辑时留空表示不修改 |
| 保留天数 | 0 为永久，最大 36500；只有管理员打开数据清理任务和 `retention.archive_backup_enabled` 后才会真正删除过期的备份文件，默认不执行，库表备份不受影响 |
| 状态 | 正常、异常、停用 |

- 本地目录写绝对路径，不含 `..`；NFS 写已挂载的目录（系统不负责挂载，“测试连接”不会替你创建目录，Linux 上还会检查目录确实落在挂载点上）；本地目录类型则会自动创建。
- 路径风格访问：MinIO 通常需要勾选。已被任务引用的存储不能修改类型。
- “测试连接”会写入、读取、删除一个探测对象，结果分成功、失败、超时（30 秒）；连接异常的存储状态显示“异常”，引用它的任务运行会被拒绝（先备份后删除的前提不成立）。
- 被任务引用的存储不能删除；可以先停用（停用会提示受影响的任务数）。

### 4.8 配置安全策略（管理员）

“安全策略”页签是全局硬约束，会直接影响向导里的校验。仅超级用户可改（`archive.policy_edit`），其他有查看权限的用户只能看。保存前先看差异预览（含放宽风险提示），再二次确认，每次修改写入系统审计。

| 项 | 默认 | 范围 |
|---|---|---|
| 最小保留天数 | 30 | 1–3650 |
| 允许不备份清理 | 否 | 仅超级用户能打开 |
| 受保护库表 | `mysql`、`information_schema`、`performance_schema`、`sys` | 每行一个：库名，或 `库.表`，支持 `*`、`?`；字符集 `[A-Za-z0-9_$.*?-]`，至多 128 字，不区分大小写；4 个系统库永远并入名单，不可移除 |
| 单次最大行数 | 5,000,000 | 1,000–2,000,000,000 |
| 每实例最大并发 | 2 | 1–10 |
| 默认批大小、休眠、阈值 | 同 4.1 第 4 步 | 休眠 50–5000 ms，其余同上 |

固定约束（不可调）：附加条件至多 500 字且只允许比较、`IN`、`LIKE`、`BETWEEN`、`AND`、`OR`、`IS NULL` 等；批大小 100–10000；归档并删除与仅清理的批间休眠不小于 50 ms；执行窗口不小于 30 分钟；cron 最短间隔 60 分钟；binlog 保持开启、不提供关闭选项（会话 `sql_log_bin` 不为 1 时直接拒绝运行）。

已有任务不会被立即改动，但下次编辑或运行时按新策略校验（例如保留天数低于新下限的任务运行会被拒绝）。

### 5.2 复制延迟与磁盘剩余的数据来源

- 复制延迟的从库是自动发现的：看源库上正在拉 binlog 的连接来源，对应平台里登记的从库实例（地址相同；登记的是主机名则解析后比较）。从库没有在平台登记、经 NAT 或代理对不上地址、账号没有 `PROCESS` 权限看不到连接时，只能标“未检测”；请把从库登记到“实例管理”里。
- 运行时每批前（结果缓存 30 秒）检查：源库磁盘、目标库磁盘（有库表去向时）、文件存储可用空间（须不小于 2 倍单文件上限，不足即限流）。磁盘剩余取自该实例最近一次（48 小时内）的 MySQL 巡检结果，目前巡检不采集磁盘剩余，所以这一项现在显示“未检测”（黄色），这是已知限制，不影响提交（勾选“我已知晓”）。

### 5.3 稳定性保护一览

| 保护 | 说明 |
|---|---|
| 分批与短事务 | 按主键分批，默认 1000 行一批，每批独立小事务，不用 `OFFSET` |
| 负载自检 | 每批前依次检查暂停 / 终止、窗口、行数上限、负载（`Threads_running`、复制延迟、磁盘剩余）、结构指纹；超限暂停并计入“限流事件” |
| 自适应降速 | 批耗时超目标则批量减半、休眠加倍，连续 5 批正常再恢复 |
| 锁与重试 | 会话锁等待超时默认 3 秒；死锁与锁等待指数退避重试 3 次；连续失败自动暂停 |
| 总量上限 | 单次运行最多处理 N 行；命中超过表的 30% 需额外确认 |
| 执行窗口与互斥 | 只在窗口内运行；同实例并发有上限；上一次未结束则跳过 |
| 结构指纹 | 源表列名、类型、主键与审批时不一致，任务暂停并通知，需重新试运行并走审批 |
| 随时叫停 | 暂停与终止（当前批做完后生效） |
| binlog | 保持开启（从库、备份依赖它），不提供关闭选项；大批量删除会产生大量 binlog，注意从库延迟与磁盘 |
| 会话固定 | `sql_mode=STRICT_TRANS_TABLES,NO_AUTO_VALUE_ON_ZERO`，`time_zone` 对齐源库偏移 |

### 5.4 备份去向怎么选

| 场景 | 建议 |
|---|---|
| 以后还可能要查、要回灌 | 归档库表（同实例的归档库最省事；数据量很大时放到独立的归档实例），库表备份可以直接在页面“恢复数据” |
| 只为合规留档、很少再用 | 文件存储（CSV 加 gzip），放对象存储（OSS / MinIO）或 NFS，成本低；敏感数据勾选加密 |
| 特别重要的表 | 两个都选：库表方便恢复，文件方便离线留档 |
| 日志类临时表、确认没有保留价值 | 模式选仅清理，需策略放开并写明理由 |
| 不确定条件对不对 | 先选仅备份跑几次，确认后再改成归档并删除（改模式属于关键字段，要重新审批） |

### 5.5 备份写入格式

- 库表备份：`INSERT`；主键已存在且内容一致计“已存在”，不一致即校验失败（源数据不删）。
- CSV：首行列名，NULL 为 `\N`，空串为 `""`，二进制为 `0x…`。
- SQL：每条至多 200 行的多行 `INSERT`，表名用源表名。
- gzip：每批一个成员；文件名形如 `part-0001.csv[.gz][.enc]`，另有清单文件；每个文件上传后回读校验大小与 sha256，上传失败重试 3 次。

### 5.6 任务状态与运行结果

| 任务状态 | 说明 |
|---|---|
| 草稿 | 向导“保存草稿”，可继续编辑、提交或删除 |
| 待审批 | 已提交，等待审批流逐级通过；列表里显示当前在哪一级、等谁 |
| 已驳回 | 被某一级驳回，原因在详情里；修改后点“编辑 / 重新提交” |
| 已启用 | 按调度运行 |
| 已暂停 | 人工暂停，或自动暂停（连续失败、校验失败、从库延迟等，原因在详情里）；结构变更暂停需重新试运行并走审批，不能直接恢复 |
| 已停用 | 不再调度；运行记录与已备份的数据保留 |

| 运行结果 | 含义 |
|---|---|
| 成功 | 符合条件的数据全部处理完，校验通过 |
| 窗口结束中断 | 执行窗口结束，当前批做完后优雅停止，下次接着跑 |
| 负载中断 | 负载超限且等待超过最长等待；不算失败，下次接着跑 |
| 已达上限 | 达到单次运行最大行数，下次接着跑 |
| 失败 | 目标写入或删除出错，失败批已回滚，源数据未被删除 |
| 校验失败 | 目标端与读到的数据不一致，已停止，该批源数据未删除，任务自动暂停 |
| 已终止 | 人工终止 |
| 结构变更暂停 | 源表结构指纹变化，本次未执行 |
| 已跳过 | 到点时上一次运行未结束、源表有未结束的 SQL 上线工单等，本次没有执行 |
| 中断 | 服务进程重启等原因导致运行中断，下次接着跑（归档并删除、仅清理接着取剩下的行；仅备份从断点继续） |

读取与断点：
- **归档并删除、仅清理**不排序、没有断点：删掉的行不会再被读到，所以窗口结束、达上限、负载中断、终止、重启之后，下一次运行直接接着取剩下的行；升级前遗留的旧断点会被忽略并清掉。
- 这两种模式要记下本次处理过的最小 / 最大主键（恢复数据时按它从备份表补回），因此要求主键各列都能在程序里比大小：整数、小数、日期时间类可以；**主键含字符串、浮点、二进制等列的表仍按主键排序读取并保存断点**（字符串的大小受排序规则影响，本地比不准，宁可用老办法也不让恢复范围出错）。这类表成功跑完会清空断点（下次从头），窗口结束、达上限、负载中断、终止保留断点。
- **仅备份**始终按主键翻页并保存断点，成功后断点保留。
- 空转与过慢保护：不排序读取没有断点可以“越过”卡住的行，所以读到行却一行也没删掉时立即停止并自动暂停任务；每批读取连续 3 次超过 15 秒（清理落后、有长事务或执行计划变了）也会停止并自动暂停。

运行详情包含：批次吞吐曲线（折线为行 / 秒，虚线为当前批大小，红色带是被限流暂停的时段）、限流事件、校验结果、备份位置与 sha256、错误信息和日志；每个运行保留最近 500 条事件。

数据归档没有独立的订阅项，沿用“平台设置 › 通知渠道”里已有的事件订阅（共 11 项），所以要在渠道上勾选对应的现有事件才会收到：

| 归档里发生的事 | 归入的订阅事件 |
|---|---|
| 归档开始 | 开始执行 |
| 归档完成；被执行窗口结束或达到单次上限中断（预期内，下次接着跑） | 执行完成 |
| 负载中断、失败、校验失败、结构变更暂停、自动暂停、运行被中断（执行进程失联） | 执行异常 |
| 申请提交、流转到下一级 | 待处理 |
| 申请通过 | 审批通过 |
| 申请被驳回 | 被驳回 |

通知会 @ 任务提交人；通知里的任务链接指向 `/archive#task/<ID>`（需要配置站点地址 `PUBLIC_URL`，否则没有链接）。人工终止、恢复运行、跳过运行不发通知。服务启动时发现上个进程被强杀留下的运行（租约已过期）会标记为“中断”，并给任务提交人发一条“执行异常”通知。

## 6. 暂存目录、强杀与密钥（管理员）

文件备份先落到本地暂存目录，再上传到备份存储。为了不丢数据，每一批是“写暂存文件、fsync、校验行数”之后就删除源数据的，上传发生在滚动或运行结束时。所以：

- 暂存目录由环境变量 `ARCHIVE_SPOOL_DIR` 指定；没设置时是 `$EXPORT_BASE_DIR/archive-spool`（`EXPORT_BASE_DIR` 缺省为当前目录）。必须是持久目录，不要指到 `/tmp`；容量要够放下一个文件分片（默认 256 MB）以上。文件名形如 `t<任务ID>-r<运行ID>-<时间戳>-part-0001.tmp`。
- 正常结束、失败、被终止都会先上传再收尾；进程被强杀或机器宕机时，未上传的部分只留在暂存目录的 `.tmp` 文件里，而这些行在源表里已经删除，它们可能是唯一的副本。
- 系统不会自动补传，也不会删除这些文件。服务每次启动会扫描暂存目录：写日志和审计（“数据归档-暂存文件遗留”），并在对应运行记录的“说明”里写“暂存目录 … 遗留 N 个未上传的备份临时文件，需人工核对并补传”。发现后请 DBA 核对该运行的清单与行数，把 `.tmp` 文件（加密备份是 `DBAARC1` 格式的分块密文）手工上传到备份存储对应路径，确认无误后再删除。
- 文件备份的加密密钥由系统派生，不展示：对 `MIRAGE_SECRET_KEY`（缺省回退 `SECRET_KEY`）做 SHA-256（固定前缀 `dba-tool/archive/file-key/v1:`）得到 32 字节密钥，AES-256-GCM 分块加密。

> 警告：`SECRET_KEY` 不能丢也不能改：改了或丢了，已经加密的备份无法解密。请把 `SECRET_KEY` 与数据库备份一起妥善保管。

## 7. 审计与安全说明

- 审计动作均为“数据归档-”加动作：保存草稿、提交申请、试运行、修改任务、驳回、审批通过、暂停任务、恢复任务、停用任务、删除任务、立即执行、暂停运行、恢复运行、终止运行、恢复数据、运行结束、运行中断、暂存文件遗留、存储-新建 / 修改 / 测试 / 启用 / 停用 / 删除、策略修改。
- 最终 WHERE 与备份目标由服务端生成并校验，页面只提交结构化参数。
- 备份存储的 AK / SK 加密保存、永不回显；文件加密密钥由系统派生，不展示。
- 备份文件里是业务数据，请按权限控制备份存储的访问，敏感数据勾选加密。

## 8. 常见问题与排障

| 现象 | 可能原因 | 处理 |
|---|---|---|
| “立即执行”提示源表有未结束的 SQL 上线工单 | 为避免归档删除与 DDL 变更同时进行，本次被跳过 | 工单结束后再执行，工单在“SQL 上线”里查看 |
| 试运行红色项“时间列没有索引” | 表很大且时间列无索引 | 先通过 SQL 上线工单给时间列建索引，再重新试运行 |
| 向导提示“该表没有可作时间列的列” | 表里既没有 `date` / `datetime` / `timestamp` 列，也没有 `int` / `bigint` 列 | 这张表不能按时间归档；时间戳存在 `varchar` / `decimal` 里的需要先改表结构 |
| 试运行红色项“时间单位”：值看起来是 13 位 / 10 位，与所选不符 | 时间单位选错了 | 改选对应的单位后重新试运行；两种位数混在同一列里的表要先清洗数据 |
| 运行失败，原因是“时间单位疑似选错”，任务被自动暂停 | 运行中读到的这一批时间值整批小于所选单位的合理下限（1980 年），多半是把 10 位秒选成了 13 位毫秒；这时没有备份、没有删除任何数据 | 编辑任务改对时间单位，重新试运行并提交审批后再恢复 |
| 保留天数设不短 | 保留天数下限由安全策略决定（默认 30 天），防止误归档近期数据 | 确需放宽请联系管理员修改安全策略 |
| 任务被“自动暂停” | 连续失败、校验失败、从库延迟等，原因在详情 | 先排查原因（从库延迟、锁等待、目标端空间），再点“恢复任务”接着跑；结构变更暂停需重新试运行并重新提交审批 |
| 提交时被拒绝 `check_mismatch` | 试运行之后改动了关键字段（含资源组） | 重新试运行 |
| 磁盘剩余一直“未检测” | 巡检不采集磁盘剩余 | 属已知限制，勾选“我已知晓” |
| 复制延迟“未检测” | 从库没在平台登记或地址对不上；PolarDB-X 上读不到复制状态；账号没有查看从库所需的权限 | 把从库登记到实例管理；PolarDB-X 上属已知情况，不阻止运行 |
| 提示“目前只支持 MySQL / MariaDB / PolarDB / PolarDB-X” | 来源或库表备份目标实例的类型不在支持范围，或不是主库、已停用 | 换成支持类型的主库；MariaDB 服务端按 `mysql` 类型登记 |
| 运行报“缺少源表的建表语句，无法创建目标表” | 目标表不存在，而源表的 `SHOW CREATE TABLE` 读不到（兼容实现上可能发生） | 先在目标库手工建好同结构表（列名、类型、主键一致），再重新试运行 |
| 目标文件存储运行被拒绝 | 存储状态为“异常” | 在备份存储里“测试连接”并修复 |
| 运行失败并自动暂停，原因是“本批读到 N 行，但一行也没有删掉” | 不排序读取没有断点可以越过卡住的行：删除没有生效（触发器、账号缺 DELETE 权限、行被并发修改） | 先排查原因（看运行日志里的删除告警与目标库的错误日志），处理后再恢复任务 |
| 运行失败并自动暂停，原因是“连续 3 次读取一批都超过 15 秒” | 不排序读取每批从索引头开始，已删除的记录要等 InnoDB 清理；有长事务拖住清理，或优化器改选了别的索引 | 先结束源库上的长事务，看时间列索引与 `EXPLAIN`，再恢复任务；放大批大小对它无效 |
| 试运行红色项“首批读取”超过 15 秒 | 时间列没有索引或优化器没用它，每批都会扫很多行 | 先通过 SQL 上线工单给时间列建索引，重新试运行 |

## 9. 验证状态与已知限制

验证状态与已知限制如下：

- 真实 MySQL 未验证：引擎测试用 go-mysql 假服务端；真库集成测试需要环境变量 `ARCHIVE_IT_DSN`，默认跳过。服务层测试用假仓库、假打开器和假目录。
- PolarDB / PolarDB-X：兼容降级与建表改写只用讲 MySQL 协议的假服务端测试过，没有在真实 PolarDB / PolarDB-X 上验证；PolarDB-X 上分区、触发器、外键子表读不到时按“没有”处理，试运行里这几项的绿色不等于确认过。
- 阿里云 OSS 走其 S3 兼容端点，没有实现 OSS 原生签名，也没有用真实 OSS 验证过；S3 / MinIO 仅用假 S3 服务端与 SigV4 已知向量测试；对象存储无法得知可用空间；单对象上传（不分片），S3 单次 PUT 上限 5 GiB。

已知限制：

- 文件备份在滚动与结束时才上传，强杀后需要人工补传。
- GEOMETRY 等空间类型列：代码里没有拒绝逻辑，按二进制以 `0x…` 搬运，设计稿称 WKB 无法写回，请不要对含空间类型列的表归档（原文档称“不支持”，仅是设计声明）。BLOB 与 BIT 列原样搬运（CSV 与 SQL 文件里是 `0x…`）。
- 不处理有外键子表引用的表；分区表按普通表处理（更推荐用[分区维护](#help/partman)直接 `DROP PARTITION`）。
- 复制延迟只能检测在平台登记过的从库；磁盘剩余依赖巡检指标，目前取不到（显示“未检测”）。
- 同一任务在多个服务进程里只会有一个在跑（数据库互斥）；运行中的暂停与终止只能在启动它的那个进程里操作。
- 不排序读取（归档并删除、仅清理）没有断点可以跳过“刚删掉、InnoDB 还没清理”的记录，清理落后时读取会变慢（有读取过慢保护）；这一点和主键含字符串列的表仍按主键排序读取的行为，都只用假 MySQL 服务端与内存替身测试过，没有在真实 MySQL 上验证；首批读取耗时请以试运行里的实测为准。
- 附加条件不支持函数、子查询、算术运算；调度按服务进程所在时区计算。
- 整型时间戳列只支持 `int` / `bigint` 里的 10 位秒、13 位毫秒；`varchar` / `decimal` 存的时间戳、`yyyymmdd` 这类整数日期、微秒 / 纳秒不支持。时间单位的核对（抽样与最早 / 最晚值）只是防选错的辅助，没有在真实 MySQL 上验证过，上线前请看一眼试运行里显示的最早 / 最晚时间是否合理。
- 安全策略保存前的“受影响的现有任务”列表：未核对到代码实现，页面只有差异与风险提示。
- 首页“我的待办”卡片对只有归档权限的用户不显示。
