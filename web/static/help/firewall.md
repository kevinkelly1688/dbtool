# SQL 防火墙

SQL 防火墙让超级用户配置“规则”：语句进入在线查询、SQL 工单、数据导出之前先过一遍规则，得到放行、拒绝、要求填写原因、限制返回行数、强制脱敏或仅告警的决定，并留下命中记录。菜单：安全合规 › SQL 防火墙（仅超级用户）。

## 1. 功能概述

处理顺序：用户语句、静态检查、防火墙规则、库表权限、执行、脱敏与审计。

规则在权限校验之前评估：被拒绝的语句不会连到目标库，也不会让用户从报错里看出“有没有这张表的权限”；被拒绝的语句同样记入查询事件表（状态“被拦截”）。防火墙是增强而不是唯一防线：库表权限、只读会话、数据脱敏都还在，即使总开关关闭也不受影响。

三个场景的规则共用同一套，各场景能执行的动作不同，见 5.2。预估扫描行数来自目标实例上的 `EXPLAIN`（见 5.5）；预估影响行数只在 SQL 工单场景有值（goInception 检查结果；没有时对 UPDATE、DELETE 取 `EXPLAIN` 的扫描行数作为上界）。

## 2. 适用范围

| 实例类型 | 在线查询 | SQL 工单 | 数据导出 | 预估扫描行数（`EXPLAIN`） |
|---|---|---|---|---|
| MySQL | ✔（库表在配置了 goInception 时用语法树，否则词法） | ✔（词法） | ✔ | ✔（在线查询仅 SELECT、WITH；工单与导出含 DML） |
| PolarDB、ADB | ✔（词法） | ✔ | ✔ | ✔ |
| PolarDB-X、SelectDB、Doris | ✔（词法） | ✔ | ✔ | ✖（条件显示“未评估”） |
| SQL Server | ✔（T-SQL 词法） | ✔（原生检查，影响行数未知） | ✔ | ✖ |
| PgSQL、ClickHouse | 部分 | ✖（无工单入口） | ✖（无导出入口） | ✖ |
| MongoDB | ✖ | ✖ | ✖ | ✖ |
| Redis | ✖ | ✖（走自己的 Redis 规则） | ✖ | ✖ |

“部分”的含义：PgSQL、ClickHouse 的在线查询可以拒绝、要求原因、限行和告警，但不能强制脱敏，强制脱敏降级为仅告警。线下手工执行的工单（系统不检查也不执行）与 Redis 工单不进防火墙。

## 3. 前提条件与权限

- 仅超级用户可访问页面与全部接口（`/settings/firewall`、`/api/v1/settings/firewall/...`），没有按钮级权限码，非超级用户返回 403“仅超级用户可以操作”。
- 防火墙的表需要先建好：在元数据库执行 `deploy/sql/240_firewall.sql`（也可用 `dbt-admin bootstrap --only-sql --apply`）。
- 规则里的用户范围按权限组判断：规则里的“用户”指工单的提交人，不是点“执行”的人。

## 4. 操作指南

### 4.1 新建规则

目标：拦截或提示一类高风险语句。入口：SQL 防火墙 › 规则 › 新建规则（也可从“规则模板”添加）。

1. 选场景、实例环境、用户范围，必要时限定实例。
2. 添加命中条件（一条或多条，选“全部满足”或“任一满足”）。
3. 选动作与提示文案，优先级留默认（100）。
4. 保持“观察”模式保存（新建的缺省就是观察）。

新建规则缺省：观察模式、启用、场景为在线查询、优先级 100。

### 4.2 安全地上线一条规则

1. 在编辑器里写规则，保持“观察”模式保存。
2. 点回放：按规则选的场景，用最近 7 天真实的在线查询日志或工单语句把当前草稿跑一遍（最多评估最近 2 万条语句、最长 10 秒；不写命中记录、不通知任何人），看命中多少条、涉及哪些用户、其中多少来自 DBA 组（权限组名称为 `DBA`，不区分大小写；没有该组则不统计）。命中超过 1% 时页面会建议继续观察。
3. 观察一周，到“命中记录”里确认没有误伤；误伤的用户加例外，或调整条件。
4. 把规则切到生效（会弹出确认；近 7 天没有命中记录时会提醒“没有观察数据”）。

回放的口径：在线查询样本取自查询日志（只含成功执行的语句，已被拦截的不在其中），语句是系统追加 `LIMIT` 之后的形态，“没有 LIMIT”类条件对在线查询偏乐观；工单样本取最近的工单语句，不含手工工单，预估影响行数取提交时的检查结果；不做 `EXPLAIN`（回放不会去连目标库），预估扫描行数条件在回放里“未评估”。

### 4.3 用语句测试台验证

在“语句测试台”粘贴一条语句（也可选内置的示例语句），选场景、实例或环境、用户权限组、时间（工作日 14 点、凌晨 3 点、晚上 22 点、周末 11 点、现在）、用户名，按当前已保存的全部规则（含观察状态）走一遍，得到最终决定、每条规则为什么命中（或为什么没命中，含已停用、例外、条件未评估，停用的规则在“被跳过”里说明），命中位置高亮。测试台不会连目标库做 `EXPLAIN`，预估扫描与影响行数需要手填来试条件：留空时这类条件显示“未评估”、不命中；只填了扫描行数时，UPDATE、DELETE 的预估影响行数取它作上界。可一键把语句指纹加入黑名单（生成一条观察模式的草稿规则）或为它添加例外。测试台不写命中记录、不通知任何人。

### 4.4 处理命中与添加例外

“命中记录”按规则、结果、场景、时间、关键字筛选；同一规则、用户、语句、结果在 10 分钟内合并为一行（滑动窗口，每次合并刷新），右侧显示合并次数。详情里可为该用户添加例外，或用语句指纹新建规则。

例外只豁免所选规则对某个用户、权限组、实例或语句指纹的约束，不影响其他规则。必须写原因（4–500 字）、必须有有效期（页面选项 7、30、90 天或 1 年，接口 1–365 天），到期按过期时间自动失效，到期的例外在名单里还显示 30 天。创建与撤销都写系统审计，到期本身不写审计。删除规则时其例外一并删除，命中记录保留。

### 4.5 调整全局模式与总开关

页头的全局模式与总开关：

- 全局模式“观察”是总闸门：打开后所有规则只记录、不拦截任何语句（包括已经“生效”的规则），适合新规则上线前评估或批量调整前使用，评估完记得切回“拦截”；切到“拦截”后，“生效”的规则才开始执行动作，观察状态的规则仍只记录。
- 总开关关闭后规则全部不执行、也不再记录命中，等于撤掉这层防护，关闭必须写原因（4–200 字）并记高危审计。

> 注意：全局模式的缺省值是“观察”（`firewall.mode` 在 `internal/settings/registry.go` 里的登记缺省是 `observe`），新部署后规则只记录、不拦截；需要拦截请在页头把全局模式切到“拦截”。

## 5. 规则、动作与字段说明

### 5.1 规则组成

| 部分 | 说明 |
|---|---|
| 适用范围 | 场景（在线查询、SQL 工单、数据导出）、实例环境（全部，或环境字典里的某一个，如仅生产、仅测试、仅预发）、可选的指定实例（至多 200 个）、用户（全部、仅某些权限组、排除某些权限组）。实例的环境以“实例管理”里为实例设置的环境为准；没设置时才按实例标签推断（含 `prod` 或“生产”视为生产，含 `test` 或“测试”视为测试）；两者都没有的实例不属于任何环境，只会被“全部实例”的规则覆盖。环境范围按编码精确匹配，“按生产对待”不影响匹配（新增的生产类环境不会被编码为 `prod` 的“仅生产”规则覆盖）；被规则引用的环境不能在“环境设置”页里删除 |
| 命中条件 | 一条或多条（至多 20 条），可选“全部满足”或“任一满足” |
| 动作 | 拒绝；要求填写原因（仅在线查询）；限制返回行数（在线查询与数据导出）；强制脱敏（在线查询与数据导出，需要至少一个带列名的对象条件，如 `*.*.id_card`）；仅告警 |
| 提示文案 | 被拦截或要求填写原因时用户看到的说明，至多 500 字 |
| 模式 | 观察：只记录命中，不执行动作；生效：执行动作 |
| 优先级 | 0–100000，数字越小越先求值；指纹黑名单建议放最前；最终决定与顺序无关，见 5.3 |
| 名称 | 至多 100 字符，不区分大小写唯一；规则总数至多 500 |

命中条件的取值：

| 条件 | 取值与说明 |
|---|---|
| 语句类型 | SELECT、INSERT、UPDATE、DELETE、CREATE、ALTER、DROP、TRUNCATE，可多选 |
| 结构特征 | 没有 WHERE（`WHERE 1=1` 算有 WHERE）、没有 LIMIT（仅 SELECT，认 `LIMIT`、`TOP`、`FETCH`）、笛卡尔积（JOIN 缺条件，或逗号多表无条件）、一次提交多条语句（工单与导出逐条求值，不会命中）、`SELECT *`（只看最外层）、LIKE 以 `%` 开头、IN 列表过长（超过 1000 项） |
| 关键字、函数 | 逗号分隔（至多 50 项，单项至多 100 字），如 `SLEEP, BENCHMARK`；不区分大小写，按词匹配，忽略注释；可写短语如 `INTO OUTFILE` |
| 正则（SQL 文本） | 至多 500 字；对去掉注释后的 SQL 文本匹配，不区分大小写；Go RE2 语法，不支持反向引用与环视 |
| 涉及库表（列） | `库.表`、`*.表`、`*.表.列`，逗号分隔（至多 50 项，至多 3 段）；`*` 代表任意；没写库名的用语句的当前库补全；识别不受别名、反引号、注释影响；列匹配按“语句里出现同名标识符”判断，不绑定到具体表，宁多勿漏 |
| 预估扫描行数至少 N | `EXPLAIN` 预估的扫描行数，口径见 5.5；取不到时不命中；N 取 1 到 10 的 12 次方 |
| 预估影响行数至少 N | 只在 SQL 工单场景有值；在线查询、数据导出里取不到，不会命中 |
| 时间 | 工作时间为周一到周五 9–19 点（服务时区）；非工作时间为周末，以及工作日 19 点后、9 点前；不识别节假日 |
| SQL 指纹等于 | 8 位小写十六进制，常从命中记录或语句测试台一键带入 |

动作的参数限制：限制行数 1–1,000,000；`limit` 仅限在线查询与导出，`reason` 仅限在线查询，`mask` 仅限在线查询与导出；强制脱敏的对象条件里库与表要同为具体名或同为 `*`（`*.*.列` 或 `库.表.列` 可以，`*.表.列` 与 `库.*.列` 被拒）。

### 5.2 不同场景里怎么生效

| | 在线查询 | SQL 工单 | 数据导出 |
|---|---|---|---|
| 什么时候求值 | 每次执行语句之前（在库表权限校验之前） | 提交检查（点“检查”和“提交”都会）对每条语句、每个目标实例求值，任一实例拒绝则整行拒绝；执行前再复核一次 | 提交检查；执行前在每个实例上再复核一次 |
| 拒绝 | 语句不执行，记为“被拦截” | 检查结果里该行标红“驳回高危SQL（防火墙）”，按系统配置 `review.auto_reject_level`（`warning`、`error`（缺省）、`never`）处理；审批通过后执行前复核仍会拒绝 | 检查不通过；执行前被拒绝的实例导出失败 |
| 要求填写原因 | 弹窗收集 | 不支持，按“仅告警” | 不支持，按“仅告警” |
| 限制返回行数 | 与权限上限取小 | 不支持，按“仅告警” | 与导出行数上限取小，超过则检查不通过或中止导出 |
| 强制脱敏 | 命中的列整体隐藏 | 不支持，按“仅告警” | 命中的列整体隐藏，即使脱敏总开关没开；做不了就中止 |
| 仅告警 | 结果上方提示 | 该行标黄“SQL 防火墙提示”，不会被“警告就驳回”的配置驳回 | 同左 |

要点：

- 规则里的“用户”指工单的提交人：审批通过后换人执行不能绕过规则。
- 执行前复核只认拒绝：观察态与告警都不拦截。被复核拒绝的工单进入“执行有异常”，结果里写明规则，不会执行任何语句；需要继续时请调整规则或为提交人添加例外后重新提交。批量上线与批量导出按实例各自复核，被拒绝的实例失败，其余照常。
- `review.critical_ddl_regex` 仍然保留并先求值；两者都命中同一行时，以它的文案为准。
- 一次提交里指纹相同的多条语句（如批量 INSERT）只记一次命中；一次检查最多记 200 条命中。
- 工单语句的库表由词法解析得出（检查结果里没有表信息），宁多勿漏：除 `FROM`、`JOIN` 外，会补上 UPDATE、INSERT INTO、REPLACE INTO、ALTER、DROP、TRUNCATE、CREATE TABLE 后面的表。
- 在线查询里以 `SET` 开头的脚本（MySQL 系）：脚本里的每条查询（包括 `SET` 赋值里的子查询）都各自过一遍规则，任一条被拒绝则整份脚本不执行；扫描行数的 `EXPLAIN` 会带上前面的 `SET`。

### 5.3 多条规则命中时：取最严

- 规则按优先级从小到大求值；命中多条时取最严的动作：拒绝、要求原因、限行与强制脱敏、仅告警。
- 任一规则拒绝则拒绝（说明取优先级数字最小的那条，同优先级取编号小的）。
- 否则任一规则要求原因则需要填写原因。
- 限制行数取最小值，并与用户的查询权限上限再取小；强制脱敏取并集，与数据脱敏页配置的脱敏并用。
- 仅告警的放行，提示显示在结果上方。
- 观察模式的规则（或全局观察）永不执行动作，只记录“若规则生效会怎样”。

### 5.4 用户会看到什么

| 动作 | 在线查询页面 |
|---|---|
| 拒绝 | 红色错误条，显示规则的提示文案；语句不执行（返回 403 `firewall_denied`） |
| 要求填写原因 | 弹窗要求写原因（页面校验 4–200 字；服务端只要求非空，命中记录里截断到 500 字），确认后带着原因重新提交，原因进命中记录（返回 428 `reason_required`） |
| 限制返回行数 | 照常返回，上限收紧，页面的限制提示条注明“SQL 防火墙规则「…」” |
| 强制脱敏 | 命中的列整体显示 `***`，即使数据脱敏总开关没开也执行 |
| 仅告警 | 放行，结果上方提示 |

防火墙自身出错且 `firewall.on_error=deny` 时返回 503 `firewall_unavailable`。

### 5.5 预估扫描行数是怎么来的

规则里的“预估扫描至少 N 行”用目标实例上的 `EXPLAIN` 估算，口径是要翻多少行（不是返回多少行）：按连接顺序，第 i 张表要检查的行数等于前面各表的 rows 乘 filtered% 之积再乘本表 rows，各子查询与派生表之和为总数。

- 只在需要时才 `EXPLAIN`：规则里的条件按成本排序（语句类型、关键字、结构特征，然后涉及库表，最后 `EXPLAIN`）。“全部满足”的规则里前面的条件已经不满足，或“任一满足”的规则里前面的已经命中，就不会为它去查执行计划；同一条语句的多条规则共用一次 `EXPLAIN`。
- 限时、缓存、熔断：每次最多等 `firewall.explain_timeout_ms`（缺省 3000 毫秒，可设 200–30000）；同一语句 10 秒内用缓存（失败 15 秒）；同一实例最多 4 路并发；实例连续 3 次超时或连不上就暂停 `EXPLAIN` 30 秒。
- 取不到就是“未评估”：超时、熔断、语句类型不支持（DDL、SHOW 等）、实例类型不在 MySQL、PolarDB、ADB 之内（PolarDB-X、SelectDB、Doris、SQL Server、PgSQL、ClickHouse 等）、计划里缺 rows 列、表不存在，这个条件都不命中，也不会拦用户；命中记录与测试台里写明“未评估：原因”。
- 在线查询里不会替没权限的人探测：语句没通过库表权限校验时，扫描行数条件不评估（也不会向目标库发 `EXPLAIN`），用户得到的是权限错误，而不是“需要填写原因”之类能暴露表大小的提示。
- 工单里：一次检查最多下发 50 次 `EXPLAIN`、总耗时最多 20 秒，超出的语句按“未评估”；`EXPLAIN` 在目标实例上以只读会话执行，不会改数据。
- 规则列表里，本进程里平均求值耗时偏高（至少 5 次求值且平均至少 100 ms）的规则标“慢”，“未评估”占比至少 20% 的标“未评估 N%”；概览下方的一行汇总 `EXPLAIN` 的使用情况（下发、失败、超时、缓存命中、熔断中的实例）。这些统计只覆盖当前进程，重启清零。

### 5.6 页面上的几块

- 规则：列表显示优先级、条件、范围、动作、状态、近 7 天命中次数（含每天的小柱图）。可直接启停、切换观察与生效、编辑、回放、删除。库里被手工改坏、无法通过校验的规则标红“无效，不会生效”，不能启用也不能切到生效。
- 语句测试台：见 4.3。
- 命中记录：见 4.4。命中查询默认近 7 天，最大 90 天；语句默认只保存把字符串与数字字面量换成 `?` 之后的形态（`firewall.store_sql=raw` 才存原文）。双引号包裹的字符串被当作标识符，不会被替换。语句最长保存 2000 字符，事实提取只看语句前 64 KB。
- 例外名单：见 4.4。
- 规则模板：一组常见规则。添加后是观察模式，不会拦截任何语句；先用“回放”和命中记录确认没有误伤，再切换为生效。模板里的示例表名与列名请在编辑器里改成实际的。

## 6. 失败时怎么办

| 情况 | 行为 |
|---|---|
| 防火墙的表没建（没执行 `deploy/sql/240_firewall.sql`） | 等同没有规则，所有语句不经过防火墙，行为与以前一致；页面顶部提示先建表，建好后刷新页面 |
| 读取规则失败 | 沿用上一份规则快照；从未读取成功时按 `firewall.on_error` 处理（`allow` 放行，缺省；`deny` 拒绝） |
| goInception 不可用 | 涉及库表的条件“未评估”、不命中，记录里写明；不会因此阻断查询 |
| 写命中记录失败 | 只记日志，不改变决定 |
| 手工改库造成规则无效 | 该规则被跳过并记日志，其他规则照常；规则列表里标红 |
| 求值 panic、权限组读取失败 | 按 `firewall.on_error` 处理 |

规则变更在当前进程内立即生效，多实例部署的其他进程最长 3 秒后生效。

## 7. 系统配置项

写在系统配置（`dbt_setting`）里，也可用页面上的开关修改前两项：

| 配置项 | 缺省 | 说明 |
|---|---|---|
| `firewall.enabled` | `true` | 总开关；`false` 时所有规则不执行 |
| `firewall.mode` | `observe` | 全局模式；`observe` 时所有规则只记录，`enforce` 时生效的规则才拦截 |
| `firewall.on_error` | `allow` | 防火墙自身出错时放行（`allow`）还是拒绝（`deny`） |
| `firewall.store_sql` | `masked` | 命中记录里的语句：`masked` 只存脱字面量的形态，`raw` 存原文 |
| `firewall.explain_timeout_ms` | 3000 | 预估扫描行数（`EXPLAIN`）每次最多等多久，200–30000 毫秒 |

## 8. 审计与安全说明

- 审计动作（归类“安全合规 › SQL 防火墙”）：“SQL 防火墙规则变更”“SQL 防火墙例外”“SQL 防火墙模式”“SQL 防火墙总开关”，高危的带“【高危】”前缀。
- 标记为高危：新建即“生效且启用”、修改时由非生效改为生效、规则由观察切到生效、全局切到观察、总开关关闭；启停与删除不标高危。无变更的保存不写库也不记审计。
- 命中记录里的语句默认脱去字面量，请在确有需要时再把 `firewall.store_sql` 设为 `raw`，原文可能包含敏感数据。
- 请求体上限 1 MB；测试台语句至多 200 KB。

## 9. 常见问题与排障

| 现象 | 可能原因 | 处理 |
|---|---|---|
| 规则没有拦截 | 规则为观察模式，或全局模式为观察，或总开关关闭 | 检查规则模式与页头的全局模式 |
| 条件“未评估” | `EXPLAIN` 取不到（见 5.5） | 在测试台里手填行数试条件，或改用其他条件 |
| 页面顶部提示先建表 | 没有执行 `240_firewall.sql` | 执行后刷新页面 |
| 在线查询返回“防火墙暂时不可用” | `firewall.on_error=deny` 且求值失败 | 检查规则表与元数据库连接 |
| 工单执行前被拒绝 | 执行前复核命中了拒绝规则 | 调整规则或为提交人添加例外后重新提交 |
| 用户反馈被误拦 | 规则条件过宽 | 在命中记录里为该用户加例外，或收窄条件 |
| 规则标红“无效” | 库里被手工改坏 | 在编辑器里修正后保存 |

## 10. 验证状态与已知限制

验证状态与已知限制如下：

- 集成测试需要 `FIREWALL_IT_DSN`，默认跳过，设计稿称本机没有跑过；管理页的存储层 SQL 只在假存储下验证；前端测试均为假后端。
- 设计稿声明未做：升级为工单审批、`review.critical_ddl_regex` 迁移为内置规则、节假日日历、PgSQL 与 SQL Server 更准的事实与执行计划、规则版本历史与回滚、命中通知（`notify` 字段只存不发）、非超级用户建例外、TiDB 与 Doris、SelectDB 的 `EXPLAIN` 格式、跨进程共享 `EXPLAIN` 缓存与熔断、指标导出到外部监控。
- 命中记录表 `dbt_firewall_hit` 目前没有自动清理：数据保留（`internal/retention/targets.go`）里没有对应目标，表会持续增长（设计稿称有 90 天保留策略，代码里未找到）。

与设计稿不一致处（以代码为准）：`firewall.mode` 缺省为 `observe`（设计稿写 `enforce`）；库表语法树只用于类型为 `mysql` 的在线查询。

其他：

- 部分页面文案已过时：测试台手填行数时的提示“EXPLAIN 尚未接入”，以及模板 `no-where-dml`、`drop-truncate`、`offhours-ddl` 的说明“SQL 工单场景接入后生效”，三个场景实际都已接入。
