# 分区维护

分区维护为按时间 RANGE 分区的表配置“提前创建多少个分区、保留多久”，由系统自动续建新分区、清理过期分区，取代手写 `ALTER TABLE ... PARTITION` 脚本。DBA 配置，系统按计划或手动触发执行。菜单：数据服务 › 分区维护。

## 1. 功能概述

- 配置：每张表一条配置（实例、库、表、分区字段与类型、周期与跨度、预创建数、保留数、时区）。
- 状态：服务端读取目标表真实分区后逐行计算，显示是否需要续建、清理或初始化。
- 执行：预览将要执行的语句后手动执行，或由管理员开启定时自动维护。
- 初始化：把 MySQL / PolarDB 的未分区表显式初始化为分区表（高危，整表重建）。
- 推送与日志：维护结果推送到钉钉、飞书、企业微信或 Slack，并保留带逐表运行输出的维护日志。

系统只接受结构化配置，不接受手写 DDL；分区名与边界值全部由服务端计算。

## 2. 适用范围

| 能力 | MySQL | PolarDB | SelectDB / Doris | PolarDB-X、ADB、SQL Server 等 |
|---|---|---|---|---|
| 续建与清理 | ✔ | ✔ | ✔（每个分区一条 `ADD PARTITION`） | ✖（提示“暂不支持”） |
| 初始化未分区表 | ✔ | ✔ | ✖（需事先在目标库建为 RANGE 分区表） | ✖ |
| `REORGANIZE`（含 `MAXVALUE` 分区） | ✔（手动，定时不执行） | ✔ | ✖（含 `MAXVALUE` 分区的表直接拒绝） | ✖ |
| 执行时设置 `lock_wait_timeout` | 15 秒 | 15 秒 | 不设置 | — |

> 注意：带子分区的表暂不支持维护，会判为“异常”。

## 3. 前提条件与权限

| 权限码 | 作用 |
|---|---|
| `partman.view` | 打开页面，查看配置、预览与维护日志 |
| `partman.add` | 新增配置 |
| `partman.edit` | 编辑配置、启停配置；设置每张表的可用分区告警（阈值、静默）；管理推送设置（含测试发送）；查看“系统记录” |
| `partman.run`（高危） | 立即执行维护、初始化分区表（只认该按钮，不由 `partman.edit` 满足） |
| `partman.delete` | 删除配置；含 DROP 的执行与初始化分区也需要它 |

- 预览不需要执行权限：没有 `partman.run` 的用户界面上只显示“预览”。
- 实例类型须是 MySQL、PolarDB、SelectDB、Doris，库名须符合实例的库名过滤规则。
- 平台账号在目标库上需要能读取分区信息并执行 `ALTER TABLE ... PARTITION`，各类型的权限模板见安装部署指南（`docs/ops-manual.md`）附录 E（该映射标记为“待验证”）。

## 4. 操作指南

### 4.1 新增配置

目标：为一张表配置自动维护。入口：分区维护 › 新增配置（`partman.add`）。

1. 选实例、库、表。库、表、分区字段可从目标实例直接选择（候选来自目标实例的 `information_schema`）；读取失败会提示，仍可手工输入。表名下拉里只列分区表，非分区表不显示；**淡红底色**表示这张表已经有分区配置（同一实例同一库表只能有一条），**浅绿底色**表示它是 RANGE 分区表且还没有配置、可以新增；LIST / HASH 等其他分区方式的表照常列出但不上色（不支持维护）。手工输入的表名不受这个列表限制。
2. 选分区字段与类型，选择字段后自动带出类型。
3. 设置周期、跨度、预创建数、保留数、时区。
4. 点“预览”查看将要执行的语句，确认后保存。

预期结果：配置出现在列表里，状态由服务端异步计算。新建表单默认：类型 `datetime`、周期 `day`、跨度 1、保留 30、预创建 3、时区 `Asia/Shanghai`、启用。同一实例同一库表只能有一条配置，重复会提示“已经有分区配置”。

### 4.2 预览并执行维护

目标：按配置续建或清理分区。入口：配置行的“预览 / 执行”（`partman.run`，高危）。

1. 系统重新读取目标表、重新计算计划，列出将创建与将删除的分区。
2. 含 DROP 时必须在确认框里输入 `库.表` 确认，并需要 `partman.delete` 权限；REORGANIZE 需要勾选确认。
3. 执行时服务端再次读取并核对：如果预览之后表被别人改过、与你确认的删除列表不一致，会拒绝并给出新计划，不会误删。
4. 执行前先写审计日志（含完整语句），写不进去就不执行；MySQL 执行时设置 `lock_wait_timeout=15`，拿不到元数据锁就失败，不会让业务查询在 ALTER 后面排队；语句遇到第一个失败即停，其余标为未执行。
5. 同一个配置同一时刻只有一个维护在跑（手动与定时互斥，跨进程用数据库锁 `dbt_partman_<配置编号>`）。

> 警告：`DROP PARTITION` 会永久删除该分区的数据且不可恢复。请先确认保留数配置符合数据保留要求，必要时先[导出](#help/export)留档。

预览示例（MySQL）：

```sql
ALTER TABLE order_db.order_event ADD PARTITION (PARTITION p20261009 VALUES LESS THAN ('2026-10-10 00:00:00'));
ALTER TABLE order_db.order_event ADD PARTITION (PARTITION p20261010 VALUES LESS THAN ('2026-10-11 00:00:00'));
ALTER TABLE order_db.order_event DROP PARTITION p20260702;
```

实际语句里库名、表名、分区名带反引号；Doris 的分区名只在含特殊字符时才加反引号。

### 4.3 初始化为分区表

只用于 MySQL / PolarDB 里还不是分区表的表。列表状态显示“未分区”，点“预览 / 执行”进入初始化流程：

1. 选起点（决定从哪个窗口开始建分区，一直建到“当前窗口 + 预创建数”）：
   - 从当前窗口开始（默认）：不读取存量数据。存量数据时间早于起点的会全部落进第一个分区；晚于最后一个分区上界的数据会让 ALTER 失败。
   - 从最早数据所在窗口开始：对目标表执行一次带 20 秒超时的 `SELECT MIN(分区字段)`；大表超时或失败时不会继续，请改用“指定起始日期”。
   - 指定起始日期：`YYYY-MM-DD`（可带 ` HH:MM:SS`），按配置时区向下对齐到分区网格，不能晚于当前窗口。
2. 看计划：起始窗口、将创建的分区个数与范围（首个到末个分区、最后上界）、前置检查结果：表是 InnoDB 等支持分区的引擎、不是视图或临时表、没有外键、分区字段存在且类型是 bigint、int、datetime 或 date、每一个唯一键（含主键）都包含分区字段、分区数不超过 5000（超过 200 会提醒）。任何一项“不满足”都不会发出 ALTER。
3. 确认：点“初始化为分区表…”，在确认框里核对语句，键入 `库.表` 才能确认。服务端会重新读取目标表并重算计划，确认值（表名、分区个数、首末分区）与重算结果逐项一致才执行，否则拒绝并显示新计划。

> 警告：初始化是一条整表重建的 ALTER，表越大耗时越长，期间持有元数据锁、可能阻塞写入；不带 `MAXVALUE` 兜底分区（超出最后上界的写入会失败，靠后续续建补上）。请在业务低峰执行并先确认有备份。需要 `partman.run` 与 `partman.delete` 权限，执行前先写审计。

### 4.4 配置推送

页头“推送设置”（需要 `partman.edit`）管理维护结果的推送通道，支持钉钉、飞书、企业微信和 Slack。

| 项 | 说明 |
|---|---|
| Webhook 地址 | 只允许 https 的官方机器人域名（钉钉 `oapi.dingtalk.com`，飞书 `open.feishu.cn` 与 `open.larksuite.com`，企业微信 `qyapi.weixin.qq.com`，Slack `hooks.slack.com`），另允许本机 `localhost`、`127.0.0.1`、`::1`（联调用）；至多 500 个字符，重复地址会被拒绝；列表里只显示脱敏后的地址 |
| 自定义关键词 | 机器人安全设置里的“自定义关键词”，会拼进消息正文（企业微信、钉钉、飞书；Slack 不适用） |
| 加签密钥 | 机器人安全设置里的“加签”密钥（钉钉、飞书；企业微信与 Slack 没有）。只写不读：保存后只显示“已设置”，留空表示不修改，可勾选“清空” |
| @ 时机 | 仅失败时 @（默认）、每次都 @、从不 @ |
| @ 对象 | 逗号、空格或换行分隔 |
| 启用 | 只有启用的通道才会推送；没有启用的通道时维护结果不会推送 |

各平台地址形式与 @ 对象写法：

| 平台 | 地址形如 | @ 对象 |
|---|---|---|
| 钉钉 | `https://oapi.dingtalk.com/robot/send?access_token=…` | 11 位手机号，或 `all`、`@all`；其他值作为钉钉 userId 发送 |
| 飞书 | `https://open.feishu.cn/open-apis/bot/v2/hook/…` | open_id，或 `all`、`@all` |
| 企业微信 | `https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=…` | 手机号按手机号 @，其他按 userid，`@all` 可用 |
| Slack | `https://hooks.slack.com/services/…` | 可写 `<!subteam^…>` 等 Slack 写法 |

- 什么时候推送：一次维护（手动或定时）执行了语句或失败之后推送；没有变更不推。定时维护里“计划失败 / 连不上目标库”也算失败；定时跳过的情形（未分区、实例不支持、近期已有日志、拿不到锁）不推。
- 全局时机由系统配置项 `partition.notify_on` 决定：`always`（默认，执行了语句或失败后推送）、`on_failure`（只在失败时）、`never`；推送设置里只读显示。通道的“@ 时机”决定何时 @ 人。
- 推送失败不会影响维护结果，只记服务日志（地址里的密钥已脱敏）。
- “测试发送”会向通道发一条固定的测试消息并显示每个通道的结果，不依赖维护事件，也不受 `partition.notify_on` 影响。

### 4.5 查看维护日志

“维护日志”页签记录你可见的实例范围内每次执行的时间、语句、结果，最新在前。可按配置、来源筛选；配置行上的“日志”按钮只看这一个配置最近 10 条。

| 来源 | 含义 |
|---|---|
| 手工 | 在“预览 / 执行”里手动执行 |
| 定时 | 本系统的定时维护 |
| 外部程序 | 日志里没有来源与执行状态字段的记录（不是本系统手工 / 定时写入的），状态显示“未记录” |
| 系统记录 | 定时维护每一轮的汇总与推送测试，不属于某个配置（需要 `partman.edit` 权限，在来源筛选里选“系统记录”） |

每条记录都可以展开运行输出（逐表的运行日志）：

- 内容：毫秒时间、级别（INFO、WARN、ERROR）和消息，包括开始与结束行、每项检查与决策的原因（为什么续建、为什么跳过、为什么没删）、每条语句的结果与耗时、推送结果。
- 操作：按级别筛选（全部、警告及以上、仅错误）、关键词搜索、“复制”（复制当前筛选结果）、“下载 .log”（下载这条记录的完整运行输出文本）。
- 截断：一次运行的输出行数与体积有上限（约 300 行、40 KB），超出时较早的 INFO 会被先截去，并在面板上方标出“已截断”和被截去的行数。
- 没有运行输出：早于该功能的记录或来源为“外部程序”的记录没有运行输出，只显示语句与结果。
- 预览：预览会在计划下方给出可展开的“检查过程”（读到了哪些现有分区、按什么时区与边界规则判断、哪些被跳过），预览不落库，所以没有下载。
- 执行结果：执行完成后，结果表下方直接展示本次的运行输出（与维护日志里保存的一致，可下载）。

运行输出里不会出现数据库密码和完整的 webhook 地址与密钥。

### 4.6 可用分区告警

分区快用完而没人续建，新数据迟早写入报错。这个功能在那之前把它标出来，并推送给你。

**可用分区数**：目标表里“上界晚于当前时间”的分区个数——含正在写入的当前分区，不含已经过去的历史分区，不含 `MAXVALUE` 兜底分区。维护正常时它稳定在“预创建数 + 1”（预创建 3 就是 4 个）。**可用分区数小于阈值就告警**，默认阈值 3。

| 位置 | 说明 |
|---|---|
| 列表“可用分区”列 | 小方块是个数（虚线方块 = 还差几个才到阈值）、数字、`/ 阈值`，下面一行是预计用尽的时间；含 `MAXVALUE` 的表带 `MAXVALUE` 标签：用尽后写入不会失败，但续建需要 REORGANIZE |
| 列表“告警”列 | 告警中 / 已用尽（0 个）/ 静默至 … / 正常 / 已关闭 / 无法判断（读不到目标表，或这张表不适用：不是 RANGE 分区、配置与表对不上等，不会告警）；有 `partman.edit` 的用户在这里点“告警设置” |
| 页顶统计卡“可用分区不足” | 当前告警中的配置数（静默中的不算） |
| “告警设置”弹窗 | 这张表自己的阈值：跟随全局默认、自定义（1–100）、或这张表不告警（0）；可静默 24 小时 / 7 天（期间只在列表里标记，不推送，到期自动解除） |
| 页头“告警记录” | 每次推送一条：首次告警、重复提醒、已恢复，以及推送结果 |

**什么时候检查、推送**：页面随状态检查在列表里标出；后台每隔“自动维护间隔”（默认 180 分钟）检查一轮，排在定时维护之后——续建成功就不会推；**自动维护没开也会检查**。推送沿用“推送设置”里启用的通道。

**去重**：首次不足推一次；之后每隔“重复提醒间隔”（默认 24 小时，0 = 不重复）提醒一次；回到阈值以上推一条“已恢复”（可关）。没有启用的通道时不推送，也不留记录，配置通道后再推；所有通道都失败会留一条失败记录，下一轮重试。

**全局设置**（超级用户，“平台设置 › 系统配置 › 分区维护”）：启用可用分区告警、全局默认阈值、重复提醒间隔、恢复后通知。

> 注意：阈值不要超过这张表的“预创建数 + 1”，否则续建之后也达不到，会一直告警（列表标“阈值过高”）。小时、分钟分区的表一个分区很短，3 个可能只有 3 小时，可以给它设大一点（同时加大预创建数）。

> 前提：需要先在元数据库执行 `deploy/sql/280_partman_alert.sql`（升级时安装脚本会自动执行）。没执行时列表仍会算出并标注可用分区数，但不推送、不能给每张表设阈值，页面上方有提示。

## 5. 字段与规则说明

### 5.1 配置字段

| 字段 | 说明 | 约束 |
|---|---|---|
| 实例 / 库 / 表 | 目标表 | 标识符匹配 `^[0-9A-Za-z_$]{1,64}$`；系统库（`mysql`、`information_schema`、`performance_schema`、`sys`）不允许 |
| 分区字段与类型 | `int`（10 位秒级时间戳）、`bigint`（13 位毫秒时间戳）、`datetime`（`YYYY-MM-DD HH:MM:SS`）、`date`（`YYYY-MM-DD`，只能精确到天，周期不能是分钟或小时） | 候选字段只列这四类；MySQL 下 `int` 无符号上限为 2106 年，有符号为 2038 年，Doris 一律按 2038 年；超出时拒绝并提示改 `bigint`；`datetime`、`date` 在 MySQL 上必须是 `RANGE COLUMNS` |
| 周期 | 分钟、小时、天、周、月、年 | — |
| 跨度 | 每个分区覆盖几个周期 | 1–255 |
| 预创建数 | 当前时刻所在分区之后要保证有几个分区 | 0–100 |
| 保留数 | 只保留最近几个历史分区，更早的会被删除；0 表示全部保留 | 0–100000 |
| 时区 | 决定按哪个时区对齐分区边界 | 见 5.2，至多 20 个字符 |
| 开启维护 | 关闭后只能预览、不能执行，定时维护也不处理；列表第一列的“启停”开关可一键启停（只改这个开关，写审计） | 手动执行关闭的配置返回“该配置的维护开关是关闭的” |
| 说明 | 备注，例如环境名；也是推送消息里的环境名 | 至多 100 字 |

### 5.2 时区怎么填

输入框可以直接输入，也可以点下面的常用项：

| 写法 | 例子 | 说明 |
|---|---|---|
| 留空 | （空） | 跟随目标库的会话时区：服务端读取目标库当前与 UTC 的偏移，按这个固定偏移计算（不随夏令时变化）；读不到时报“时区未知” |
| 固定偏移 | `+08:00`、`+0800`、`+8`、`UTC+8`、`GMT+08:00`、`UTC` | 不受夏令时影响，边界稳定，推荐；范围 ±14:00 |
| IANA 名字 | `Asia/Shanghai`、`America/New_York`、`Europe/London` | 区分大小写；服务端内置时区数据，不依赖服务器系统；`Asia/Shanghai` 固定按 +08:00；不接受 `Local` |

- 时区保存在库里的 `timezone` 列只有 20 个字符，超过的名字（如 `America/Argentina/Buenos_Aires`）无法保存，请改用固定偏移（如 `-03:00`）。
- 夏令时：有夏令时的 IANA 区域在换季日附近，“按天”的分区边界会漂移一小时，按小时或分钟的分区还可能重复或缺失一个窗口，已存在的分区边界与新边界可能对不上。保存和预览时会给出提示，建议改用固定偏移。
- 目标库时区不固定或经常调整时，建议显式填写。页面上的提示只是辅助，是否合法以保存与预览时服务端的校验为准。

### 5.3 分区名与边界

分区名取该分区起始时刻：minute `p202610091504`、hour `p2026100915`、day `p20261009`、month `p202610`、year `p2026`；week 取该窗口的最后一天（`p<最后一天YYYYMMDD>`）。已存在的分区只要边界与期望一致就视为已存在，不论名字；将创建的分区与现有分区同名但边界不同会报冲突（`name_conflict`）。

MySQL / PolarDB 的边界是 `VALUES LESS THAN`，datetime 为 `'YYYY-MM-DD HH:MM:SS'`、int 为秒、bigint 为毫秒；SelectDB / Doris 每个分区一条 `ALTER TABLE db.t ADD PARTITION pXXX VALUES [("下界"), ("上界"))`，边界写成双引号字符串。

### 5.4 状态

状态由服务端读取目标表的真实分区后逐行计算（只读，逐行异步加载，结果缓存约 1 分钟），鼠标移到状态上可看原因，“刷新状态”会重新读取目标表：

| 状态 | 含义 |
|---|---|
| 正常 | 分区已是最新，没有需要执行的语句 |
| 待续建 N | 当前分区之后不足“预创建”个，还差 N 个 |
| 待清理 N | 已过去的历史分区超过“保留”个，有 N 个可清理 |
| 未分区 | MySQL / PolarDB 的表还不是分区表，可在“预览 / 执行”里初始化；SelectDB / Doris 需先在目标库建为 RANGE 分区表 |
| 异常 | 无法生成维护计划：表不存在、不是 RANGE 或 RANGE COLUMNS 分区、带子分区、字段类型不符、边界不连续或重名、一次要建超过 100 个、时区未知、库名被实例规则禁止等 |
| 未知 | 连不上或读不到目标库，不代表配置有问题 |
| 暂不支持 | 实例类型不在支持范围之列 |

状态旁的“需重组”表示表里有 `MAXVALUE` 分区、续建需要 REORGANIZE（定时维护不会执行）；“可初始化 / 不可初始化”标注未分区的表能否在页面里初始化。页顶统计卡为配置数、自动开（“开启维护”开关为开的配置数）、待续建、待清理、未分区、异常；统计卡对可见范围内的全部配置逐个检测后累计（最多前 1000 个），“未知”不计入。

### 5.5 续建与清理规则

- 续建：从现有最后一个有边界的分区继续向后接，保证边界连续；周期为月或年时，要求现有最后一个分区边界已是月初或年初，否则拒绝（`misaligned`）；所有分区都已过期时先补到包含当前时刻的分区（追赶）；单次最多创建 100 个，超过就拒绝（说明配置不合理）。
- 清理：边界早于当前时刻的是“历史分区”，只保留最近“保留数”个，更早的 `DROP PARTITION`；`MAXVALUE` 分区永不删除。
- MySQL 表里有 `MAXVALUE` 分区时无法直接 `ADD PARTITION`，改用 `REORGANIZE PARTITION`，会重写该分区的数据，标记为“重操作”，需要额外确认，定时维护不执行；SelectDB / Doris 没有 REORGANIZE，含 `MAXVALUE` 分区的表会直接拒绝。
- SelectDB / Doris 里读不到上界的分区会被视为“未知”：不会被删除，计划里给出提示，其余分区照常处理。

## 6. 定时自动维护

默认关闭，由管理员通过系统配置开启；自动执行默认只续建分区，不删除（除非单独开启清理）；永远不会初始化未分区的表，也不会执行 REORGANIZE。

| 配置项 | 默认 | 说明 |
|---|---|---|
| `partition.auto_run` | `false` | 启用自动维护 |
| `partition.auto_drop` | `false` | 自动删除过期分区 |
| `partition.auto_interval_minutes` | 180 | 自动维护间隔，5–1440 分钟，非法值回退 180 |
| `partition.notify_on` | `always` | 推送时机 |

开关每轮重读，修改后无需重启。首轮延迟 1 分钟；同一配置在“保护窗口”（间隔的一半，至多 30 分钟）内已有维护日志时本轮跳过，避免手动与定时、多个服务实例撞车。定时操作人为 `system`，每轮写一条系统记录（最多 100 项摘要）。

## 7. 限制与注意事项

- 定时维护只续建、可选清理，不会做初始化与 REORGANIZE。
- 单次最多创建 100 个分区，初始化最多 5000 个分区（超过 200 提醒）。
- 单个配置执行 10 分钟超时；预览 30 秒；库表列表 15 秒，表列表最多 3000 张。
- 状态检查每次 8 秒超时，单实例并发 2、全局并发 6；未知结果只缓存 15 秒。
- 推送 10 秒超时，不跟随重定向。

> 注意：SelectDB / Doris 的表列表不读取分区信息，因此表名下拉对它们既不过滤也不标“分区表”（所有表都列出，只有已经有配置的会标淡红），选中后会提示“还不是分区表，需先在目标库建为 RANGE 分区表”，即使表已经是分区表。状态以保存后的服务端计算为准。

## 8. 审计与安全说明

- 审计动作：分区维护-新增配置、编辑配置、删除配置、启用配置、停用配置、执行、执行初始化、定时执行，以及新增 / 编辑 / 删除 / 启用 / 停用推送通道、测试推送。执行前先写审计，写不进去就不执行。
- 权限在服务端校验：`partman.run` 只认按钮，不能用 `partman.edit` 代替；`partman.delete` 控制含 DROP 与初始化。
- 删除配置时在确认框里输入 `库.表`，维护日志一并删除，目标表的分区不动。
- 机器人密钥只写不读；日志与审计里不出现完整 webhook 地址。

## 9. 常见问题与排障

| 现象 | 可能原因 | 处理 |
|---|---|---|
| 状态“异常”：subpartition | 表带子分区 | 暂不支持，改用手工维护 |
| 状态“异常”：misaligned | 月 / 年分区的最后边界不在月初 / 年初 | 先在库里调整分区边界 |
| 状态“异常”：name_conflict | 将建的分区与现有分区同名但边界不同 | 手工整理现有分区 |
| 状态“未知” | 连不上或读不到目标库 | 检查实例连通性与账号权限 |
| 执行报“拿不到元数据锁” | `lock_wait_timeout=15` 内拿不到 | 业务低峰重试 |
| “该配置正在被另一个进程维护” | 跨进程锁 | 稍后重试 |
| 初始化被拒绝 | 前置检查不满足（有外键、唯一键不含分区字段等） | 按计划里“不满足”的项处理 |
| `int_overflow` | `int` 秒级时间戳超过上限 | 改用 `bigint` |
| 推送不到 | 通道未启用，或地址不在允许的域名里 | 检查通道与地址 |
| 一直“告警中”，续建之后也不消失 | 阈值大于“预创建数 + 1”（列表标“阈值过高”），或这张表的维护开关关着 / 计划失败（状态异常），没有续建 | 调小阈值或加大预创建数；检查启停开关与状态里的原因 |
| 没有收到可用分区告警 | 总开关没开；没有启用的推送通道；这张表在静默期，或阈值是 0；还没到下一轮检查（间隔同自动维护间隔） | 到“系统配置 › 分区维护”看总开关与间隔；“推送设置”里启用通道；“告警记录”里看有没有失败记录 |
| “告警设置”按钮是灰的，页面上方提示先执行脚本 | 没执行 `deploy/sql/280_partman_alert.sql` | 执行脚本后刷新页面（升级时安装脚本会自动执行） |
