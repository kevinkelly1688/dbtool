# 性能工单

性能工单把慢 SQL 变成可跟踪的问题：系统从慢日志等来源按“实例 + 库 + SQL 指纹”聚合并自动建单，按影响程度定级 P0–P3，指派给负责人，按 SLA 计时、超时逐级升级催办，直到修复并验证关闭。研发负责处理，DBA 负责验证、审批与兜底。

## 1. 功能概述

| 页面 | 菜单 | 用途 |
|---|---|---|
| 问题工单 / 详情 | 性能治理 › 问题工单 | 处理、验证、审批性能工单 |
| 团队榜单 | 性能治理 › 团队榜单 | 按团队统计健康度 |
| 采集配置 | 性能治理 › 采集配置 | 配置每个实例的采集来源与阈值 |
| 团队配置 | 性能治理 › 团队配置 | 团队负责人、升级对象与路由规则 |
| SLA 策略 | 性能治理 › SLA 策略 | 四个级别的时限与升级通知对象 |

### 1.1 工单从哪来

采集器按“实例 + 库 + SQL 指纹”聚合慢 SQL（平台慢日志、pt-query-digest、performance_schema、Doris 审计表、自定义采集 SQL 等），超过阈值就建单，并：

- 诊断问题类型：全表扫描无索引、缺少索引、前模糊 LIKE、列上套函数、深分页、`ORDER BY RAND()`、IN 过长、隐式转换、filesort、相关子查询等。
- 评估级别：按日均浪费的数据库时间、占比、平均耗时与日均次数判定 P0 到 P3，任一条件命中即定级。
- 路由负责人：按路由规则找团队和负责人；“纯缺少索引”类问题分给 DBA，其余分给研发。
- 去重：同一指纹只有一张工单，影响扩大时自动升级级别（级别只升不降，除非人工调级）。关闭后同一 SQL 再次出现会自动重开：被“误报关闭”的不重开；豁免关闭的仅在重新评估为 P0 时重开；其余关闭原因还要求影响分不低于 `perf.reopen_min_score`（默认 20）。

DBA 也可以手工建单（`perf.create`，见 4.2）。

## 2. 适用范围

性能工单支持 6 种实例类型：MySQL、PolarDB、PolarDB-X、SelectDB、Doris、ADB。其他类型的实例不能建采集配置或手工建单。

| 采集方式 | 来源 | MySQL | PolarDB | PolarDB-X | SelectDB / Doris | ADB |
|---|---|---|---|---|---|---|
| 平台慢日志 | 元数据库 `dbt_slow_logs`，复用慢日志采集 | ✔ | ✔ | ✔ | ✔ | ✖ |
| pt-query-digest | 慢日志表 `dbt_mysql_slow_query_review_history` | ✔ | ✖ | ✖ | ✖ | ✖ |
| performance_schema | `events_statements_summary_by_digest`，首次采集只建立游标 | ✔ | ✔ | ✖ | ✖ | ✖ |
| mysql.slow_log | `mysql.slow_log` 表（`log_output=TABLE`） | ✔ | ✔ | ✖ | ✖ | ✖ |
| Doris audit_log | `__internal_schema.audit_log` | ✖ | ✖ | ✖ | ✔ | ✖ |
| PolarDB-X statements_summary | `statements_summary_history` | ✖ | ✖ | ✔ | ✖ | ✖ |
| PolarDB-X SHOW FULL SLOW | `SHOW FULL SLOW` | ✖ | ✖ | ✔ | ✖ | ✖ |
| 自定义 SQL | 自定义采集 SQL | ✔ | ✔ | ✔ | ✔ | ✔ |

新建采集配置时按类型取默认值：MySQL、PolarDB、PolarDB-X、SelectDB、Doris 默认“平台慢日志”，ADB 默认“自定义 SQL”。

EXPLAIN 自动诊断按产品类型判断：只对 MySQL 系（自建 MySQL、阿里云 RDS、PolarDB、AWS RDS）执行；PolarDB-X、SelectDB / Doris、ADB 不做 EXPLAIN。超过 1 亿行扫描的 OLAP 大扫描规则只用于 SelectDB / Doris 与 ADB 产品，PolarDB-X 有 IN / EXISTS 子查询与分区键提示。

## 4. 操作指南

### 4.1 受理工单（研发）

目标：确认处理并承诺完成日。入口：性能治理 › 问题工单 › 我的待办 › 工单详情。

1. 打开工单，查看指标、诊断结论和优化建议。
2. 点“受理”，填写承诺完成日（不早于今天，不晚于 SLA 解决截止日）。
3. 确认后状态变为“处理中”。

预期结果：工单进入“处理中”，SLA 继续计时。截止日已过的工单最晚选今天，处理记录会标注“已超时受理”；需要更晚请先受理，再走“申请延期”。受理时如果工单还没有负责人，受理人自动成为负责人。

### 4.2 手工建单（DBA）

入口：问题工单页的手工建单入口（需要 `perf.create`）。

1. 填实例、SQL（真实样例）。库名、级别、负责人、备注可选。
2. 提交后系统对样例执行 EXPLAIN 并自动诊断。

约束：SQL 只支持单条 SELECT / UPDATE / DELETE / WITH，不能带分号；不超过 200000 字节，库名不超过 128 个字符。手工建单没有慢日志明细，影响指标为 0，级别留空时默认为 P2，不做自动评估；填了级别则按所填值。备注作为第一条评论。负责人留空时按路由规则自动指派。

### 4.3 标记修复（研发）

1. 工单处于“待受理”或“处理中”时点“已优化上线，申请验证”。
2. 必填修复方案，可同时填关联的 SQL 上线工单号（详情页给出跳转链接）。
3. 提交后记录修复前的耗时基线，状态变为“待验证”，SLA 暂停计时。

关联上线工单号需要先执行 `deploy/sql/060_perf_ext.sql`；工单号不存在会提示“SQL 上线工单 #N 不存在”。

### 4.4 申请延期与豁免（研发）

| 动作 | 允许的状态 | 校验 |
|---|---|---|
| 申请延期 | 待分派、待受理、处理中 | 次数不超过该级别上限；新日期晚于当前截止日且不超过一年；必填理由（至多 1000 字）；不能已有待审批申请 |
| 申请豁免 | 待分派、待受理、处理中 | 理由至少 10 字（至多 1000 字）；不能同时有待审批的延期 |
| 评论 | 任意状态（含已关闭） | 必填内容（至多 2000 字） |

### 4.5 DBA 的处理动作

| 动作 | 说明 |
|---|---|
| 指派 | 改负责人与团队；负责人必须是启用用户；待分派变为待受理 |
| 验证通过 / 不通过 | 通过后关闭（优化完成·已验证）；不通过必须写原因，工单回到处理中、通知负责人并累计重开次数 |
| 同意 / 驳回延期 | 同意：解决截止改为该日 23:59:59，已延期次数加 1，重置升级级别；驳回：清除申请 |
| 同意 / 驳回豁免 | 同意后关闭（豁免·接受现状）；驳回回到处理中、待受理或待分派 |
| 调级 | 级别必须有变化；调级后锁定，不再自动调整；SLA 时限按新级别重算（调高从建单时刻算，调低从当前算） |
| 切换处理方 | 改为 DBA 处理或改回研发（按路由重新找负责人）；改为 DBA 时负责人取跟进 DBA |
| 误报关闭 | 必须写原因，之后还有第二步确认：说明此后同一 SQL 再出现也不会重开，并要求键入工单号 `#编号`；第二步取消则不发请求 |
| 重开 / 重新诊断 | 重开回到待受理或待分派并累计次数；重新诊断可粘贴真实 SQL 替换样例（约束同 4.2；留空则用现有样例，处理方不会自动改变） |

> 注意：不能同意自己提交的延期或豁免申请，必须由另一位 DBA 处理，超级用户也一样；驳回自己的申请相当于撤回。验证通过、同意豁免、误报关闭在系统审计里是三个不同的动作，在工单时间线里都记为“关闭”。

工单被别人同时更新时会提示“工单刚刚被他人更新，请刷新页面后重试”，不会覆盖对方的操作。

### 4.6 配置采集

入口：性能治理 › 采集配置。每个实例一条采集配置。

1. 点新增采集配置（或使用按实例类型批量生成，为没有配置的实例生成默认停用的配置，确认后再逐个启用）。
2. 选实例、产品类型、采集方式，设置平均耗时阈值和窗口总耗时阈值，按需填排除规则、排除库、默认归属团队。
3. 先点“试采集”：只预览最近一个窗口的结果（最多 50 行），不建单、不动采集进度。
4. 启用后下一轮采集生效。

### 4.7 配置团队、路由与 SLA

- 团队配置：团队就是资源组。这里补充默认接口人（库负责人找不到时的兜底）、团队 TL（L2 升级，可多选）、总监（L3 升级，可多选）、是否参与排行与周报。群通知沿用资源组上配置的钉钉 / 飞书 / Slack webhook 以及[管理员指南](#help/sysadmin)通知渠道里的机器人。没有配置的团队仍会建单，只是没有默认接口人、TL 与总监。
- 路由规则：按“实例（空为全部）+ 库名正则 + 表名正则”分派到团队与负责人，正则整体匹配；表名正则留空表示不限制，工单涉及的任一张表匹配即命中（需先执行 `deploy/sql/060_perf_ext.sql`）；优先级数字小的优先。分派顺序：路由规则、实例“数据库”页里的库负责人、团队默认接口人；处理方为 DBA 的问题改派给 DBA 值班（系统配置 `perf.dba_users`，取未关闭工单最少的人）。“路由测试”输入实例、库、表（或粘贴一条 SQL 提取涉及的表），显示会命中哪条规则、指派给谁，只读，不建单。
- SLA 策略：见 5.2。保存前用“差异预览”列出变化的项，没有变化提示“没有变更”且不发请求；“重置”丢弃页面上未保存的修改。

## 5. 字段、状态与规则说明

### 5.1 状态与 SLA 计时

| 状态 | 含义 | SLA 计时 |
|---|---|---|
| 待分派 | 还没有负责人 | 计时 |
| 待受理 | 已指派，等负责人受理 | 计时 |
| 处理中 | 已受理，承诺了完成日 | 计时 |
| 待验证 | 研发标记已修复，等 DBA 验证 | 暂停 |
| 豁免审批中 | 研发申请豁免，等 DBA 审批 | 暂停 |
| 已关闭 | 验证通过、豁免通过、误报、长期未复现 | — |

### 5.2 默认 SLA 策略

在 SLA 策略页调整。新策略只对之后建立（或重算时限）的工单的受理 / 解决截止生效，已有工单的截止时间不变；升级总监小时数、催办间隔和最多延期次数在巡检或申请时读取当前策略，对存量工单立即生效。

| 级别 | 受理时限 | 解决时限 | 超过解决时限后升级总监 | 催办间隔 | 最多延期 |
|---|---|---|---|---|---|
| P0 | 4 小时 | 48 小时 | 24 小时 | 4 小时 | 0 次 |
| P1 | 24 小时 | 7 天 | 3 天 | 24 小时 | 1 次 |
| P2 | 72 小时 | 14 天 | 7 天 | 48 小时 | 1 次 |
| P3 | 72 小时 | 30 天 | 14 天 | 72 小时 | 2 次 |

保存校验：受理与解决时限 1–8760 小时且受理不大于解决，升级总监 0–8760 小时，催办间隔 1–720 小时，延期 0–20 次，必须一次提交 P0–P3 四个级别。

### 5.3 超时升级与静默

| 升级级别 | 触发条件 | 通知对象（默认） |
|---|---|---|
| 即将超时提醒 | 处理中，距解决截止不足时限窗口的 20%（且至少 4 小时），只提醒一次 | 负责人 |
| L1 催办 | 待分派或待受理且超过受理时限 | 负责人 |
| L2 | 超过解决时限 | 负责人、团队 TL、跟进 DBA |
| L3 | 超过解决时限再加“升级总监”小时数 | L2 的对象加总监，走全局渠道 |

L1、L2、L3 在同一级别内按催办间隔重复催办。每一级的通知对象可在“升级规则与通知对象”里配置（每级必须通知负责人，全局渠道列控制该级消息是否同时发到未关联资源组的通知渠道，默认都发）。升级通知对象从下一次升级起生效，需先执行 `deploy/sql/060_perf_ext.sql`，没执行时只能使用默认值。

静默规则只作用于 SLA 巡检的催办、升级和即将超时提醒，不影响建单、指派、评论等状态变更通知：

- P0 不受静默限制。
- P2、P3 周末静默，由 `perf.weekend_silent` 控制（默认开启）。
- 所有非 P0 级别在 `perf.quiet_hours` 时段（默认 `22-9`）静默。
- 静默期间 L1、L2、L3 动作被跳过，不延后补发；工单是否“曾超时”只在超过解决时限（L2 及以上）时记录。
- `perf.silent_mode` 开启后不发任何性能工单通知。

### 5.4 级别评估规则

系统配置 `perf.severity_rules`（JSON，页面只读展示）。按 P0、P1、P2 顺序评估，任一条件满足即命中，其余为 P3。默认值：

| 级别 | 日均浪费 DB 时间 | 占比 | 平均耗时且日均次数 |
|---|---|---|---|
| P0 | 至少 3600 秒 | 至少 30% | 至少 10000 ms 且至少 1000 次 |
| P1 | 至少 600 秒 | 至少 10% | 至少 5000 ms 且至少 100 次 |
| P2 | 至少 60 秒 | 至少 3% | 至少 3000 ms 且至少 10 次 |

占比条件还要求绝对量不低于该级别日均浪费阈值的 30%，避免“实例上只有一条慢 SQL 所以占 100%”被判为 P0。日均浪费等指标取近 7 天（或自首次出现起的天数）。占比的分母是该实例所有已建单问题近 7 天的总耗时，不是实例全部慢 SQL。非法 JSON 回退到默认值。

### 5.5 问题工单

页顶 6 张统计卡：

| 统计卡 | 含义 |
|---|---|
| 我的待办 | 指派给你且 SLA 计时中的工单（DBA 另含作为跟进 DBA 的待验证、豁免审批中工单），其中几张已超时 |
| 已超时 | SLA 计时中且已过解决截止 |
| 待分派 | 还没有负责人 |
| 待验证 | 等待 DBA 验证 |
| 本周新增 | 近 7 天新建的工单 |
| 本周完成 | 近 7 天关闭的工单（含豁免） |

页签（带数量角标，0 不显示）：我的待办、全部未关闭、待分派、待受理、处理中、待验证、审批中、已超时、已关闭、全部。可按级别、团队、实例、处理方（研发 / DBA）、问题类型、状态、来源、关键字（指纹、库、表、`#编号`）筛选，DBA 还可切换“全部团队 / 我的团队与我负责的”。默认按日均浪费 DB 时间倒序，可按日均浪费、平均耗时、日均次数、SLA 排序；超时的工单高亮。侧栏角标是你的待办数，橙色表示其中有已超时的，列表页“已超时”页签的角标为红色。

### 5.6 工单详情

指标（日均浪费 DB 时间、占实例已建单问题总耗时的比例、日均次数、平均与最大耗时、平均扫描与返回行）、诊断结论与优化建议、建议 DDL（需 DBA 评估后通过 SQL 上线执行）、执行计划、近 30 天趋势图（柱为每日总耗时，线为平均耗时，虚线标记修复日期）、处理记录和可用的操作按钮。

“修复效果”卡片与标记修复时记录的基线对比（修复当天与今天的数据不计）：修复前后的平均耗时、日均浪费 DB 时间，以及已观察天数和是否满足自动验证条件；DBA 的验证弹窗里有同样的对比。

### 5.7 团队榜单

入口：性能治理 › 团队榜单。按团队统计健康度：未关闭工单数、超时数、平均修复天数、近 12 周新增与完成趋势、未关闭问题类型分布（按浪费 DB 时间占比，最多 5 类加其他）。

- 时间范围（近 7、30、90 天）和处理方（研发、DBA、全部）只作用于团队表和顶部指标，近 12 周趋势与问题类型分布不受过滤。表里只含设置了团队且“参与排行与周报”的团队；完成数、按时率、平均修复天数只统计关闭原因为“已验证”的工单（豁免、误报、未复现不计）。
- 健康分 = 100 − 超时数 × 15 − 未受理数 × 5 − 日均浪费 DB 小时数 × 10 − (100 − 按时率) / 5，限制在 0–100；表格按健康分从低到高排序。

### 5.8 采集配置字段

| 字段 | 说明 | 约束与默认 |
|---|---|---|
| 实例 | 一个实例只能有一条配置，保存后不能换实例 | 类型须在支持范围内 |
| 采集方式 | 见第 2 节 | 采集方式须适用于该实例类型 |
| 平均耗时阈值 | 平均耗时达到阈值就建单 | 1–36000000 ms；新建默认 1000 |
| 窗口总耗时阈值 | 窗口内累计耗时达到阈值就建单，让高频小慢 SQL 也能建单 | 1–31536000 秒；新建默认 10 |
| 排除规则 | 正则，匹配 SQL 文本则忽略 | 至多 500 字符；新建默认忽略 `show`、`set`、`use`、`commit`、`rollback`、`begin`、`start`、`xa`、`flush`、`analyze`、`optimize`、`kill` 开头的语句 |
| 排除库 | 逗号分隔 | 至多 500 字符；新建默认 `mysql`、`information_schema`、`performance_schema`、`sys`、`__internal_schema` |
| 默认归属团队 | 路由找不到团队时使用 | 为空时取实例的第一个资源组 |
| 自定义采集 SQL | 仅“自定义 SQL”方式使用 | 至多 20000 字符；单条 SELECT、WITH 或 SHOW；禁止 `INTO OUTFILE`、`INTO DUMPFILE` 与危险函数（如 `sleep`）；保存与每次执行前都校验 |

自定义 SQL 的占位符是 `%(start)s` 与 `%(end)s`。明细模式返回 `db_name, sql_text, query_ms, rows_examined, rows_sent, ts`；聚合模式返回 `db_name, sql_text, exec_count, total_ms, max_ms, rows_examined, rows_sent, last_seen`。

采集窗口：每隔 N 分钟采集一次，也是每次采集的时间窗口，页面内可改，范围 5–1440 分钟，默认 60 分钟。距上次窗口结束满一个窗口的启用配置才会采集，长时间停机后一次最多补 24 个窗口，同时最多采集 3 个实例。当前环境不支持在页面里修改时，到「平台设置 → 系统配置」修改 `perf.collect_window_minutes`。

### 5.9 自动流转与后台任务

后台任务默认全部关闭，由系统配置 `perf.jobs` 决定（`collect`、`sla`、`verify`、`report` 的逗号组合，每分钟重读）。「采集配置」页显示本进程的后台任务开启状态。

| 任务 | 节奏 | 行为 |
|---|---|---|
| `collect` | 每分钟检查到期配置 | 采集并建单 |
| `sla` | 每 30 分钟 | SLA 巡检、催办与升级 |
| `verify` | 每天 10:05 之后 | 自动验证与长期未复现关闭 |
| `report` | 每周一 09:35 之后 | 发送周报；需要运行记录表 `dbt_perf_job_run`（`deploy/sql/017_perf.sql`），否则不发 |

自动验证：修复后观察 `perf.verify_days` 天（默认 3）；观察期内平均耗时或日均耗时任一下降达到 `perf.verify_improve_ratio`（默认 0.5，即至少下降 50%）、或不再出现，则验证通过并关闭；否则退回“处理中”，累计重开次数并通知负责人。长期未复现：待分派、待受理、处理中且来源为采集器的工单，连续 `perf.auto_close_absent_days` 天（默认 14，0 为关闭）没有再出现则自动关闭，再次出现会自动重开。

周报：全局渠道一条（全公司汇总加团队榜前 15），各团队一条（本团队统计加最多 8 张 SLA 计时中的待处理工单，并 @ 负责人）；固定近 7 天、只统计处理方为研发的工单；不能关闭，没有个人私信。

其他系统配置项：`perf.auto_explain`（默认 true）、`perf.explain_timeout_ms`（默认 3000，200–60000）、`perf.group_notify`（默认 true）、`perf.dba_users`。

## 6. 限制与注意事项

> 注意：升级与催办依赖后台任务 `sla`，周报依赖 `report`。`perf.jobs` 缺省为空时本进程不做任何采集、巡检和周报，需要管理员显式开启。

> 注意：自动验证与长期未复现关闭会自动关闭工单。如果业务上不希望自动关闭，请把 `perf.verify_days` 调大或把 `perf.auto_close_absent_days` 设为 0。

> 警告：误报关闭后，同一 SQL 再次出现不会重开。确认是误报再执行。

- 采集入库中途失败时，已写入的指标会被重复累加。
- 一次新建超过 5 张工单时，通知按团队汇总（每团队最多列 30 条）。
- 全局渠道会同时收到各团队的催办与周报，周报不能单独关闭。
- 后台任务不支持自定义 cron。
- 路由规则表名正则、关联上线工单和升级通知对象依赖 `deploy/sql/060_perf_ext.sql`，表缺失时降级为默认行为，写入时返回“请先执行 060_perf_ext.sql”。

## 7. 审计与安全说明

- 所有工单动作写系统审计，动作名为“性能工单-”加动作（建单、指派、受理、标记修复、评论、申请延期、同意延期、驳回延期、申请豁免、同意豁免、驳回豁免、验证通过、验证不通过、关闭、误报关闭、重开、级别变更、切换处理方、SLA升级、重新诊断），内容为“工单#N：前 200 字”。
- 配置变更写“性能工单配置-”加动作：采集配置新增 / 修改 / 删除、批量生成采集配置、团队配置、路由规则、SLA 策略修改、升级通知对象修改、采集窗口修改。
- 自定义采集 SQL 只读校验，且采集用账号只执行 SELECT、WITH、SHOW。
- 服务层所有保存与删除配置的接口再次校验 DBA 身份，不只依赖按钮码。

## 8. 常见问题与排障

| 现象 | 可能原因 | 处理 |
|---|---|---|
| 没有自动建单 | `perf.jobs` 没有 `collect`，或采集配置未启用，或阈值过高 | 在系统配置开启后台任务；用“试采集”确认能读到数据 |
| 试采集为空 | 采集来源没有数据（如 `slow_query_log` 未开、`log_output` 不含 `TABLE`、实例未开启慢日志采集） | 先检查对应来源，见[慢日志检索与慢 SQL 洞察](#help/slowlog) |
| 受理时报承诺日期超过 SLA 截止日 | 承诺完成日晚于解决截止 | 先受理，再用“申请延期” |
| “P1 最多延期 N 次，请联系DBA” | 已达该级别延期上限 | 联系 DBA 调级或豁免 |
| 无法同意延期或豁免 | 申请人是自己 | 请另一位 DBA 处理 |
| 标记修复时提示 `dbt_perf_issue_ext` 未创建 | 没有执行 `060_perf_ext.sql` | 在元数据库执行后重试 |
| 周报没有发出 | `perf.jobs` 缺 `report`，或缺 `dbt_perf_job_run` 表 | 开启任务并执行 `017_perf.sql` |
| 采集方式提示“不适用于 X 类型的实例” | 采集方式与实例类型不匹配 | 按第 2 节选择适用的采集方式 |

## 9. 验证状态与已知限制

验证状态与已知限制如下：

- 真实 MySQL 8.0 冒烟覆盖了状态机、乐观锁、排行榜、平台慢日志 / pt-query-digest / 自定义 SQL 的试采集、后台任务竞争与周报。
- 未在真库验证：performance_schema、`mysql.slow_log` 表、Doris audit_log、两种 PolarDB-X 采集方式（列名与权限）；UTC 服务器时区换算；钉钉 / 飞书 / Slack 真实发送与 @；页面 JavaScript 交互没有自动化测试。
- 周报是简化版；个人私信不发。

已知限制与文档说明：

- 慢日志页面没有“生成性能工单”按钮：`/perf/issues/from-slowlog` 接口存在（需要 `perf.create`），但页面上没有入口。
- ADB 的默认采集方式是自定义 SQL；平台慢日志采集器不采集 ADB。
- 系统配置 `perf.group_notify` 在代码里取 false 时会关闭所有群通知，与界面名称“按分组汇总通知”不完全一致，未核对其他影响。
- 采集窗口：页面保存要求 5–1440 分钟，但系统配置项 `perf.collect_window_minutes` 允许 1–10080，运行时只要求不小于 1。
