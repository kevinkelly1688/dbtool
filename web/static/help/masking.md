# 数据脱敏

数据脱敏让超级用户指定“哪些库表的哪些字段、用什么方式”脱敏。配置保存即生效，在线查询与 SQL 导出工单都按同一份配置处理。菜单：安全合规 › 数据脱敏（仅超级用户）。

## 1. 功能概述

- 配置：批量选择多个库表的多个字段，套用同一条规则（保留首尾、三段式、整体隐藏、自定义正则）。
- 执行：各引擎的在线查询结果、SQL 导出工单的结果按同一份配置脱敏；脱敏失败时按系统配置阻断或放行。
- 定位：不同数据库用不同方式把结果列对应到“库.表.字段”，精度分精确定位、保守匹配、字段路径匹配三档，见 2.2。

配置每次查询实时读取，没有缓存，保存即生效。

## 2. 适用范围

### 2.1 哪些实例在脱敏范围内

Redis、Elasticsearch / OpenSearch、Memcached 没有“表 / 字段 / 结果列”的结构，不在脱敏范围内。Oracle、Cassandra、TDengine 目前只有实例类型、没有在线查询入口，脱敏无从生效，页面里不提供。范围外的实例不出现在页面的实例下拉里，其数量在提示中说明。

| 数据库 | 在线查询 | SQL 导出工单 |
|---|---|---|
| MySQL、PolarDB、PolarDB-X、ADB、SelectDB、Doris | ✔ | ✔ |
| SQL Server | ✔ | ✔ |
| PostgreSQL、ClickHouse、MongoDB | ✔ | ✖（没有导出工单入口） |
| Redis、Elasticsearch / OpenSearch、Memcached | ✖ | ✖ |

只处理 SELECT（含 WITH）的结果；`SHOW`、`EXPLAIN`、`DESC` 不脱敏；MongoDB 只处理 `find`、`aggregate`、`distinct`。

### 2.2 各数据库怎么脱敏

页面顶部的标签显示所选实例的数据库类型和“结果列定位”精度（精确定位、保守匹配、字段路径匹配）：

| 数据库 | 字段层级 | 结果列怎么定位 | 精度 |
|---|---|---|---|
| MySQL、PolarDB、ADB | 库 › 表 › 字段（来自目标库 `information_schema.COLUMNS`） | goInception 语法树逐列溯源（含别名、子查询、JOIN、UNION）；表达式列再按列名保守补一遍，来源是视图的列再按视图定义展开补一遍；实例没有配置 goInception 时降级为按结果列名保守匹配 | 精确 |
| SQL Server | 库 › 架构.表 › 列 | 执行前让服务端分析结果集每列的来源（`sys.dm_exec_describe_first_result_set`），视图与基表两层都对照，视图里的表达式列再按视图定义展开补一遍；无法分析（临时表、动态 SQL）时降级为保守匹配 | 精确 |
| PostgreSQL | 库 › 架构.表 › 列 | 结果集描述里自带每列的表 OID 与列号，反查即得；表达式列、视图列再按列名和视图定义展开保守补一遍 | 精确 |
| SelectDB、Doris、PolarDB-X、ClickHouse | 库 › 表 › 列 | 没有来源信息：按结果列名、别名和表达式引用匹配；引用了敏感字段的函数或运算结果列会整列脱敏，调用了存储函数 / 自定义函数的列也会整列脱敏（ClickHouse 除外），来源是视图的列按视图定义展开（第 6 条），宁多勿漏 | 保守 |
| MongoDB | 库 › 集合 › 字段路径 | 按字段路径匹配返回的文档（嵌套 `profile.phone`、数组元素 `contacts[].mobile`；管道里改名输出的字段一并脱敏；视图按 `viewOn` 与视图的管道展开，见第 6 条） | 路径 |

PolarDB-X 的字段读取与 MySQL 相同，但不使用 goInception 语法树，视同 SelectDB / Doris 完全按列名保守匹配。原因：goInception 取列来源要连目标库拉表结构，而 PolarDB-X 的建表语句含 `dbpartition by`、`tbpartition by`、`GLOBAL INDEX`、广播表等非 MySQL 语法，没有在真实实例（AUTO 与 DRDS 两种模式）上验证过 goInception 能否取到列来源，而失败时的处置只能二选一（阻断或放行未脱敏数据）。后果是不同库表里同名的列也会被脱敏，用 `/*+TDDL:node()..*/` 按物理表名查询时列名照样命中。

保守匹配的意思：结果列满足任一条件就整列脱敏：

1. 列名（或别名）与已配置的字段名相同；
2. 列的表达式里引用了已配置的字段名（如 `concat(phone,'')`、`substr(phone,1,3) AS p`）；
3. 引用了被前两类污染的别名（子查询、CTE；传播最多迭代 8 轮）；
4. 调用了**非内置函数**（存储函数、自定义函数，如 `select fn_get_phone(1)`、`select dbo.fn_x(id)`），或取自 FROM 里的自定义表值函数（SQL Server 的 `cross apply dbo.f(…) x`、PostgreSQL 的 `from public.get_users(1)`）：函数体里读了哪些字段，语句里看不出来，整列按本实例已配置字段里**最严**的一条规则脱敏（与参数是不是敏感字段无关），别名同样视为被污染。
5. 取自**变量或表变量**：敏感字段的值可以先放进变量再取出来，列名和敏感字段对不上，所以污染也传给变量名。SQL Server 的 `DECLARE @k = (SELECT …)`、`SET @k = …`（含 `+=` 等）、`SELECT @k = …` / `SELECT @s += …`，MySQL 的 `SET @k = …`、`@v := …`，后面引用这些变量的结果列按被污染处理；SQL Server 的表变量（`DECLARE @t TABLE (…)`）被 `INSERT INTO @t SELECT … / VALUES (…)` 写入了敏感字段（或调用了自定义函数）的值时，这个表变量的所有列都按最严的一条规则脱敏（写入来源是 `*` 时按配置里最严的规则），换个列名取出来也不会漏。
6. 来源是**视图**的列：配置写在基表字段上时，视图可以把字段改名（`phone AS mobile`）、套表达式（`left(phone,3) AS head`）、套另一个视图或自定义函数，结果列的名字和来源都看不出它来自敏感字段。执行前平台从目标库读出语句用到的视图的定义（连同定义里又用到的视图，嵌套最多 8 层），把定义里的别名、表达式引用、自定义函数调用像子查询 / CTE 一样顺着传到视图的输出列，外层语句再引用这些列就脱敏。视图定义只用于分析，不会被执行。支持 MySQL 系（MySQL、PolarDB、ADB、SelectDB、Doris、PolarDB-X）、SQL Server、PostgreSQL（含物化视图）、ClickHouse（含物化视图、实时视图、窗口视图）和 MongoDB（视图 = 源集合 + 聚合管道）。

视图定义从各库的目录里读：MySQL 系读 `information_schema.VIEWS`，SQL Server 读 `sys.views` 与 `sys.sql_modules`，PostgreSQL 读 `pg_get_viewdef`，ClickHouse 读 `system.tables.as_select`。只按语句里写的对象名去查，所以每条脱敏的 SELECT 多几次目录查询（有嵌套视图时每多一层多一次）；系统库 / 系统架构（`mysql`、`sys`、`information_schema`、`system`、`pg_*` 等）里的视图不查；实例上没有配置脱敏字段时不查。MySQL 系与 PostgreSQL 来源是视图的列、SQL Server 视图里的表达式列，都会再按展开后的定义补一遍；SQL Server 的视图列能直接溯源到基表时仍按基表精确匹配；ClickHouse 本来就整体按名字匹配，展开后视图里的别名、表达式一并算进去。ClickHouse 特有的 `WITH <表达式> AS <别名> SELECT …` 写法（别名取表达式的值）也认得，语句里和视图定义里都一样。

MongoDB 的视图由 `listCollections` 的 `viewOn`（源集合，也可能是另一个视图）与 `pipeline`（聚合管道）定义。查询视图等于先对源集合跑视图的管道、再跑语句自己的管道，所以平台把视图的管道接在语句的管道前面，沿 `$project`、`$addFields`、`$set`、`$group`、`$replaceRoot`、`$replaceWith` 里的改名追踪（和语句里自己写管道时一样，见 2.2 表里 MongoDB 一行）；视图的源集合、视图管道里 `$lookup` / `$graphLookup` / `$unionWith` 引用的集合，也算“语句涉及的集合”去匹配脱敏配置；视图套视图、`$lookup` 到视图都会递归读取。直接给视图本身配置字段路径同样有效。

读不到视图定义按**脱敏失败**处理：账号没有查看视图定义的权限（MySQL 的 `SHOW VIEW`、SQL Server 的 `VIEW DEFINITION`）、视图加密、定义看不懂（超过 1 MB、引号没结束等）、目录查询出错（权限不足、超时、连接错误）、视图嵌套超过 8 层、一条语句里涉及的视图超过 100 个。处理方式同其它脱敏失败（见 5.3）：`query.block_on_mask_error` 开启时阻断，缺省（关闭）时放行结果并在页面提示是哪个视图——其余的列已经按配置脱敏，只有经过那些视图的列可能漏；SQL 导出工单遇到这种情况一律中止导出。目标库根本没有视图目录（`information_schema.VIEWS` 不存在或列不兼容）不算失败，只是不展开。

第 4 条用各数据库的内置函数清单判断：带限定的名字（`库.fn(`、`dbo.fn(`、`schema.fn(`）一律算自定义函数，系统架构（`sys`、`pg_catalog`、`information_schema`）与 SQL Server 的 xml / hierarchyid / geography 方法除外；不带限定的名字不在清单里就算自定义函数。清单不全只会多脱敏，不会漏。有精确来源的普通列（直接取自某张表的列）不受影响。ClickHouse 的内置函数太多、清单列不全，目前不做这一条（自定义函数 `CREATE FUNCTION` 的结果列只按前三条匹配）。

存储过程（`CALL`、`EXEC`）在线查询与导出工单本来就不放行，能返回数据的只有在 SELECT 里调用函数这一条路。

会有少量误伤（别的库表里恰好同名的列也会被脱敏）；用 `AS` 改别名、套函数、经子查询 / CTE 的别名传递，都认得出来，认不出的几种写法见第 6 节。同一个字段名在不同位置配置了不同规则、又分不清来源时，取最严的一条（整体隐藏，其次保留位数少的，其余最后）。

> 注意：`REQUIRE_GOINCEPTION` 环境变量开启（生产推荐的严格模式）后，MySQL 系实例没有配置 goInception 时不再降级为保守匹配，而是直接报“数据脱敏异常”并阻断，不看 `query.block_on_mask_error`。goInception 已配置但调用失败属于“脱敏失败”，按 `query.block_on_mask_error` 处理。

## 3. 前提条件与权限

- 仅超级用户可访问页面与接口（`/settings/masking`、`/api/v1/settings/masking/...`），没有按钮级权限码。
- 需要先建脱敏策略表：执行 `deploy/sql/230_masking_policy.sql`（`dbt-admin bootstrap` 或 `install.sh --bootstrap` 或 `--only-sql` 会自动执行）。没建时不能保存脱敏策略，查询结果不脱敏。
- 系统脱敏总开关 `query.mask_enabled` 需要为 `true` 才会真正脱敏（缺省 `false`）；字段上的“启用”只管那一条配置，不等于总开关。

## 4. 操作指南

### 4.1 配置向导：选字段、选规则

1. 顶部选实例，再选库（库不多时可选“全部库”，会逐个加载，库多时较慢）。
2. 选字段（左侧）：可以跨库、跨表多选；标题旁显示已选字段数及涉及的表数、库数。
   - 按表 / 按字段名两种视图：“按字段名”把所有表里的同名字段聚合成一行（如 `mobile` 出现在 3 张表），勾一下就选中全部，是批量最快的方式。
   - 筛选：关键字（多个词用空格）、状态（全部、疑似敏感、未脱敏、已脱敏）。“疑似敏感”只是按字段名猜（手机、身份证、银行卡、邮箱、姓名、地址、微信），仅作提示，不会自动脱敏；“选中疑似敏感”一键勾选所有还没脱敏的。
   - 粘贴清单：从 Excel 或文档粘贴，每行一个 `库.表.字段`、`表.字段` 或只写字段名（匹配当前实例所有同名字段），按行从右往左匹配，并告诉你哪几行没匹配到。PostgreSQL、SQL Server 的表带架构，如 `public.account.phone`；MongoDB 写 `集合.字段路径`。勾选“目录里没有的完整路径也添加进来”后，写了完整路径（库.表.字段）但目录里没有的行也会被添加。
   - 字段目录不全：一个库最多读取前 30000 个字段，超出部分用“粘贴清单”按名字选；MongoDB 的字段来自对每个集合最近文档的采样，可能不全，一个库最多读取前 100 个集合，缺的路径在“补充字段路径”里手动添加（`集合.字段路径`，如 `users.profile.wechat`）。
3. 选规则（右侧），一次只应用一种规则到所选字段；同一字段只保留一条规则，应用新规则会覆盖它原来的规则。
4. 生效范围：只对所选的“库.表.字段”（精确匹配，同名字段在别的表里不受影响）；或“该实例所有表里的同名字段”（写成 `*.*.字段名`，新建的表里同名字段也自动脱敏）。
5. 应用只是暂存，保存后才生效；底栏显示“待保存 N 项（新增、覆盖、移除、启停）”。点“保存并生效…”会弹出变更差异表，确认后才真正生效，并写入系统审计。有未保存变更时离开页面会提示。

选字段时下方会给出影响面板：将对几张表的几个字段设置脱敏；哪些字段已有别的规则会被覆盖；数值类型（脱敏后以文本返回，金额、数字列通常不需要脱敏）、类型不统一（如部分文档里是数字：先转成文本再脱敏，结果按文本返回）、JSON / Map 类型（对其中所有文本值逐个按规则处理，不区分键名）等提示；所选字段含多类疑似敏感数据时，可以点“每类用各自的推荐规则”。

### 4.2 管理已配置字段

“已配置字段”列出该实例所有已配置的字段：范围（精确，或任意库表的同名字段）、规则、示例、启用开关。支持筛选，以及批量启用、停用、移除（同样先暂存，保存后生效）和“用所选字段改规则”（带回向导换一种规则）。

### 4.3 开启总开关

系统脱敏总开关关闭时，页面顶部有橙色横幅，带“开启总开关…”按钮：确认后把 `query.mask_enabled` 置为 `true`，并写一条系统审计“数据脱敏总开关”（含原值与导出开关状态），立即生效、无需重启。页面只提供开启；关闭脱敏降低保护，仍需直接改系统配置。已开启时重复操作幂等，不重复记审计。

## 5. 规则与字段说明

### 5.1 脱敏规则

| 方式 | 效果 | 参数与说明 |
|---|---|---|
| 保留首尾 | 前 N 位 + `***` + 后 M 位，如 `138***5678` | 前、后位数各 0–64；按字符计；中间固定三个星号，不泄露长度；值太短时自动少保留（先保前缀、再缩后缀），保证至少隐藏 1 个字符 |
| 三段式 | 按长度三等分（余数依次给中段、后段），隐藏其中一段，如 `138****5678` | 隐藏第 1、2 或 3 段；星号个数与被隐藏的字符数一致（会泄露长度）；需要不泄露长度请用“保留首尾” |
| 整体隐藏 | 一律显示 `***` | 对非 MongoDB 页面按钮显示“整列隐藏”，MongoDB 显示“整字段隐藏” |
| 自定义正则 | 正则 + 要隐藏的分组 | 高级用法。正则至多 255 字符，隐藏分组为 1 到分组总数；固定不区分大小写、取首个匹配；命中时把隐藏分组换成等长 `*`，输出只含到“最后一个参与匹配的分组”为止的各分组；正则不匹配时原值原样返回；若中间分组没参与匹配则报错“脱敏正则的第 N 组没有参与匹配”，该错误按脱敏失败处理，请谨慎使用 |

常用预设：手机号 3+4、身份证 3+4、银行卡 6+4、姓名 1+0、邮箱 2+0、地址 6+0。“试算”里可以直接改“原值”看结果，页面试算与服务端共用同一份测试向量，结果一致。

通用处理：空值（`NULL`、空串、`0`、`false`）原样返回；数值先转文本再处理，结果一律是文本；嵌套的 map 与数组（JSON、Map 类型、Mongo 嵌套文档，PostgreSQL 的 json / jsonb、ClickHouse 的 Map / Array / Tuple）对其中每个叶子值逐个处理，键名不变。

### 5.2 保存请求的限制

| 项 | 限制 |
|---|---|
| 一次保存 | 至多 2000 项，请求体至多 4 MB |
| 操作 | `set`、`remove`、`enable`、`disable`；对不存在的策略做 `remove`、`enable`、`disable` 被静默忽略 |
| 库名 / 表名 / 字段 | 库名至多 128，表名至多 255，字段至多 255；库与表要么都是 `*`，要么都写具体名字 |
| 唯一性 | 同一实例同一库表字段只有一条策略；运行时按编号顺序先匹配到的生效 |
| 事务 | 一次保存在一个事务里，并写一条审计；无实际变更不写审计 |

### 5.3 导出与失败策略

- SQL 导出工单默认脱敏，开关是系统配置 `export.mask_enabled`（默认开启，设为 `false` 关闭）；系统脱敏总开关 `query.mask_enabled` 关闭时导出也不脱敏。导出时脱敏失败会中止导出，不会产出带原值的文件；结果里会写明“已脱敏”的列。唯一的例外是超级用户在提交导出申请时勾选的“导出原值（不脱敏）”（必须写理由、审批人可见、SQL 防火墙强制脱敏的列仍会脱敏，详见[数据导出](#help/export)的 5.4），它只影响那一张导出工单。
- 在线查询脱敏失败：`query.block_on_mask_error=true` 时阻断、不返回数据（返回“数据脱敏异常，结果未返回，请联系管理员。”）；`false`（缺省）时放行未脱敏的结果并在页面提示。SQL 防火墙强制脱敏的列脱敏出错一律阻断，不看该开关。
- 日志：查询日志记录“是否脱敏、是否命中规则”；保存配置写入系统审计。

| 配置项 | 缺省 | 说明 |
|---|---|---|
| `query.mask_enabled` | `false` | 脱敏总开关 |
| `export.mask_enabled` | `true` | SQL 导出工单是否脱敏 |
| `query.block_on_mask_error` | `false` | 在线查询脱敏失败时阻断（`true`）还是放行（`false`） |

## 6. 限制与注意事项

> 注意：保守匹配没有表级精度。ClickHouse 的 `SELECT *` 靠结果列名命中；不同库表里恰好同名的列也会被脱敏，这是“宁多勿漏”的代价。

> 注意：没有表级“免脱敏名单”（谁能看原值），所有人一律脱敏。

- MongoDB 的脱敏必须在文档整形成表格之前做；已知不覆盖 `$facet` 子管道内部的改名、`$setWindowFields` 等少见阶段里的改名。
- 配置不区分库表的“该实例所有表里的同名字段”会对任何同名列生效，新建的表同名字段自动脱敏。
- 调用存储函数 / 自定义函数的结果列按“该实例所有已配置字段里最严的一条”脱敏，哪怕函数其实不碰敏感数据；如果配置里有“整体隐藏”，这类列就显示 `***`。个别内置函数（尤其 Doris / ADB 的扩展函数、PostgreSQL 的少见函数）不在清单里时同样会被整列脱敏。ClickHouse 的自定义函数目前不识别。
- 往表变量里写入了敏感字段的值后，这个表变量的所有列都按最严的一条规则脱敏，同一个表变量里不敏感的列偶尔会被一起脱敏；没有写表变量的脚本，脱敏行为不变。
- 保守匹配认不出这几种把敏感字段的值换个列名输出的写法：用列名列表给 CTE / 派生表的列改名（`WITH c(z) AS (SELECT phone …)`、`(SELECT phone …) d(z)`）、`PIVOT` / `UNPIVOT`、`VALUES` 派生表（`CROSS APPLY (VALUES (u.phone)) v(c)`）、`FROM` / `CROSS APPLY` 里的内置表值函数（`STRING_SPLIT`、`OPENJSON`、MySQL 的 `JSON_TABLE`、PostgreSQL 的 `unnest(…)`）。SelectDB、Doris、PolarDB-X、ClickHouse 和没配 goInception 的 MySQL 系实例只有保守匹配，这些写法会漏脱敏；MySQL + goInception、SQL Server、PostgreSQL 先按语法树 / 服务端给出的来源判断，这几种写法能不能追到原字段没有在真实实例上验证。这是保守匹配一直有的限制，不是新版本引入的。
- 视图展开（2.2 第 6 条）和保守匹配的其它规则一样按名字传递污染、没有表级精度：视图定义把敏感字段改成某个名字后，同一条语句里别的表恰好同名的列也会被脱敏。SQL Server 视图定义里显式写了列清单（`CREATE VIEW v (a, b) AS …`）时，输出列名按位置取自清单；查询体是 `*` 时清单里的每个名字都按最严规则处理。MongoDB 视图的追踪覆盖的阶段与语句里自己写管道时一样，不覆盖 `$facet` 子管道内部的改名、`$setWindowFields` 等少见阶段；ClickHouse 视图定义里调用的自定义函数（`CREATE FUNCTION`）认不出来，同第 4 条。
- 实例上一条脱敏字段都没配置时，这些规则都不生效（脱敏流程不会执行）。
- 对象列表上的“敏感列数”对 PostgreSQL、ClickHouse、MongoDB 没有统计。

## 7. 审计与安全说明

- 保存配置写系统审计“数据脱敏配置变更”（内容含新增、覆盖、移除、启停计数，最多列 12 项）；开启总开关写“数据脱敏总开关”。
- 权限校验点：整个页面与接口仅超级用户。
- 在线查询的脱敏发生在结果返回之前，查询日志记录“是否脱敏、是否命中规则”。

## 8. 常见问题与排障

| 提示 | 原因与处理 |
|---|---|
| 还没有建脱敏策略表 | 需要执行 `deploy/sql/230_masking_policy.sql`（`dbt-admin bootstrap` 或 `install.sh --bootstrap` 或 `--only-sql` 会自动执行）；没建时不能保存脱敏策略，查询结果不脱敏 |
| 系统脱敏总开关已关闭 | 系统设置 `query.mask_enabled` 不是 `true`，保存的配置暂时不生效，在线查询和 SQL 导出工单返回的都是原值；横幅上的“开启总开关…”按钮可直接开启（确认后写系统审计） |
| SQL 导出工单的脱敏已关闭 | 系统配置 `export.mask_enabled` 为 `false`：在线查询会脱敏，导出工单导出的是原值 |
| 另有 N 个实例不在脱敏范围内 | Redis、Elasticsearch、Memcached 等没有表字段结构的类型，见 2.1 |
| 无法分析该语句的结果列来源 | SQL Server 的临时表、动态 SQL 等；已降级为保守匹配，可能多脱敏 |
| 不是敏感字段的列也显示成脱敏结果 | 保守匹配宁多勿漏，常见原因：列的表达式引用了已配置的字段名；调用了存储函数 / 自定义函数；取自被污染的别名、变量或表变量、视图（见 2.2 的第 1–6 条）；同名字段在别的库表里配置过（保守匹配没有表级精度）。有精确来源的普通列不受影响 |
| 未配置 goInception，按结果列名保守匹配 | MySQL 系没配 goInception 时的降级；配置后改为精确定位；严格模式下会直接阻断 |
| 返回“数据脱敏异常，结果未返回” | 脱敏失败且 `query.block_on_mask_error=true`；请排查 goInception 连通性、视图定义是否读得到（下面两行），或评估后临时设为 `false` |
| 视图 xxx 的定义读不到或看不懂，经过这些视图的结果列可能没有脱敏 | 脱敏需要读视图定义（见 2.2 第 6 条），但查询账号没有查看视图定义的权限（MySQL 的 `SHOW VIEW`、SQL Server 的 `VIEW DEFINITION`，ClickHouse 的 `system.tables` 里 `as_select` 为空）、视图加密、定义超过 1 MB 或看不懂（MongoDB：视图的 options 里没有 `viewOn`、管道格式不对）。处理：给查询账号补权限；确实不能读的视图，不要通过它查询敏感数据。放行时其余的列（字段）已按配置脱敏，只有经过这个视图的列可能漏 |
| 读取视图定义失败，经过视图的结果列可能没有脱敏 | 查视图目录出错（权限不足、超时、连接错误；MongoDB 是账号没有 `listCollections` 的权限），或视图嵌套超过 8 层、一条语句涉及的视图超过 100 个；具体原因看服务日志里的“读取视图定义失败”“数据脱敏失败” |

## 9. 验证状态与已知限制

验证状态与已知限制如下：

- SQL Server 的 `sys.dm_exec_describe_first_result_set`、PostgreSQL 的 `Parse + Describe`、ClickHouse HTTP、MongoDB 真实服务端都只用假后端验证过；对着真实实例的冒烟清单：视图、别名、子查询、`concat(phone,'')`、`jsonb` 列、Mongo 嵌套与 `$lookup`、管道 `$project` 改名，尚未执行。
- 存储函数 / 自定义函数的识别、变量与表变量的传播（保守匹配第 4、5 条）只用语句文本和假后端测试过，没有在真实 MySQL、SQL Server、PostgreSQL 上建函数、跑含变量 / 表变量的批处理验证；内置函数清单按各数据库文档整理，没有逐个对照真实版本。SQL Server 的内联表值函数，服务端能否把结果列溯源到基表，也没在真实实例上确认（能溯源时按基表列精确匹配，不能时整列脱敏）。
- 视图展开（保守匹配第 6 条）只用手写的典型视图定义和假后端测试过，没有在真实 MySQL、SQL Server、PostgreSQL、ClickHouse、MongoDB 上建视图验证：MySQL 的 `VIEW_DEFINITION`、SQL Server 的 `sys.sql_modules.definition`、PostgreSQL 的 `pg_get_viewdef`、ClickHouse 的 `system.tables.as_select` 实际输出的格式（对象名是否带库名、是否规范化），MongoDB 真实驱动解出来的 `options.pipeline` 的类型（代码按有序的 `bson.D` 处理，并把 `bson.M` / map 统一转成 `bson.D`），以及 SelectDB / Doris / PolarDB / ADB / PolarDB-X 的 `information_schema.VIEWS` 能不能用、返回的定义里列别名全不全，都没有在真实实例上确认。goInception 对视图列报的来源（视图本身还是基表）也没有确认，两种情况都能处理：来源是视图的列会再按展开的定义补一遍，来源是基表的列按基表精确匹配。
- PolarDB-X 上 goInception 未在真实实例（AUTO 与 DRDS 两种模式）验证，所以走保守匹配；日后验证可用后，才能改回精确定位。
- 保守匹配没有表级精度；表级“免脱敏名单”没有做。

文档与界面差异：

- 页面“开启总开关…”确认框与英文界面里把导出开关写成 `export_data_masking`、把阻断开关写成 `query_check`，真实键为 `export.mask_enabled` 与 `query.block_on_mask_error`（`query_check` 仅是接口 JSON 字段名）。本章使用真实键名。
- 审计页对“数据脱敏配置变更”“数据脱敏总开关”的分类规则未在 `internal/audit` 里找到，页面上显示的分类未核对。
- 前端交互细节（“选中疑似敏感”“每类用各自推荐规则”“未保存变更离开提示”）只核对到按钮文案，行为未运行验证。
